# Chapter 1 — Technical concerns in the English source

This file records material technical inaccuracies or oversimplifications in the English source. These are source-author concerns, not translation errors. The Chinese translation should not silently rewrite the source; confirm any source corrections with the author/editor.

## High

1. **Monotonic write consistency is defined incorrectly** (section “Consistency spectrum model”). The source says that after a write is acknowledged, subsequent reads from that replica return the updated value. That describes a read-your-writes-style guarantee, not monotonic writes. Monotonic writes normally guarantees that writes issued by one process are observed in the same order by all processes (or replicas); it does not define the ordering of reads after an acknowledged write. The current Chinese translation faithfully follows the source, so the source definition needs correction.
2. **Strong consistency is described as all replicas having identical data at all times** (section “Consistency spectrum model”). This is an overly strong and misleading characterization. Strong consistency is commonly specified through a formal guarantee such as linearizability; it does not require every physical replica to contain identical state at every instant. Replication lag, quorum protocols, and leader-based implementations make the distinction important. The text should define the intended consistency model rather than equating it with instantaneous physical equality across all replicas.

## Medium

1. **The source equates 99% reliability with failing 1% of the time** (section “Reliability”). Reliability is a probability of performing without failure over a specified mission time and under defined conditions; “1% of the time” is not a well-defined complement without specifying the time window and failure model.
2. **Synchronous replication is presented as updating every replica simultaneously** (sections “Data replication” and “Strong consistency”). Real systems use different replication and acknowledgement policies, including quorum-based and leader-based approaches; blocking synchronous replication to every replica is not a general recipe for consistency.
3. **Consensus is oversimplified as all replicas agreeing before updating data** (section “Consensus protocols”). Consensus protocols agree on an ordered value or log entry under defined fault assumptions; they do not necessarily make every replica synchronously apply an update before the operation can proceed.
4. **Monotonic read consistency is described as preventing clients from seeing another client's updates as stale** (section “Consistency spectrum model”). Monotonic reads guarantee that a client's successive reads do not move backward relative to values it has already observed. They do not guarantee that the client sees every update made by other clients; the source confuses monotonic reads with a stronger freshness guarantee.
5. **Locking is said to ensure reads always return the latest write** (section “Locking”). A lock can serialize conflicting operations, but read guarantees depend on the lock scope, isolation level, transaction boundaries, and whether all reads use the same coordination mechanism.
6. **Data versioning is said to make reads always return the latest version while allowing concurrent writes** (section “Data versioning”). Version numbers alone do not establish a globally latest version or resolve concurrent updates; ordering, conflict resolution, and visibility rules are also required.
7. **The parallel availability formula assumes independent failures without stating the assumption** (section “Availability in parallel versus in sequence”). The expression 1 − (unavailability₁ × unavailability₂) is valid only when component failures are independent and either component can fully serve the request. Common-mode failures and shared dependencies can materially reduce actual availability.
8. **The MTBF/MTTR discussion overstates what the metrics establish** (section “Measuring reliability”). High MTBF and low MTTR can contribute to higher availability, but they do not alone establish overall reliability; failure definitions, operating conditions, repair assumptions, and failure distributions matter. MTBF is also not a universal predictor of an individual component’s remaining lifetime.
9. **The source calls latency and throughput inversely related** (section “Latency Versus Throughput”). They can be correlated under saturation and queueing, but there is no universal inverse relationship. Workload, concurrency, batching, service time, and capacity all affect the relationship.
10. **The CAP theorem is reduced to “at most two” guarantees** (section “CAP theorem”). This popular shorthand can mislead readers into thinking a system chooses two properties permanently. The more precise statement concerns the behavior of a distributed read/write system during a network partition: it cannot guarantee both linearizability and full availability for every request. Outside partitions, the CAP trade-off does not force the same choice.
11. **The checkpointing descriptions are presented as general definitions** (section “Checkpointing”). Stopping all mutations for synchronous checkpointing and allowing all mutations during asynchronous checkpointing are particular implementation strategies, not universal definitions. Consistent snapshots can be created without globally stopping writes, and asynchronous snapshots need not inherently leave server states inconsistent.
12. **RPO is presented as requiring a fixed checkpoint interval without qualification** (section “Recovery point objective”). An RPO of 15 minutes does not, by itself, mean a checkpoint must be taken exactly every 15 minutes. Recovery-point guarantees depend on checkpoint completion, log shipping/replication, failure timing, and the recovery mechanism.
13. **The statement that every additional “nine” requires an exponential increase in resources is too categorical** (section “Measuring availability”). Higher availability targets generally become more expensive, but the cost curve depends on architecture, failure domains, operational maturity, and the availability model; it is not universally exponential.
14. **The definition of scalability implies performance grows with resources** (section “Scalability”). Adding resources does not necessarily increase performance proportionally; bottlenecks, coordination overhead, serial portions of workloads, and data locality can limit or reverse gains.

## Low

1. **The availability table labels 99.5% as “2 nines”** (table “Availability percentages represented in nines”). This is an informal and potentially confusing label; 99.5% is more clearly stated as 99.5% rather than exactly “two nines.”
2. **The MTTR equation contains a source typo** (equation in “Mean time to repair”): “Total Maintenance Tim” is split as “Total Maintenance Tim}e”. Confirm and correct the English source equation.
