# Chapter 9 — Technical concerns

This file records material technical issues and misleading simplifications in the English source. These are source-content concerns, not ordinary translation edits. Where the Chinese translation clarifies a point, that is noted.

## High

### 1. VPC IPv6 CIDR size is confused with subnet IPv6 CIDR size

The source says the IPv6 CIDR block for a VPC is fixed at `/64`. This conflates VPC-level and subnet-level addressing. AWS commonly assigns a `/56` IPv6 CIDR block to a VPC, while IPv6 subnet CIDR blocks are typically `/64`. The exact allocation options depend on the address source and configuration.

**Suggested correction:** Distinguish the IPv6 CIDR size associated with the VPC from the `/64` prefix commonly used for each subnet.

**Status: corrected in translation.** `ch09.translated.html` now states that AWS commonly assigns a /56 IPv6 CIDR block to the VPC while subnet-level IPv6 CIDR blocks are typically /64, instead of stating the VPC IPv6 CIDR is fixed at /64. Source still needs correction/confirmation with author/editor.

### 2. The definition of a public subnet is incomplete

The source repeatedly implies that resources in a public subnet can access the internet simply because the subnet has a route to an Internet Gateway (IGW), and that an IGW only connects to resources in public subnets. A route to an IGW is necessary for public-subnet internet routing, but an IPv4 resource also needs a public IPv4 address (or Elastic IP) for direct IPv4 internet communication. Subnet classification is fundamentally based on its route table, not on whether the subnet contains a resource that is currently internet-accessible. An IGW is attached to a VPC; it is not attached exclusively to, or limited to, a particular class of subnet.

**Suggested correction:** Define a public subnet as one whose route table has a route to an IGW. Explain separately that a resource generally also needs a public IPv4 address for direct IPv4 internet connectivity. Clarify that the IGW is attached to the VPC and traffic routing is controlled by route tables and resource addressing.

**Status: corrected in translation.** `ch09.translated.html` now explains that a route to the IGW is a necessary condition for a public subnet's internet path, that an IPv4 resource also needs a public IPv4/Elastic IP for direct IPv4 connectivity, that subnet classification depends on the route table rather than on currently-accessible resources, and that the IGW is attached to the VPC rather than being exclusive to public subnets. Source still needs correction/confirmation with author/editor.

## Medium

### 3. Additional VPC CIDR blocks are said to have to be strictly smaller than the primary CIDR block

The source says the address range of every additional CIDR block must be strictly smaller than the primary CIDR block. AWS permits secondary VPC CIDR blocks subject to supported prefix lengths and non-overlap constraints; the rule is not that every secondary block must be strictly smaller than the primary one.

**Suggested correction:** State the supported prefix-length range and non-overlap requirements, and remove the blanket “strictly smaller” requirement unless a specific AWS constraint is being referenced.

### 4. VPC peering is described as having no bandwidth constraints

The source says traffic between peered VPCs flows over the AWS private network “with no bandwidth constraints.” VPC peering does not impose a separate aggregate bandwidth quota in the way some network services do, but traffic is still subject to the bandwidth capabilities and limits of the participating EC2 instances and network interfaces, as well as other applicable service limits.

**Suggested correction:** Say that VPC peering uses the AWS network and does not require customer-managed physical networking, but throughput is still bounded by the participating resources and applicable network limits.

### 5. Internet Gateway is described as being replicated across Availability Zones

The source says IGWs are automatically replicated across multiple AZs within a Region. IGWs are highly available, redundant, and horizontally scaled AWS-managed VPC components, but describing their implementation as automatic replication across AZs is imprecise and may suggest that customers deploy or manage one IGW replica per AZ.

**Suggested correction:** Describe the IGW as a highly available, horizontally scaled component attached to a VPC. Avoid asserting a particular internal replication topology unless supported by AWS documentation.

### 6. VPN traffic is said to be transferred anonymously

The source says a VPN transfers packets over the internet “anonymously.” A VPN provides an encrypted tunnel and can authenticate tunnel endpoints; it does not inherently make traffic anonymous. Source and destination metadata may still be observable, and anonymity requires separate privacy mechanisms and threat-model assumptions.

**Suggested correction:** Replace “anonymously” with a description of encrypted transport and endpoint authentication.

### 7. Direct Connect is presented as a private connection that simply avoids the internet

The source describes Direct Connect as a dedicated connection from a customer data center to an AWS Direct Connect location “without using the internet.” This is broadly useful but incomplete: the connection reaches AWS through a Direct Connect location, and the type of virtual interface determines which AWS resources and address space are reachable. A public VIF can reach public AWS service endpoints; a private or transit VIF is used for private connectivity.

**Suggested correction:** Explain the Direct Connect location and distinguish public, private, and transit VIF use cases. Avoid implying that every Direct Connect path has the same private-routing semantics.

### 8. NLB is said to support long-lived TCP connections while ALB does not

The source says NLB supports long-lived TCP connections “unlike ALB,” using WebSocket as an example. This is misleading: Application Load Balancers support WebSocket connections over HTTP/HTTPS as well. NLB supports TCP/TLS listeners and is suitable for transport-layer workloads, but persistent connections are not exclusive to NLB.

**Suggested correction:** Explain the differences in protocol handling and load-balancing layer. Do not claim that ALB cannot support persistent or WebSocket connections. The Chinese translation has been clarified to avoid repeating this claim.

### 9. ALB and PrivateLink support statements are internally inconsistent

The source says ALB does not support PrivateLink, then later describes using an ALB as a target behind an NLB. AWS supports exposing an Application Load Balancer through AWS PrivateLink by registering the ALB as a target of a Network Load Balancer and associating the NLB with an endpoint service. The source's blanket statement is therefore misleading.

**Suggested correction:** Clarify that an ALB cannot itself be directly associated with an endpoint service, but it can be exposed through PrivateLink using an NLB in front of it.

### 10. ELB is said to serve requests without disruption whenever targets are added or removed

The source presents uninterrupted request serving during target addition or removal as a general ELB capability. Load balancers can help maintain availability during target changes, but uninterrupted service is not guaranteed in every case. Existing connections, connection draining/deregistration delay, target health, capacity, application readiness, and deployment strategy all affect whether users experience disruption.

**Suggested correction:** Qualify this as a capability that supports availability when targets are healthy and draining/readiness are configured appropriately, rather than a guarantee of zero disruption.

### 11. Route 53 Anycast is simplified to routing queries to the nearest data center

The source says Route 53 uses Anycast to route requests through the nearest data center. Anycast generally directs a query to an appropriate network location based on routing topology, not necessarily the geographically nearest data center. Resolver location, network routing, and the specific Route 53 feature in use can affect the result.

**Suggested correction:** Explain that Anycast advertises the same IP address from multiple locations and network routing directs queries to an appropriate reachable location. Avoid equating network proximity with geographic distance.

### 12. The source treats classful IPv4 addressing as a current allocation model

The source explains IP classes A, B, and C as the basis for allocating network and host bits, then discusses CIDR as a later workaround. This is useful historical context, but classful addressing is obsolete for modern IP allocation and routing; CIDR has been the standard for decades.

**Suggested correction:** Explicitly label A/B/C classes as historical background, and make clear that modern networks use CIDR prefix lengths rather than class-based allocation.

### 13. Main route table is described as providing private access among subnets

The source says the main route table is created to provide private access among subnets. A VPC route table's default `local` route enables communication between resources in the VPC's CIDR ranges, subject to security controls. This is not a special private-access feature of the main route table: custom route tables also retain the local route, and security groups/NACLs still govern traffic.

**Suggested correction:** Explain that each VPC route table includes a local route for VPC-internal traffic, and distinguish routing from security filtering.

### 14. NAT gateway's role is described too broadly as connecting a private subnet to the public internet

The source's restaurant analogy and wording can imply that a NAT gateway provides general two-way connectivity between private instances and the internet. A public NAT gateway enables resources in private subnets to initiate outbound connections; unsolicited inbound connections from the internet are not allowed through that NAT mapping. A private NAT gateway has a different use case and does not provide public internet access.

**Suggested correction:** State explicitly that a public NAT gateway supports outbound-initiated internet connectivity for private-subnet resources, and distinguish public from private NAT gateway behavior.
