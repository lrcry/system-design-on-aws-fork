缓存机制与策略

在计算领域，缓存是一种 组件或机制，用于将频繁访问的数据或指令存储在更靠近计算单元的位置，从而降低从较慢的存储设备或外部资源获取信息时的延迟。在传统硬件中，缓存通常以高速、小容量存储器的形式实现，其位置比主存更靠近 CPU。其目标是通过减少访问数据或指令所需的时间来提升系统整体性能。

缓存的核心思想围绕 局部性原理展开。该原理指出，程序往往会反复访问相对较小的一部分数据或指令。通过将这些频繁访问的信息存储在缓存中，后续对相同数据的访问可以得到更快的响应，从而提升性能。

从缓存中访问数据时，存在两种可能的结果：缓存命中和缓存未命中。缓存命中 发生在缓存中找到所请求数据时，此时无需访问较慢的主存或外部资源便可快速获取数据。缓存未命中 则发生在缓存中未找到所请求数据时，系统需要从主存或外部存储中取回数据。缓存命中率衡量缓存在无需访问较慢外部存储的情况下响应请求的有效性，而缓存未命中率则表明缓存未能响应请求数据的频率。

本章将介绍帮助您有效使用数据缓存的重要知识。我们将讨论缓存淘汰策略——即决定何时从缓存中删除数据以加快重要数据检索速度的规则。我们还将介绍缓存失效机制，以确保缓存数据始终正确并与真实的底层数据源保持一致。本章将讨论面向读密集型和写密集型应用的缓存策略，并介绍如何将缓存付诸实践，包括如何部署缓存以获得最佳效果。您将了解缓存的工作原理以及 CDN 的重要性。最后，您将发现两种流行的开源缓存解决方案。让我们从缓存入手。

缓存的优势

缓存 在以下几个方面对提升系统性能和降低延迟起着至关重要的作用：

更快的访问

与主存或外部存储相比，缓存提供了更快的访问速度。将频繁访问的数据保存在更靠近 CPU 的位置，可以显著降低缓存访问时间，从而缩短平均数据获取时间，即降低平均访问时间或延迟。

降低延迟

缓存通过减少对较慢存储资源的访问需求来降低延迟。通过从缓存命中中获取数据，系统避免了从主存或外部数据源取回数据所带来的延迟，从而降低了整体延迟，这一概念在 #ch01_system_design_trade_offs_and_guidelines_1734552285979675 中有详细讨论。

带宽优化

缓存通过减少发送到较慢存储设备的请求数量来优化带宽使用。当数据频繁从缓存中获取时，可以降低对内存总线或外部接口的需求，从而释放资源用于其他操作。

提升吞吐量

缓存使 CPU 能够快速访问频繁所需的数据，无需等待较慢的存储访问，从而提升系统整体吞吐量。这使 CPU 能够在给定时间内完成更多计算操作。

阿姆达尔定律和帕累托分布为缓存的优势提供了进一步的理论支撑。

阿姆达尔定律指出， 优化系统某一特定组件所能实现的整体速度提升，受限于该组件被使用的时间占比。缓存作为关键的优化组件，尤其在缓存命中率较高时，可以对系统整体性能产生显著影响。阿姆达尔定律强调了高效缓存的重要性，以最大化性能优化带来的收益。

帕累托分布，  又称二八定律，指出系统工作负载的很大一部分由少量数据驱动。缓存与这一分布高度契合——将频繁访问的数据存储在快速缓存中，可以高效地服务于最关键的操作。通过将缓存资源集中在访问频率最高的数据上，可以借助帕累托分布来优化最重要工作负载的性能。

总而言之，缓存为频繁访问的数据提供了更快的访问速度，从而降低延迟并提升系统整体性能。缓存还能优化带宽、提高吞吐量，并与阿姆达尔定律和帕累托分布等原则相契合，以最大化性能 收益。

缓存淘汰策略

缓存  通过将频繁访问的数据存储在更靠近消费者的位置，在提升数据检索系统的性能和效率方面发挥着至关重要的作用。缓存策略决定了当缓存容量达到上限时，如何处理数据的淘汰和替换。缓存淘汰策略致力于最大化缓存命中率——即请求的数据项在缓存中被找到并响应的时间占比。较高的缓存命中率减少了从外部存储获取数据的需求，从而提升系统整体性能。本节将探讨多种缓存淘汰策略，包括 Belady 算法、基于队列的策略、基于时效性的策略以及基于频率的策略。

Belady 算法

Belady 算法是一种最优缓存 算法，它淘汰未来最长时间内不会被使用的数据项。该算法需要掌握未来的访问模式，这在实际中通常难以获取。Belady 算法作为理论基准，用于评估其他缓存淘汰策略的性能。

基于队列的策略

基于队列的 缓存淘汰策略将缓存视为队列进行管理。当缓存达到容量上限时，采用以下策略之一删除数据，为新数据腾出空间：

先进先出（FIFO）

先进先出（FIFO）  是一种简单的缓存淘汰策略，它淘汰缓存中最旧的数据项。其原则是：最先插入缓存的数据项在缓存满时最先被淘汰。请注意，在传统 FIFO 中，数据项被访问时不会调整位置；它们仅在插入缓存时被加入队列。因此，数据项一旦插入，其位置便固定不变，直至最终被淘汰。这可能导致仍有需求的数据项被过早淘汰，产生老化问题。

后进先出（LIFO）

后进先出（LIFO）  与 FIFO 相反，最近插入的数据项最先被淘汰。LIFO 不考虑访问模式，可能导致缓存利用率低下和淘汰决策不合理。

FIFO 的一个实际应用场景是打印队列管理——FIFO 通过按提交顺序处理文档来保证公平性，当队列满时淘汰最早的任务。 

基于时效性的策略

基于时效性的 缓存淘汰策略侧重于数据访问的时间维度，优先将最近访问的数据项保留在缓存中：

最近最少使用（LRU）

最近最少使用（LRU）  是一种常用的缓存淘汰策略，它淘汰缓存中最久未被访问的数据项。该策略假设最近访问的数据项在近期更可能再次被访问。LRU 需要跟踪每个数据项的访问时间戳，因此实现起来稍显复杂。

最近最多使用（MRU）

最近最多使用（MRU）  淘汰缓存中最近访问的数据项，其假设是最近访问的数据项不太可能很快再次被访问。MRU 在少量数据项被频繁访问、而较旧的数据项更可能被复用的场景中效果较好。

以实际应用为例，MRU 在 Web 浏览器中淘汰最近访问的页面，假设用户短期内不太可能重新访问这些页面，从而为新内容腾出空间。

基于频率的策略

基于频率的 缓存淘汰策略根据数据项的访问频率来决定其保留优先级，替换访问频率最低的数据项，假设访问较少的数据对性能优化的重要性较低。基于频率的策略包括：

最不经常使用（LFU）

最不经常使用（LFU）  淘汰缓存中访问频率最低的数据项，假设访问频率较低的数据项在未来被访问的可能性也较低。LFU 需要为每个数据项维护访问频率计数，可能占用较多内存。

最不经常最近使用（LFRU）

最不经常最近使用（LFRU）  综合了 LFU 和 LRU 的概念，同时考虑访问频率和访问时效性，淘汰在最近未使用的数据项中频率计数最低的数据项。

在提供频繁访问静态内容的 CDN 中，LFRU 能够通过平衡时效性和频率来优化缓存。例如，一个热门视频可能在短期内被频繁访问，但随着时间推移其相关性逐渐降低。LFRU 可确保在视频持续获得频繁访问的情况下将其保留在缓存中，同时兼顾其他可能频率增加的内容，确保最有价值的内容始终可用。CDN 架构将在  #ch04_content_delivery_networks_1734552287180133 中详细介绍。

允许列表策略

缓存替换的允许列表策略 是一种机制，用于定义一组在空间有限时优先保留在缓存中的数据项。与删除最近最少使用或最不经常访问数据项的传统缓存淘汰策略不同，允许列表策略侧重于明确指定哪些数据项应保留在缓存中。即使在缓存压力较大的时期，该策略也能确保重要或高优先级的数据始终可用。通过允许特定数据项留在缓存中，同时淘汰其他数据项，允许列表策略优化了缓存利用率，并在关键数据访问场景中提升了性能。

在提供动态内容的 Web 应用程序中，可以实施允许列表策略以保留关键的用户特定数据，例如会话信息或频繁访问的配置设置。当缓存达到容量上限时，系统优先处理允许列表中的数据项，确保关键数据始终可用，而非允许列表中的数据项则按 LRU 等标准淘汰策略正常淘汰。这一机制提升了应用程序性能和用户体验，尤其在访问关键数据至关重要的使用高峰期。

缓存淘汰策略的目的各异，并根据系统的访问模式和工作负载展现出不同的性能特征。选择合适的缓存策略取决于应用程序的具体需求和特点。通过有效理解和实施这些缓存策略，系统设计师和开发人员可以优化缓存利用率、提升数据检索性能并改善整体用户体验。接下来，我们将讨论缓存失效策略——这些策略在基于缓存淘汰策略确定要淘汰的数据后  应用。

缓存失效

缓存失效  是缓存管理的关键环节，用于确保缓存数据与底层数据源保持一致。有效的缓存失效策略有助于维护数据完整性，防止陈旧或过期数据被提供给用户。以下是四种常见的缓存失效技术：

主动失效

主动失效 涉及在底层数据源发生变化时，显式删除或使缓存数据失效。该方法要求应用程序或系统通知或触发缓存失效操作。例如，当数据源中的数据被修改或删除时，缓存立即更新或清除，以确保后续请求获取最新数据。主动失效提供了对缓存一致性的精确控制，但需要额外开销来有效管理失效过程。

在社交媒体应用中，当用户发布新内容时，系统主动使所有可能包含过期信息的用户动态缓存失效，确保每个人都能无延迟地看到最新更新，提供新鲜、准确的用户体验。

修改时失效

当底层数据源中的数据被修改时，缓存 随之失效。发生修改操作（如更新或删除）时，缓存被通知或标记以使相应的缓存数据失效。下次访问已失效数据时会触发缓存未命中，数据从数据源重新获取，确保缓存包含最新信息。这种方法最大程度地减少了陈旧数据被响应的可能性，但在失效过程中对缓存未命中引入了轻微的延迟。

在电商平台上，每当商品详情（如价格、描述或库存状态）被修改时，对应的缓存条目随即失效。这可以防止用户看到过期信息，确保他们始终访问到最新的商品数据，这对于做出购买决策至关重要。

读取时失效

当访问缓存数据或发起读取请求时， 缓存失效。收到读取请求时，缓存根据数据版本或实体标签（ETag）检查数据是否仍然有效或已过期。如果数据已过期或被标记为无效，缓存从数据源获取最新数据并在响应请求前更新缓存。这种方法保证了每次都响应最新数据，但由于缓存必须在响应前验证数据的新鲜度，因此为每次读取操作增加了延迟。

在新闻应用中，当用户阅读一篇文章时，系统会检查该文章的缓存版本是否仍然有效。如果文章在缓存后有所更新，缓存失效，最新版本将被获取并响应给用户。这确保了后续读者能够获取到最新内容，尤其是在初次发布后不久进行了更新或更正的情况下。

实体标签（ETag）是 分配给 Web 服务器上资源特定版本的唯一标识符，用于缓存验证。客户端请求资源时，可在 If-None-Match 请求头中附带 ETag，以检查缓存版本是否仍然有效。若 ETag 与当前版本匹配，服务器响应"304 未修改"状态，从而减少带宽占用并提升 性能。

生存时间（TTL）

生存时间（TTL）是  一种将时间段与每个缓存数据项关联的缓存失效技术。数据项存入缓存时，会被标记一个 TTL 值，表示该数据项被视为有效的时长。TTL 到期后，缓存将该数据项视为已过期，后续对该数据项的请求会触发缓存未命中，促使缓存从数据源获取最新数据。基于 TTL 的缓存失效提供了一种简单且自动的缓存新鲜度管理方式，但在 TTL 到期前可能会响应轻微过期的数据。

天气应用可以使用 TTL 将天气数据缓存特定时长，例如 30 分钟。超过这一时限后，缓存数据被视为陈旧并自动失效，系统将获取最新天气信息，确保用户收到及时、准确的天气更新，同时避免大量请求压垮数据源。

选择缓存失效策略取决于数据的性质、更新频率、性能需求以及所需的一致性保证等因素。主动失效提供精确控制但需要主动管理；修改时失效可确保数据的即时新鲜度；读取时失效保证每次读操作都获取最新数据；基于 TTL 的失效则提供基于时间的过期机制。了解数据特性和系统需求，有助于选择合适的缓存失效策略，以维护数据一致性并提升  整体性能。

缓存策略

缓存策略 定义了数据在缓存与底层数据源之间的管理和同步方式。本节将探讨如 #ch04_figure_1_1734552287163557 所示的几种缓存策略：旁路缓存（Cache-Aside）、读穿透（Read-Through）、预刷新（Refresh-Ahead）、写穿透（Write-Through）、绕写（Write-Around）和写回（Write-Back）。

读密集型策略

图示 左侧展示了读密集型缓存策略，侧重于优化频繁读取或访问的数据检索。读密集型缓存策略的目标是通过直接从内存返回缓存数据来降低延迟、提升读操作的整体性能，这比从较慢的远程数据源获取数据快得多。该策略对于大多数操作涉及数据读取而非更新或写入的应用程序尤为有益。下面我们详细了解这些读密集型缓存策略。

旁路缓存（Cache-Aside）

 旁路缓存（Cache-Aside）策略，又称懒加载，将缓存管理的职责委托给应用程序代码。数据被请求时，应用程序首先检查缓存。如果数据已在缓存中，则直接从缓存返回；否则，应用程序从数据源获取数据，将其存入缓存，然后返回给调用方。旁路缓存提供了灵活性，因为应用程序对缓存决策拥有完全控制权，但需要额外的逻辑来管理缓存。

读穿透（Read-Through）

 读穿透（Read-Through）策略在缓存数据可用时直接从缓存获取，否则由缓存自身从底层数据源取回数据。当读操作发生缓存未命中时，缓存从数据源获取数据，将其存储以备后用，并将数据返回给调用方。后续对相同数据的读请求可直接从缓存响应，提升整体读性能。与旁路缓存策略不同，该策略将缓存查找的管理职责从应用程序中剥离，提供了更简化的数据检索流程。读穿透缓存在数据填充后可提升读性能，但在预热期由于缓存未命中可能初期引入较高延迟。这可能导致 P999 延迟不可预测地出现峰值，因为首批请求需要从数据源进行较长时间的获取，而非从缓存快速检索。

预刷新（Refresh-Ahead）

 预刷新（Refresh-Ahead）策略，又称预取，在数据被显式请求之前主动将数据从数据源取入缓存。缓存预判特定数据项的未来需求并提前获取。通过预取数据，缓存降低了后续读请求的延迟，提升了数据检索的整体性能。该策略带来了更优、更可预测的 P999 延迟特性，因为数据已预先加载至缓存中。当用户请求预期的数据时，可以几乎即时从缓存响应，而无需从较慢的数据源获取。这种主动方式最大程度地减少了延迟峰值的出现，即使在负载条件变化的情况下也能实现更稳定、可靠的性能。

缓存预热是指   在数据被需要之前将其预先加载到缓存中，确保频繁访问的数据随时可用。冷启动发生在缓存为空时，系统需要从底层数据源获取数据，随着缓存逐渐填充，会导致较高的延迟和潜在的性能瓶颈。相比之下，热启动则预先在缓存中加载了数据，使后续请求能够从内存中快速响应，从而提升应用程序 整体性能。

写密集型策略

图示 #ch04_figure_1_1734552287163557 右侧展示了写密集型策略，侧重于优化频繁更新或写入数据的存储与管理。与读密集型缓存侧重于优化数据检索不同，写密集型缓存策略旨在提升数据更新和写入的效率，同时保持可接受的性能水平。在写密集型缓存策略中，缓存被设计为能处理频繁的写操作，确保更新后的数据临时存储在缓存中，最终与底层数据源（如数据库或远程服务器）同步，从而实现更好的一致性。这种方式可以减少主数据存储的负载，并通过更快速地确认写操作来提升应用程序的响应能力。下面我们详细了解这些写密集型缓存策略。

写穿透（Write-Through）

 写穿透（Write-Through）策略涉及将数据同时写入缓存和底层数据源。发生写操作时，数据首先写入缓存，然后在写操作被视为完成之前同步传播至持久化存储。该策略确保缓存与数据源之间的数据保持一致，但同步写操作可能引入额外延迟。

绕写（Write-Around）

 绕写（Write-Around）策略在写操作时绕过缓存。当应用程序需要更新数据时，直接写入底层数据源，不经过缓存。因此，写入的数据不会存储在缓存中，从而减少了不常访问数据对缓存的污染。但是，对已更新数据的后续读操作可能会遇到缓存未命中，直到数据再次从数据源获取并被缓存为止。

写回（Write-Back）

 写回（Write-Back）策略允许写操作直接在缓存上执行，将对底层数据源的更新推迟到稍后时间。缓存中的数据被修改后，变更记录在缓存本身，更新最终按计划或在满足特定条件时（如缓存淘汰或时间间隔）异步传播至数据源。写回缓存通过减少立即磁盘写入的次数来提供更快的写操作速度。

除了改善写延迟之外，写回缓存还提供了更好的吞吐量管理，使其能够处理突发数据流量。由于写操作首先在内存中处理，系统可以吸收写请求的峰值，而不会压垮底层数据源。这一能力使得系统能够更有效地处理工作负载的突然增加，确保应用程序即使在高需求时期也能保持响应能力。然而，若在变更被刷入数据源之前发生系统故障，则存在数据丢失的风险。

每种缓存策略都有其各自的优势和注意事项，选择合适的策略取决于系统的具体需求和特点。通过了解这些缓存策略，系统设计师和开发人员可以做出明智决策，优化数据访问并提升应用程序的 整体性能。

缓存部署

部署  缓存时，可根据系统的具体需求和架构选择多种方案。缓存部署有三种常见方式：进程内缓存、进程间缓存和远程缓存。

进程内缓存

 缓存与请求组件驻留在同一进程或应用程序中，通常以内存数据存储的形式实现，可由应用程序或服务直接访问。进程内缓存提供了快速的数据访问和低延迟。这种部署方式适用于数据共享和缓存需求仅限于单个应用程序或进程的场景。

例如，在 Web 应用程序中，用户会话数据可以缓存在内存中，以便在无需对每次请求都查询数据库的情况下快速检索会话信息，从而实现会话粘滞（Sticky Sessions）。这在 #ch05_load_balancing_approaches_and_techniques_1734552287463010 中有详细讨论。

进程间缓存

 缓存作为独立的进程或服务部署，与应用程序或服务并行运行，充当可被多个应用程序或进程访问的专用缓存层。应用程序通过进程间通信（IPC）机制（如共享内存、管道、套接字或远程过程调用（RPC））与缓存通信。进程间缓存改善了不同组件之间的资源利用率和数据一致性，非常适合需要在单台机器上跨多个应用程序或进程共享和缓存数据的场景。

例如，金融服务应用程序可能使用 Apache Ignite 来缓存交易数据，使应用程序的各个组件可以访问这些数据进行实时分析和报告。金融应用的设计与架构将在 #ch21_designing_an_online_stock_trading_platform_1734552295606829 中详细介绍。

远程缓存

 缓存作为独立服务或集群部署，运行于与请求组件不同的机器或位置。缓存服务通过 HTTP、TCP/IP 或自定义通信协议等网络协议进行远程访问。远程缓存可用于在运行于不同机器的应用程序或服务之间共享缓存数据，甚至跨地理分布的位置共享，提供可扩展性和容错性。远程缓存适用于需要在分布式系统中缓存数据，或缓存需要被运行在不同机器上的组件访问的场景。

例如，社交媒体应用程序可能使用 Redis 集群（详见 #ch04_redis_1734552287180570）来缓存用户资料信息和动态数据，确保所有应用程序服务器都能快速访问这些信息，而无需反复查询主数据库。社交媒体应用的设计与架构将在 #ch16_designing_a_social_network_and_newsfeed_system_1734552293547861 中详细介绍。

缓存机制

以下 缓存机制可用于提升应用程序性能：

客户端缓存

缓存数据 存储在客户端设备上，通常位于浏览器的内存或本地存储中。这种机制允许 Web 应用程序直接从客户端设备存储和检索静态资源，如 HTML、CSS、JavaScript 和图片。客户端缓存减少了后续请求从服务器获取资源的需求，从而加快页面加载速度并改善用户体验。

CDN 缓存

静态  内容缓存在分布于不同地理区域的分布式服务器上。CDN 根据用户与 CDN 服务器的地理位置就近为其提供缓存内容，从而降低延迟和源服务器的负载。CDN 缓存常用于缓存静态文件、媒体资源及其他频繁访问的内容，提升 Web 应用程序的整体性能和可扩展性。

Web 服务器缓存

这些 缓存机制在服务器端实现，用于存储频繁访问的内容。向服务器发出请求时，服务器首先检查请求的内容是否已被缓存。若已缓存，服务器直接提供缓存内容，无需重新生成。Web 服务器缓存对于静态网页、具有较长过期时间的动态内容以及生成代价高昂的内容非常有效。

应用程序缓存

数据 缓存在应用程序的内存或内存数据库中。这种机制通常用于存储频繁访问的数据或从其他数据源获取或生成代价高昂的计算结果。应用程序缓存通过减少重复数据检索和计算的需求来提升响应时间，增强应用程序的整体性能。

数据库缓存

数据库 缓存侧重于通过缓存频繁访问的数据或查询结果来提升数据库操作性能。该机制可在两个层面实现：

查询级缓存

查询级缓存  将频繁执行的查询结果存储在内存中。当相同查询再次执行时，直接响应缓存结果而非再次查询数据库，从而降低数据库负载并提升响应时间。

对象级缓存

对象级缓存  缓存从数据库检索的单个数据对象或记录。当频繁访问特定对象或数据库相对静态时，这种机制非常有用。对象级缓存减少了频繁数据库查询的需求，提升了应用程序整体性能。

如 #ch04_figure_2_1734552287163590 所示，通过采用这些缓存机制，组织和开发人员可以优化数据检索，降低延迟，并提升系统的可扩展性和响应能力。然而，必须认真考虑缓存失效、缓存一致性和缓存管理策略，以确保缓存 数据的一致性和完整性。

内容分发网络（CDN）

在  缓存机制中，CDN 通过在边缘站点进行缓存，以降低延迟和增强可扩展性，在提升最终用户的 Web 内容性能和可用性方面发挥着至关重要的作用。CDN 采用多种策略和架构模型，在地理分布的服务器上高效分发和缓存内容。CDN 主要分为两种类型：推送型 CDN 和拉取型 CDN。

推送型 CDN

在 推送型 CDN 中，内容被提前预先缓存并分发至边缘服务器。CDN 服务商根据预测的需求或预定规则主动将内容推送至边缘站点。使用推送型 CDN 时，内容仅在新增或变更时上传，既减少了流量，又最大化了存储效率。这种方式确保了更快的内容分发，因为最终用户请求时内容已在边缘服务器上就绪。

推送型 CDN 适用于流量较低或内容无需频繁更新的网站，例如 Netflix 和 Amazon Prime Video 等视频流媒体平台（这些平台的设计与架构将在 #ch20_designing_a_video_processing_pipeline_for_a_stream_1734552295245731 中的流媒体服务用例中介绍）。内容无需定期从服务器拉取，而是上传至 CDN 一次后保留，直至发生变更。

拉取型 CDN

在 拉取型 CDN 中，内容按需缓存。当第一个用户请求内容时，CDN 服务器从源服务器拉取内容，随后将内容缓存在边缘服务器上供后续请求使用，为未来用户优化分发。内容缓存的时长由 TTL 设置决定。拉取型 CDN 最大程度减少了 CDN 上的存储空间，但如果文件在过期前被拉取，可能产生冗余流量，导致不必要的数据传输。拉取型 CDN 非常适合高流量网站，因为最近请求的内容会保留在 CDN 上，均匀分布负载。

CDN 优化技术

CDN 采用多种优化技术来提升边缘服务器缓存的性能：

动态内容缓存优化

CDN 在缓存根据用户交互或实时数据频繁变化的动态内容时面临挑战。为优化动态内容缓存，CDN 采用多种技术：

内容分片

将 动态内容分解为较小的片段，以实现部分缓存和高效更新

边缘端包含（ESI）

实施  ESI 标签以分离动态和静态内容，允许动态部分即时处理，同时缓存静态片段

内容个性化

利用 用户画像和分群技术在边缘服务器缓存个性化或用户特定内容

多层 CDN 架构

多层 CDN 架构 涉及在多个层级或层次的边缘服务器之间分发内容。这种方式带来了更好的可扩展性与容错性，以及向地理上分散的区域提供更优化的内容分发。它实现了高效的内容复制，并通过将内容移近最终用户来降低延迟。

DNS 重定向

CDN 使用 DNS 重定向，根据地理位置就近性、网络状况和服务器可用性等因素，将用户请求引导至最近或最合适的边缘服务器，优化内容分发并降低延迟。

客户端多路复用

该 技术将客户端与边缘服务器之间的多个 HTTP 请求和响应合并为单个连接。这减少了建立多个连接的开销，提升了效率，尤其对小对象请求效果显著，从而加快内容 分发速度。

CDN 中的内容一致性

确保  CDN 中多个边缘服务器上的内容一致性对于提供最新、最准确的内容至关重要。CDN 采用多种方法来维护内容一致性：

周期性轮询

CDN 定期轮询源服务器以检查内容更新或变化，确保缓存内容刷新以反映最新版本。

生存时间（TTL）

CDN 使用在 HTTP 头或 DNS 记录中指定的 TTL 值，确定缓存内容保持有效的时长。TTL 到期后，CDN 从源服务器获取更新后的内容。

租约

CDN 使用基于租约的机制来控制边缘服务器上内容缓存的时长。租约定义了内容在需要续期或重新验证之前保持有效的特定时间窗口。

AWS 提供了 Amazon CloudFront——一款面向高性能、安全性和开发者便捷性构建的拉取型 CDN，我们将在 #ch09_aws_network_services_1734552289953244 中详细介绍。

使用 CDN 也存在一些局限性。根据流量大小，CDN 的使用成本可能相当可观，但仍需将其与不使用 CDN 时的成本进行比较。如果源服务器上的内容在 TTL 到期前发生更新，那么在 CDN 缓存刷新之前，用户仍可能获取到旧版本的内容。此外，使用 CDN 还需要修改静态资源的 URL，使其指向 CDN，这可能带来额外的管理工作。总体而言，CDN 能够提升性能和可扩展性，但在决定是否使用时，仍需综合考虑这些因素以及网站自身的需求。  

接下来，我们将介绍两种流行的开源缓存解决方案，了解它们的架构以及如何实现本章讨论的缓存概念。

开源缓存解决方案

开源缓存解决方案因其高效性、可扩展性和易用性而广受欢迎。接下来，我们将详细介绍 Memcached 和 Redis 这两种被广泛采用的开源缓存解决方案  。

Memcached

Memcached 是一种开源的高性能缓存解决方案，广泛应用于 Web 应用程序。它是一种分布式内存对象缓存系统，可以将数据存储在多台服务器的内存中。Memcached 具有以下主要特点和优势 ：

简单轻量

Memcached 的设计简洁轻量，易于部署。它专注于缓存功能，并提供简单的键值接口，用于存储和读取数据。

水平可扩展性

Memcached 采用分布式架构，可以通过向缓存集群增加服务器来实现水平扩展。这种架构有助于提高缓存系统的可用性和容错能力，并在工作负载增长时改善性能。

协议兼容性

Memcached 使用一种简单的通信协议，可供多种编程语言使用。因此，无论应用程序采用哪种受支持的语言开发，都可以方便地集成 Memcached。

透明缓存层

Memcached 可以作为应用程序与数据源之间的透明缓存层，通过缓存频繁访问的数据，减少重复查询，从而减轻数据库或 API 的负载。

旁路缓存（Cache-Aside）是 Memcached 最常采用的缓存策略，应用程序可以根据数据的访问模式自行管理缓存。最近最少使用（LRU）淘汰策略则通过淘汰最久未被访问的数据项，尽可能保留仍有访问需求的数据，因此也被广泛采用，有助于让频繁访问的数据继续保留在缓存中。

Memcached 的架构由一台负责协调缓存数据存储和读取的中央服务器组成。当客户端发起数据存储或读取请求时，该服务器会处理请求，并与底层内存分配机制交互。

Memcached 采用多线程架构，能够高效处理并发请求，并充分利用多个 CPU 核心。在这种架构下，Memcached 使用工作线程池并发处理客户端请求，每个工作线程负责处理一部分请求，从而实现并行处理并提高吞吐量。这种方式能够将处理任务分配到可用的 CPU 资源上，使 Memcached 更有效地应对高流量负载。通过利用多个线程，Memcached 可以提升性能和响应速度，因此适用于并发量较高、对缓存性能要求严格的场景。

在内存分配方面，Memcached 采用 slab 分配策略，将已分配的内存划分为固定大小的块，称为 slab。每个 slab 又被划分为更小的单元，称为页（page），这些页随后被分配用于存储各个缓存数据项。通过将大小相近的数据项集中存放，slab 分配策略使 Memcached 能够更高效地管理内存，减少内存碎片并提高内存利用率  。

向缓存添加新数据项时，Memcached 根据数据项的大小确定合适的 slab 尺寸。如果存在具有足够空闲空间的 slab，数据项将存储在该 slab 中；否则，Memcached 从可用内存池中分配新的 slab 并将数据项添加至其中。slab 分配策略使 Memcached 能够在保持最优性能的同时在内存中存储大量数据项。

Memcached 通过架构设计与内存分配策略的配合，提供了一种轻量、高效的缓存解决方案，既能应对高流量负载，又能实现快速的数据访问。Memcached 能够高效利用内存，并通过可扩展的架构，使应用程序可以将频繁访问的数据缓存在内存中，从而显著提升性能 。

Redis

Redis 是 Remote Dictionary Server（远程字典服务器）的缩写，是一种基于服务器的内存数据结构存储系统，可以用作高性能缓存。与依赖对数据行进行遍历、排序和排列的传统数据库不同，Redis 从底层就采用可定制的数据结构来组织数据，支持字符串、位图、位域、列表、集合、哈希、地理空间数据和 HyperLogLog 等多种数据类型。这种灵活性使 Redis 能够适用于多种缓存场景。以下是 Redis 的主要特点和优势  ：

高性能

Redis 以高性能为设计目标，通过内存存储模型实现极快的数据读取和更新。它每秒能够处理大量操作，因此适用于性能要求较高的应用程序。

持久化选项

Redis 提供多种持久化选项，可以将数据保存到磁盘中，使数据在系统重启后仍能保留。这一特性适用于需要在系统重启或缓存失效后继续保留数据的场景。

高级缓存功能

Redis 提供多种高级缓存功能，包括设置过期时间、配置缓存淘汰策略，以及根据 TTL 自动使缓存数据失效。它还支持数据分区和复制，以提高可扩展性和容错能力。旁路缓存（Cache-Aside）是 Redis 最常用的缓存策略。此外，Redis 支持多种淘汰策略，包括 LRU、LFU、随机淘汰和基于 TTL 的淘汰方式。

发布/订阅与消息传递

Redis 支持发布/订阅（Pub/Sub）消息机制，可用于实时消息传递和事件驱动架构，因此适用于需要实时更新数据或发送通知的场景。

Redis 是一种内存数据库，通常作为 MySQL 或 PostgreSQL 等数据库的前置缓存。凭借内存访问速度快的优势，Redis 可以提升应用程序性能，并减轻主数据库的负载。它尤其适合缓存两类数据：一类是变化较少但经常被访问的数据，另一类是重要性相对较低但更新频繁的数据。常见的缓存内容包括会话缓存或数据缓存、排行榜信息，以及用于仪表板的汇总分析结果。

Redis 的架构设计注重高性能、低延迟和简洁性，并提供多种部署方式，以便根据系统需求和成本限制实现高可用性。

Redis 部署中的高可用性

如图 #ch04_figure_3_1734552287163614 所示，Redis 支持多种部署架构，包括单实例部署、Redis 高可用（HA）部署、Redis Sentinel（哨兵）和 Redis Cluster（集群）。不同架构各有需要权衡的因素，适用于不同的使用场景和扩展需求  。

在单实例部署模式下，Redis 以独立服务器的形式运行。这种方式简单，适合规模较小的应用，但缺乏容错能力。一旦该实例发生故障或无法访问，客户端对 Redis 的所有请求都将失败，从而影响整个系统的性能。

Redis 高可用（HA）部署通常包含一个主实例和一个或多个通过复制机制与主实例保持同步的从实例。从实例可以分担读取请求，提升读取能力，也可以在主实例故障时用于故障转移。复制 ID 和复制偏移量在数据同步过程中发挥着重要作用，帮助从实例追赶主实例的数据进度。

Redis Sentinel（哨兵）是一套用于保障 Redis 高可用性的分布式系统。各哨兵进程协同工作，监控主实例和从实例的运行状态与可用性，同时为客户端提供服务发现功能，帮助客户端找到当前的主实例。当主实例不可用时，哨兵进程可以启动故障转移流程。

Redis 集群（Redis Cluster）通过将数据分布到多台机器或多个分片上，实现水平扩展。系统通过分片算法确定某个键应由哪个 Redis 实例（分片）存储。Redis 集群采用哈希槽机制将数据映射到不同分片，并支持在向集群添加新实例时进行平滑的重新分片。集群使用 Gossip 协议维护集群健康状态，各节点持续通信，以判断分片的可用性，并在必要时将从实例提升为主实例  。

Redis 部署中的持久性

为了保障数据的持久性，Redis 提供两种持久化方式：Redis 数据库文件（RDB）和仅追加文件（AOF）。这些持久化机制确保数据在系统重启或崩溃时不会丢失      。

RDB 是 Redis 默认的持久化方式。它会定期为数据集创建快照，并将快照保存为二进制格式的 RDB 文件。这些文件记录了 Redis 数据库在某个特定时间点的状态。RDB 持久化具有以下主要特点：

基于快照的持久化

RDB 持久化通过定期生成整个数据集的快照文件来实现。快照的生成频率可以配置。

高效与快速

RDB 文件在磁盘空间占用和数据加载速度方面表现出色。文件体积紧凑，并且可以快速重新加载到 Redis 中，因此适用于需要快速恢复的场景。

完整数据恢复

RDB 文件包含快照生成时的完整数据集，因此可以用于恢复整个数据集。当系统发生故障时，Redis 可以通过加载最新的可用 RDB 文件来恢复数据。

需要注意的是，RDB 文件也存在一定的局限性。由于 RDB 采用快照方式，因此无法提供实时的数据持久化保障。如果系统在两次快照之间发生崩溃，可能会丢失部分数据。此外，加载大型 RDB 文件进行数据恢复可能需要较长时间，并影响恢复期间的系统性能。

与 RDB 不同，AOF 是另一种持久化方式，它将每次写操作记录在仅追加文件中。AOF 按顺序记录写操作，使 Redis 能够通过重放日志来重建数据集。AOF 持久化具有以下主要特点：

预写日志

AOF 将每次写操作以一系列命令或原始数据的形式记录到仅追加文件中。Redis 可以利用这份日志从头重建数据集。

持久性与灵活性

AOF 比 RDB 文件提供更强的持久性，因为它捕获每次写操作，能够恢复到最后一次执行命令时的数据。此外，AOF 提供不同的持久化选项（如每次写入、每秒同步或两者兼用），以平衡持久性和性能。

仅追加特性

AOF 将新的写操作追加到文件末尾，确保原始数据集永不被修改。这种方式防止了因崩溃或断电造成的数据损坏。

AOF 持久化也有一些需要权衡的因素。随着时间推移，仅追加文件可能不断增大，占用可观的磁盘空间。Redis 支持通过 AOF 重写来压缩日志、减小文件体积。此外，由于需要将每条命令写入磁盘，与 RDB 相比，AOF 持久化通常会带来略高的性能开销。

在实际应用中，Redis 用户通常会根据具体需求，权衡性能、数据持久性和恢复时间目标，选择结合使用 RDB 和 AOF 持久化机制。需要注意的是，如果数据持久性并非首要考虑因素，或者系统重启或崩溃后可以从外部数据源重新生成数据，也可以选择不启用持久化（易失模式）    。

Redis 主要用于易失性缓存，而 AWS 推出了 Amazon MemoryDB，这是一项兼容 Redis、具备数据持久性的内存数据库服务，专为需要微秒级读取性能和个位数毫秒级写入性能的应用程序设计。MemoryDB 注重数据持久性和高可用性，适用于缓存、会话管理和实时分析等场景。关于它的其他功能和应用，读者可以进一步自行探索   。

Redis 的内存管理

Redis 利用进程分叉（fork）和写时复制（Copy-on-Write，CoW）技术，在单线程架构下高效实现数据持久化。当 Redis 执行 RDB 快照或后台保存操作时，会经历以下步骤     ：

  1. Redis 使用 fork() 系统调用创建子进程，该子进程是父进程的完整副本。进程分叉是一种轻量级操作，因为它采用写时复制（CoW）机制创建父进程内存的副本。

  2. 子进程最初与父进程共享相同的内存页。然而，当父进程或子进程修改某个内存页时，写时复制（CoW）机制便会发挥作用。操作系统不会立即复制被修改的内存页，而是仅在必要时创建新的副本。

通过采用写时复制（CoW）机制，Redis 获得了以下优势：

内存效率

子进程刚创建时，会与父进程共享相同的内存页。这种共享内存的方式只需要很少的额外内存。只有在必要时才会复制被修改的内存页，从而节省内存资源。

性能

由于只需复制被修改的内存页，Redis 可以利用写时复制（CoW）机制执行持久化操作，而不会产生显著的性能开销。这对于大型数据集尤其有利，因为如果为了持久化而复制整个数据集，将会非常耗时。

fork 安全性

Redis 采用基于 fork 的持久化方式，避免在创建快照的过程中阻塞主事件循环。通过创建子进程，父进程可以继续处理客户端请求，而子进程则独立执行持久化操作。这确保了系统能够保持较高的响应能力，并持续提供服务。

尽管进程分叉和写时复制（CoW）能够提高内存使用效率并改善性能，但也存在一些需要考虑的局限性。如果在写时复制过程中需要复制大量被修改的内存页，内存使用量就可能增加。此外，在内存占用较大的系统上，fork 操作也可能需要更长的时间。

总体而言，Redis 在单线程架构下有效利用进程分叉和写时复制（CoW）机制，实现高效的数据持久化。借助这些技术，Redis 可以执行快照和后台保存操作，而不会对性能或内存使用量产生显著影响。

总体而言，Redis 为开发人员提供了一种强大而灵活的数据存储解决方案，具有多种部署选项和功能。

Redis 和 Memcached 都是优秀的开源缓存解决方案，各有优势。如何选择取决于具体需求和应用场景。Redis 适用于需要多种数据结构、持久化、发布/订阅消息机制以及高级缓存功能的场景。Memcached 则在注重可扩展性和易于集成的简单、轻量级缓存场景中表现出色   。

AWS 提供 Amazon ElastiCache，这是一项兼容 Redis 和 Memcached 的服务，适用于缓存、会话存储、游戏、地理空间服务、分析和队列处理等实时应用场景。我们将在 #ch10_aws_storage_services_1734552290474903 中进一步介绍这项服务。
