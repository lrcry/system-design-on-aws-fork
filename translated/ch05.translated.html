负载均衡方法与技术

为了实现可扩展性并确保服务持续可用，各组织采用了水平扩展与垂直扩展技术，如#ch01_system_design_trade_offs_and_guidelines_1734552285979675所述。这些方法在一定程度上解决了可扩展性的挑战，但无法保证服务的持续可用性。随着互联网的快速发展，现代高流量网站需要处理数十万个并发请求，这迫切要求采用更为强健的解决方案。

当单台服务器负责处理所有传入请求时，它将面临过载风险，进而导致系统故障。为了克服这一局限，我们对系统进行水平扩展。此时，负载均衡便发挥作用——将传入的网络流量高效地分发到一组后端服务器（通常称为 服务器池）中。这就好比一个人创业，后来雇用了更多员工（并在他们之间分配任务）以实现业务扩展。

在本章中，我们将首先了解用于管理流量和提升性能的各种网络组件，然后重点介绍负载均衡器（LB）的概念——它在实现高效负载分配和确保服务高可用性方面发挥着关键作用。我们将深入探讨负载均衡的机制，以及各种负载均衡算法及其各自的优缺点。理解 LB 及其功能，有助于组织提升应对不断增加的负载、扩展基础设施以及为用户或客户提供无缝体验的能力。最后，您将了解一种流行的开源负载均衡解决方案。现在让我们从各种网络组件开始。

网络组件

在 网络和 Web 服务领域，若干组件在管理和优化流量流转、扩展、增强安全性及提升性能方面发挥着关键作用。其中四个核心组件为：正向代理、反向代理、LB 和 API 网关，如#ch05_figure_1_1734552287453572所示。

尽管这些组件具有一些相似之处，但每个组件都有其独特的用途，并在网络架构中的不同层级运行。让我们来探讨它们之间的区别：

负载均衡器

LB  是网络架构中的关键组件，用于将传入的网络流量分发到多台服务器，以提升应用程序、网站或数据库的性能和可访问性。它承担双重职责：监控资源状态的同时协调请求的流转。当某台服务器无响应、无法处理新请求或错误率升高时，LB 会停止向该服务器发送流量，并将其路由到另一台可用服务器。LB 可以在开放系统互联（OSI）模型的不同层工作，包括 L4（传输层）和 L7（应用层），并使用不同的算法根据服务器负载、响应时间乃至地理位置等因素来分发流量。

OSI 模型描述了计算机系统通过网络进行通信所使用的七个层次  ，我们将在#ch06_communication_networks_and_protocols_1734552288217584中进行更详细的介绍。AWS 提供  弹性负载均衡（ELB），包括应用程序、网络和网关等不同类型的 LB，我们将在#ch09_aws_network_services_1734552289953244中进行更详细的介绍。

反向代理

 反向代理作为互联网与 Web 服务器之间的网关，拦截来自客户端的传入请求并将其路由到合适的后端服务器。反向代理通常通过向客户端隐藏后端服务器详情来提升安全性，同时通过将安全套接字层（SSL）终止、内容缓存、压缩和负载均衡等任务从后端服务器卸载，改善可扩展性和性能。

正向代理

与反向代理相反， 正向代理充当客户端设备与互联网之间的中间人，对两者之间的流量进行中介。当客户端发送请求以访问 Web 资源时，该请求首先被正向代理拦截，然后由代理代表客户端将请求转发到互联网。正向代理通常用于执行企业访问控制策略、过滤 Web 内容、通过屏蔽客户端 IP 地址来提升隐私和安全性，以及缓存频繁访问的内容。因此，它们通常部署在企业网络内，用于管理对外的 Web 流量。

API 网关

 API 网关是一种特殊类型的反向代理，充当外观层，为客户端应用程序访问多个后端服务或 API 提供单一统一的入口点。API 网关通过执行安全策略、速率限制、身份验证、授权、请求和响应转换、协议翻译以及内容协商，简化 API 管理。它们通常用于微服务架构，以屏蔽复杂性并为客户端应用程序提供统一接口，对于管理 API 生命周期（包括版本控制、文档和监控）也非常有用。

AWS 提供  Amazon API Gateway，这是一项完全托管的服务，使开发人员能够轻松地以任意规模创建、发布、维护、监控和保护 API，我们将在#ch09_aws_network_services_1734552289953244中进行更详细的介绍。

了解这些网络组件之间的差异，对于为现代应用程序和服务设计强健、可扩展且安全的架构至关重要。每个组件在网络环境中的流量管理和优化中都发挥着独特的作用。本章将重点介绍负载均衡，因为上述其他组件通常与 LB 集成以获得额外的优势。让我们首先深入探讨 负载均衡的优势。

负载均衡的优势

负载均衡 在网络和应用程序性能方面提供了若干优势：

可扩展性

LB 能够无缝地向网络中添加和移除服务器，随着服务需求的增加或减少实现轻松扩展。这可以基于自动扩缩容策略来实现，我们将在#ch11_aws_compute_services_1734552290903110中进行更详细的讨论。

高可用性

通过负载均衡，应用程序和网站可以将流量从因维护或其他问题而暂时不可用的服务器上重新路由，从而保持高可用性。

性能提升

通过将传入流量分散到多台服务器，负载均衡可以防止单台服务器过载，有助于为访问应用程序或网站的用户保持最优性能（即吞吐量）和响应速度（即延迟）。

改善容错性

在多台服务器之间分配流量，可以最大限度地降低单点故障的风险。如果某台服务器出现问题或发生故障，LB 会将流量重定向到健康的服务器，保持服务的连续性并实现高可用性。

资源利用率优化

负载均衡通过在服务器之间均匀分配工作负载，确保资源得到高效利用，防止任何服务器出现利用率不足或过载的情况。均匀的负载分配取决于所选算法，但 LB 的核心理念是在所有服务器之间平衡负载，确保其最优利用。

高级 LB 甚至能够根据用户的地理位置路由流量，从而优化性能并遵守当地法规。此外，作为反向代理运行的 LB 还可以扩展为防御特定网络威胁的保护屏障，通过审查传入流量来检测并拦截潜在的有害请求。随着时间的推移，LB 与 API 网关等服务之间的功能差距已逐渐缩小，功能集也会因具体的 LB 或 API 网关解决方案而有所不同。我们建议在 LB 后端使用无状态服务器，以确保从池中移除现有服务器时不会造成数据丢失。LB 的部署策略在复杂 网络架构中确保最优性能、高可用性和高效资源利用方面也发挥着举足轻重的作用。

LB 部署与放置策略

负载均衡     不仅在数据中心网络内部需要，还可以在全局和本地两个层面进行部署。全局与本地负载均衡之间的选择，以及 LB 在 Web 服务器、应用服务器和数据库服务器之间的战略性放置，对分布式系统的可靠性和响应能力都有重大影响。

全局服务器负载均衡

全局服务器负载均衡（GSLB）  在更大的范围内运作，通常通过将流量分配到不同的数据中心或地理区域来实现。它通过将请求定向到距离用户最近或可用性最高的数据中心，优化用户体验。这一策略对于向全球用户提供内容、提升性能以及确保遵守区域法规至关重要。

GSLB 有三种实现方式：

基于 ADC 的 GSLB

应用交付控制器（ADC）是数据中心中的计算机网络  设备，通常是应用交付网络（ADN）的一部分，用于管理流向服务器的流量。部分 ADC 能够实时查看服务器状态，并根据数据中心的健康状况和容量转发请求。

基于 DNS 的 GSLB

通过 DNS 实现的 GSLB 会对客户端的 IP 位置进行分析。每当用户请求某个域名的 IP 地址时，基于 DNS 的 GSLB 会将用户定向到地理位置上距离用户最近的数据中心的 IP 地址。

基于 CDN 的 GSLB

GSLB 还可以通过 CDN 来实现：全球 CDN 服务从客户端的源服务器收集数据，并将其存储在地理上分散的服务器网络中，确保向全球用户快速、可靠地分发在线静态内容。

本地负载均衡

与全局负载均衡相比， 本地负载均衡在特定数据中心或本地网络内管理流量，其功能类似于反向代理。它在同一地理区域或网段内的服务器之间平衡负载。这一策略对于优化内部网络流量、确保高效资源利用以及在特定基础设施内保持高可用性至关重要。客户端的请求通过虚拟IP地址（VIP）无缝连接到 LB。

VIP 是 一种不直接绑定到某台物理机器的地址；多台机器共享同一个 VIP。如果某个网络接口发生故障，发往该接口的数据包通常会丢失。但借助 VIP，数据包会自动重定向到故障转移机器。从外部看，VIP 表现为单台机器，而内部则是一组机器共享同一地址。通常，DNS 查询会返回 VIP，从而实现流量的无缝重路由并确保强健的故障转移能力。

通常，LB 位于客户端与服务器之间，接收传入的网络和应用程序流量，然后使用不同的算法将其分发到多台后端服务器。在三层架构中，LB 可以放置在三个层次的服务器实例之间，如#ch05_figure_2_1734552287453606所示。

放置在客户端与 Web 服务器之间的 LB 充当传入用户请求的入口点。它们将 Web 流量分发到多台 Web 服务器，优化响应时间，防止任何单台服务器过载，从而确保用户请求得到高效处理，提升基于 Web 的服务的整体性能和可靠性。

放置在 Web 服务器与应用服务器之间的 LB 管理应用层内的请求流转。它们将请求均匀分发到多台应用服务器，确保没有单台服务器过载。这一部署方式提升了应用程序的可扩展性、容错性和性能，有效处理用户交互和功能请求。

虽然不太常见，但将 LB 放置在应用服务器与数据库服务器之间对于读密集型工作负载是有益的。它们可以将读取查询分发到多台数据库服务器，优化读取性能并扩展数据库操作。在应用层 LB（L7）中，可以通过 URL 路径来区分读操作和写操作，并据此进行路由；也可以根据 HTTP 方法进行路由，例如将 GET /path 路由到服务器 A，将 POST /path 路由到服务 B。我们将在#ch06_communication_networks_and_protocols_1734552288217584中进一步讨论 HTTP 方法。数据库服务器之间的负载均衡需要慎重考量，因为涉及数据一致性和同步方面的问题。

在不同基础设施层之间战略性地放置 LB，对于保持均衡、优化资源利用率和确保高可用性至关重要。在确定 LB 最有效的部署策略和放置位置时，必须仔细考虑流量模式、应用程序需求和系统架构。

负载均衡的概念围绕着在可用工作节点之间分配任务展开，没有唯一规定的分配方法。因此，存在多种负载均衡算法，每种算法都提供不同的      工作负载分配方式。

负载均衡算法

负载均衡算法  是将传入流量高效分发到多台服务器的基础。这些算法可分为静态和动态两大类，各自提供不同的负载均衡方法和资源利用优化手段。让我们探讨各种负载均衡算法、它们的特点，以及它们如何影响流量的分配。

静态负载均衡算法

静态算法根据对服务器配置的既有了解来分配 负载，不考虑运行时服务器状态的变化。它们复杂度较低，通常在所有请求汇聚的单台路由器或通用机器上实现。常见的静态负载均衡算法包括：

轮询

该 算法以顺序方式将传入请求均等地分发给各台服务器。每台服务器依次接收一个请求，确保工作负载均衡分配。但它不考虑服务器负载或响应时间，可能导致资源利用不均匀。

加权轮询

与轮询类似， 该算法根据服务器的能力或容量为其分配不同的权重，流量按权重比例在服务器之间分配，适用于在配置各异的服务器之间均衡工作负载。不过，在大多数情况下，集群中的所有机器配置相同以保持一致性，因此通常使用简单的轮询算法。

基于哈希的算法

这些 算法使用请求中的特定属性（如源 IP 或内容）生成哈希键，然后将其映射到某台服务器。这确保了具有相似属性的请求始终被定向到同一台服务器，有助于实现会话持久性。由于在对池中服务器进行再均衡时存在问题，该算法很少使用：在添加或移除服务器时需要重新整理服务器映射，可能导致某些服务器与 其他服务器相比承受过多流量。

动态负载均衡算法

动态算法根据服务器的当前或近期状态来 分配负载。它们需要与服务器进行通信，因此会带来通信开销。维护状态信息会使算法设计更加复杂，但能做出更优的请求转发决策。常见的动态负载均衡算法包括：

最少连接

活动连接数 最少的服务器接收新请求。该算法旨在将流量分配给负载较轻的服务器，有效管理当前的服务器负载。但它可能不考虑服务器容量，从而导致潜在的负载不均衡。

最短响应时间

该 算法将请求定向到响应时间最短的服务器，监控服务器的成功响应时间并将流量引导至响应最快的服务器，确保资源得到高效利用。

最低负载

该 算法评估每台服务器的当前负载，并将新请求定向到负载最低的服务器。这种动态方式根据服务器的当前性能参数（如 CPU 和内存利用率）确保资源的高效分配。

静态算法采用预定义规则分发流量，简单易用，但可能导致服务器负载不均。动态算法根据实时服务器状况调整流量分配，负载均衡效果更好，但可能产生较高的处理开销。

选择合适的负载均衡算法取决于应用程序或系统的具体需求。某些应用程序因静态算法的简单性而更适合使用，而另一些——尤其是服务器负载变化较大的应用程序——则可能更适合动态算法。

理解这些负载均衡算法，对于优化系统性能和确保在多样化网络环境中高效使用资源至关重要。不同的场景可能需要使用特定算法或多种算法的组合，以实现所需的工作负载   分配目标。

LB 中的会话持久性

静态和     动态算法都必须在监控托管服务器健康状况的同时，维护存储各客户端会话信息的状态。如果会话数据未在分布式缓存或数据库等较低层进行存储，则由 LB 负责管理。本节将根据 LB 处理和管理会话信息的方式，探讨有状态 LB 与无状态 LB，如#ch05_figure_3_1734552287453630所示。

有状态负载均衡器

有状态 LB （如#ch05_figure_3_1734552287453630左侧所示）维护会话信息，追踪每个客户端-服务器交互的状态，存储与进行中的会话相关的数据（如会话 Cookie 或其他会话标识符）。这使 LB 能够将来自同一客户端的后续请求始终定向到最初处理该请求的服务器，从而确保会话持久性。

粘性会话，也  称为会话持久性或会话亲和性，是负载均衡中使用的一种机制，用于确保用户的请求在有状态负载均衡的服务器群组或服务器集中始终被定向到同一台服务器。粘性会话通过在用户会话持续期间将其"绑定"到特定服务器来实现这一目标。初始连接建立后，LB 会将该用户的后续请求路由到同一台服务器。这可以通过多种技术来实现：

基于 Cookie 的会话亲和性

 LB 使用初始连接时生成的会话 Cookie 来识别后续请求，并将其路由到 Cookie 中指定的服务器。

源 IP 亲和性

来自特定 IP 地址的请求 始终被定向到同一台服务器。在用户位于网络地址转换（NAT）后方或使用代理服务器的场景下，这种方法的有效性会降低。

粘性会话对于维护会话状态至关重要，确保与某个会话相关的所有用户交互和数据在由 LB 管理的分布式服务器环境中，始终在特定服务器上保持一致性和可访问性。

有状态负载均衡的优势包括：

会话持久性

确保同一客户端在会话期间的所有请求都被定向到同一台服务器，为跨多个请求的任务或交互保持连续性

高效处理有状态应用程序

适用于需要跨多个请求持续连接或状态信息、且应在同一台服务器上处理的应用程序，例如电子商务平台或银行系统

有状态负载均衡的注意事项包括：

资源开销

维护会话信息需要额外的内存和处理资源，可能影响 LB 的性能。这需要额外的资源，但也节省了外部资源（如数据库），并减少了对数据库的网络调用，从而降低网络延迟。

可扩展性挑战

需要跨多台服务器维护会话状态，可能导致 扩展方面的限制。

无状态负载均衡器

无状态 LB （如#ch05_figure_3_1734552287453630右侧所示）不保留会话信息或状态数据。每个请求都被独立处理，对客户端与服务器之间的历史交互没有任何了解或追踪。请求仅根据负载均衡算法进行分配，不考虑会话连续性。

无状态负载均衡的优势包括：

可扩展性

无状态 LB 具有高度可扩展性，因为无需维护会话信息。请求可以轻松地被定向到任何可用服务器，而无需考虑历史交互。

简单性与高效性

这类 LB 通常复杂度较低，能够在不产生会话管理开销的情况下高效分发流量。

有状态与无状态负载均衡的选择取决于应用程序或系统的需求。需要会话连续性的应用程序更适合有状态 LB，而强调可扩展性和简单性的应用程序则更适合无状态 LB。在复杂的网络架构中，通常会同时采用这两种类型以满足多样化需求。

在确定最终方案之前，请评估您的业务用例，但一个简单且推荐的方案是使用无状态 LB，并借助 Redis 或类似数据存储来进行会话管理。我们将在#ch19_designing_a_chat_application_1734552294951889中讨论为 WhatsApp      规模构建有状态服务器的用例。

负载均衡器的类型

了解   不同类型 LB 的特点，对于有效管理流量和确保应用程序的无缝交付至关重要。本节将探讨基于功能和配置对 LB 进行的分类。

按功能划分的 LB 类型

LB 可以 按功能分为不同类型，每种类型满足特定的需求和要求。让我们深入了解 DNS LB、等价多路径（ECMP）路由器以及网络和应用程序 LB 的详细信息。

DNS 负载均衡器

DNS LB 通过将 域名解析为基于预定义策略的不同 IP 地址，在 DNS 层面分发流量，充当 0 层（tier-0）LB。它们易于配置，能够提供基本的负载均衡功能，但与 L4 和 L7 LB 相比可能缺少某些高级功能。DNS 负载均衡器的典型例子包括 Amazon Route 53 和 Azure Traffic Manager。

ECMP 路由器

ECMP 路由器是一种  负载均衡方法，通常用于网络层，作为 1 层（tier-1）LB。它们将流量分发到具有相同开销的多条路径或链路上，实现网络资源的高效利用并提供容错能力。ECMP 路由器通过对数据包头进行哈希运算来确定每个数据包的合适路径，确保流量在可用链路之间均匀分配。这种方式通过同时利用多条路径来提升网络性能和可靠性。ECMP 路由器的典型例子包括 Cisco Nexus 交换机和 Juniper Networks 路由器。

网络负载均衡器（L4 LB）

网络负载均衡器    工作在 OSI 模型的传输层（L4），根据 IP 地址和目标端口等网络变量处理流量。这类 LB 在传输层分发流量，完全基于网络层信息做出路由决策，主要处理 IP、TCP、FTP 和 UDP 等网络层协议。L4 LB 通常以网络地址转换（NAT）的形式实现，在后端服务器之间分发流量。

L4 LB 的一些特性包括：

基于 IP 地址的会话持久性

L4 LB 可以通过在 IP 地址层面保持一致性来实现会话持久性，确保来自同一客户端的后续请求被定向到同一台后端服务器。

不终止 TCP 连接

与 L7 LB 不同，L4 LB 不终止 TCP 连接，而是在不检查数据包内容的情况下将传入流量转发到后端服务器。网络负载均衡器非常适合高效管理 TCP 流量，常用于基本负载均衡即可满足需求的场景。

L4 LB 有以下两种工作模式：

直接服务器返回（DSR）模式

在此模式下，TCP 连接直接在客户端与后端服务器之间建立。LB 仅更改数据包的目标 MAC 地址，允许后端服务器直接向客户端响应。这种模式确保 LB 不会成为出站流量的瓶颈。DSR 模式适用于 WebSocket 连接以及响应流量远大于请求流量的场景（例如从 Amazon S3 下载对象）。

NAT 模式

客户端连接到服务 VIP，LB 通过更改目标 IP 地址（即 DNAT）将数据包转发到后端服务器。LB 成为后端服务器的默认网关，所有流量都经由它传输。这种模式将出站带宽限制在 LB 的容量范围内，并对客户端隐藏后端服务器信息，从而提升安全性。

网络负载均衡器的典型例子包括 AWS Network Load Balancer（NLB）、Azure Load Balancer、配置为 TCP 的 nginx，以及    UDP 负载均衡器。

应用程序负载均衡器（L7 LB）

应用程序负载均衡器    工作在 OSI 模型的应用层（L7），能够根据应用程序特定参数做出路由决策。这类 LB 综合考虑 HTTP 头、Cookie 和内容等因素来智能分发流量，优化应用程序性能并增强安全性。应用程序负载均衡器非常适合需要高级路由能力的复杂应用程序和环境。

L7 LB 的一些特性包括：

基于应用层协议的分发

L7 LB 根据 HTTP 等应用层协议分发请求，还可以根据应用消息中的特定数据进一步分发请求，并可用于分配读写工作负载。

基于 Cookie 的会话持久性

L7 LB 可以通过使用 Cookie 追踪客户端会话来实现会话持久性，确保来自同一客户端的后续请求被定向到同一台后端服务器。这在电子商务购物车等场景中非常有用，用户会话可以从其上次离开的地方继续。

连接终止

为了提取 HTTP 信息，L7 LB 在 LB 处终止连接，从而形成两条 TCP 连接：一条在客户端与 LB 之间，另一条在 LB 与后端服务器之间。一个典型例子是在负载均衡器处进行 SSL/TLS 卸载，然后通过 HTTP 或其他协议将解密后的流量转发到后端服务器。这有助于简化后端服务器的处理，后端服务器无需维护用于请求验证的 SSL 证书。

应用程序负载均衡器的典型例子包括 AWS Application Load Balancer（ALB）、Azure Application Gateway 以及配置为 HTTP LB 的 nginx。

了解这些不同类型 LB 之间的差异，对于根据应用程序或基础设施的具体需求选择合适的解决方案至关重要。无论您需要基本的网络层负载均衡还是高级的应用感知路由，都有一种 LB 类型 能够满足您的需求。

按配置划分的 LB 类型

LB 可以 配置为硬件、软件或云端形式。正确的配置有助于实现经济高效的扩展、容错，以及与基础设施的无缝集成，从而高效管理流量和资源。因此，LB 可按配置分为两大类：硬件型和软件型。

硬件负载均衡器

硬件负载均衡器 是专用于负载均衡任务的物理设备。这些设备需要专有硬件，通常部署在数据中心或本地环境中，作为独立单元运行，能够处理大量并发用户。虽然硬件负载均衡器具有高性能和高可靠性，但采购和维护成本较高。此外，其可扩展性可能受到硬件基础设施的限制，配置也可能相当耗费资源，这使其即便对于大型企业也不太理想。由于在发生故障时需要额外的硬件来进行故障转移，可用性方面也面临挑战。维护和兼容性问题以及供应商锁定限制了其灵活性。硬件负载均衡器的典型例子包括 F5 BIG-IP Load Balancer、Cisco System Catalyst 和 Citrix NetScaler。

软件负载均衡器

软件负载均衡器 以软件应用程序的形式在标准服务器硬件或虚拟机上运行。它们能够随着需求的增加而有效扩展，并通过以极低的额外成本实现影子 LB 来确保可用性。与硬件 LB 相比，软件 LB 可以部署在通用硬件或云环境中，因而具有更高的灵活性、可扩展性和适应性。软件负载均衡器是硬件方案的经济高效替代品，非常适合动态或基于云的基础设施。此外，这些解决方案还提供预测性分析，以支持对未来流量模式的规划。软件负载均衡器的典型例子包括 HAProxy 和 nginx。

在云计算领域，  负载均衡即服务（LBaaS）应运而生——云服务提供商提供负载均衡服务，用户按使用量或服务级别协议（SLA）付费。LBaaS 的主要优势在于易用性、灵活性、计量计费以及强健的审计和监控服务，有助于提升业务决策能力。

了解不同类型 LB 及其各自的特点，对于设计具有弹性的可扩展应用程序架构至关重要。通过根据功能和配置需求选择合适的负载均衡解决方案，组织可以优化资源利用率、提升应用程序性能，并确保    用户体验的无缝连贯。

在本章的收尾部分，让我们深入了解一种流行的开源负载均衡解决方案，以理解其细节以及它如何实现本章所讨论的概念。

Nginx：开源负载均衡器

Nginx 是     一款以高效性、可扩展性和多功能性著称的高性能开源 Web 服务器和反向代理服务器。除了作为 Web 服务器和反向代理的核心功能之外，nginx 还是一款强大的 LB，为将传入流量分发到多台后端服务器提供了高级能力。Nginx 的负载均衡特性包括：

L4 与 L7 负载均衡

Nginx 同时提供 L4（传输层）和 L7（应用层）负载均衡能力，允许用户根据 IP 地址、TCP/UDP 端口、HTTP 头、Cookie 和内容等多种因素分发流量。

多种负载均衡算法

Nginx 支持多种负载均衡算法以适应不同的用例和需求，包括轮询、最少连接、IP 哈希等。用户可以配置所需算法，根据服务器负载、响应时间和会话持久性等因素优化流量分配。

健康检查与故障检测

Nginx 通过可配置的健康检查持续监控后端服务器的健康状况，自动检测故障或性能下降的服务器并将其从负载均衡池中移除，确保流量只路由到健康的服务器。这种主动方式提升了应用程序的可用性和可靠性。

动态配置更新

Nginx 支持动态配置更新，无需中断服务或人工干预即可无缝扩展和重新配置负载均衡设置。这种灵活性在基础设施频繁变化的动态或云环境中尤为有益。

Nginx 实现了本章详细讨论的以下负载均衡概念：

反向代理负载均衡

Nginx 作为反向代理，拦截传入的客户端请求并将其分发到多台后端服务器。通过卸载 SSL 终止、内容缓存和压缩等任务，nginx 提升了 Web 应用程序的安全性、可扩展性和性能。

HTTP 负载均衡

凭借对基于 HTTP 负载均衡的全面支持，nginx 可以根据 URL 路径、HTTP 头和 Cookie 等多种标准智能分发 HTTP 请求，实现高级路由和流量整形，提升应用程序性能和用户体验。

TCP 与 UDP 负载均衡

Nginx 将其负载均衡能力扩展到 HTTP 以外，支持 TCP 和 UDP 协议，使用户能够在多台后端服务器之间分发数据库查询、DNS 请求和游戏流量等非 HTTP 流量，从而提升各类应用程序的可扩展性和可靠性。

会话持久性

Nginx 提供会话持久性机制，确保来自同一客户端的后续请求被定向到同一台后端服务器。这通过 IP 哈希负载均衡等技术实现——来自特定客户端 IP 地址的请求被持续路由到特定的后端服务器，从而保持会话连续性。

从宏观来看，将 nginx 配置为 Web 服务器，就是定义它处理哪些 URL 以及如何处理对这些 URL 上资源的请求。在微观层面，配置定义了一组虚拟服务器，用于控制对特定域名或 IP 地址的请求处理。

以下是一个简单的 nginx 配置示例：

http {
    upstream backend_servers {
        server 10.0.0.1:8080;
        server 10.0.0.2:8080;
        server 10.0.0.3:8080;
   server 10.0.0.4:8080;
    }

    server {
        listen 80;
        server_name example.com;

        location / {
            proxy_pass http://backend_servers;
            # Additional proxy settings can be configured here
        }
    }
}

在此示例配置中，nginx 被配置为反向代理和 LB。发送到域名 example.com 的 HTTP 请求被代理到 upstream 块中定义的后端服务器池。Nginx 使用默认的轮询负载均衡算法在后端服务器之间分发请求。

Nginx 以其多功能性和强大的开源 Web 服务器特性著称，是一款出色的 LB。无论是管理 Web 应用程序、API 服务还是其他网络系统，nginx 都能确保现代分布式     架构的可扩展性、可靠性和性能优化。
