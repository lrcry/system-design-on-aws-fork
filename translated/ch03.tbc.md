# Chapter 3 — Technical concerns in the English source

This file records material technical inaccuracies or oversimplifications in the English source. These are source-author concerns, not translation errors. The Chinese translation follows the source unless a wording issue can be corrected without changing its technical claim. Please confirm source corrections with the author/editor.

## High

1. **The chapter conflates wide-column stores with columnar databases** (throughout “Columnar (Wide-Column) Store”). A wide-column/column-family database such as Apache Cassandra is not the same storage model as a column-oriented analytical database (for example, a columnar OLAP engine). Cassandra stores partitioned rows with columns and clustering order; it is not generally described as a columnar database in the OLAP sense. The chapter should consistently use “wide-column” or “column-family” terminology and avoid implying columnar storage layout/analytics properties.
2. **The Cassandra ANY consistency level is defined incorrectly** (section “Consistency Levels”). ANY is a write consistency level. A write can be acknowledged after the coordinator stores a hint for an unavailable replica; it does not mean the write has been applied to at least one replica. It is not a read consistency level. The source's description of “at least one replica” is materially misleading.
3. **The source equates ALL with strong consistency and synchronous convergence of every replica** (section “Strong consistency”). Cassandra's ALL consistency level requires all replicas for the relevant partition to respond to the operation. This is not equivalent to linearizability or a general strong-consistency guarantee, and it does not establish that every replica is globally synchronized at every instant. The source should distinguish a product-specific consistency level from a formal consistency model.
4. **The comparison table says SQL transactions always comply with ACID and NoSQL databases generally follow BASE/eventual consistency** (conclusion comparison table). Both statements are overgeneralizations. SQL systems differ in transaction isolation and distributed guarantees; many NoSQL systems support ACID transactions or strong consistency, while some relational systems offer weaker isolation or eventual replication. Database category alone does not determine the consistency model.

## Medium

1. **The majority formula is written as N/2 + 1 without integer rounding** (sections “Leaderless replication” and “Quorum”). A majority is normally floor(N/2) + 1 (or an explicitly defined ceiling convention); the expression N/2 + 1 is not an integer for odd N and is ambiguous as written.
2. **The W + R > N quorum condition is presented without its assumptions** (section “Leaderless replication”). A read/write quorum intersection can help ensure overlap only when read and write quorums are drawn from the same fixed replica set and the protocol's version/conflict-resolution rules preserve the relevant write. The inequality alone does not guarantee that a read returns the latest value, particularly with concurrent writes, sloppy quorums, or different replica placement.
3. **The sloppy quorum description omits its defining behavior** (section “Sloppy quorum and last write wins”). Sloppy quorum does not simply mean that a smaller subset of the normal replicas acknowledges an operation. In Dynamo-style systems, writes may be accepted by the first healthy nodes in a preference list, including nodes outside the key's usual replica set, with hinted handoff used to deliver the write later.
4. **Last-write-wins is described as selecting the latest timestamp without discussing clock skew** (section “Sloppy quorum and last write wins”). Timestamp ordering is not necessarily the same as real-time ordering; clock skew and concurrent writes can cause a write that happened earlier to win. The source should mention the timestamp-generation assumptions and the possibility of lost updates.
5. **The statement that MongoDB replica-set failover continues “without data loss” is too categorical** (sections “Replica sets” and “Primary-secondary node clusters”). Whether acknowledged writes survive a primary failure depends on write concern, replication state, election behavior, and rollback handling. Automatic failover does not guarantee zero data loss under every configuration.
6. **The chapter says clients can read from any secondary node without qualification** (section “Primary-secondary node clusters”). In MongoDB, secondary reads depend on read preference and may return stale data; the default read preference is primary. The statement should describe the required configuration and consistency implications.
7. **The claim that DynamoDB is based on a leader-follower architecture is presented as an established implementation fact** (section “Leaderless replication”). AWS does not expose enough implementation detail to treat this simplified internal topology as a general public architectural guarantee. The chapter should distinguish the original Dynamo paper/system from the managed DynamoDB service and avoid unsupported claims about its internal replication topology.
8. **“Tunable eventual consistency” is used as a general description of Dynamo** (Dynamo feature list). The original Dynamo design exposes tunable read/write quorum parameters and uses versioning/conflict resolution; describing it simply as a tunable eventual-consistency model obscures the distinction between consistency guarantees and operation-level quorum settings.
9. **Size-tiered compaction is described as progressing through levels** (section “Compaction strategies”). Size-tiered compaction groups similarly sized SSTables and compacts a group when thresholds are reached; the level-based description is closer to leveled compaction.
10. **Leveled compaction is described as each level containing SSTables of roughly equal size and merging into larger SSTables** (section “Compaction strategies”). In common leveled-compaction designs, SSTables have a configured size limit, while the total data capacity increases across levels. The source's description can give readers the wrong model of how levels are organized.
11. **The Bloom-filter description incorrectly says it is used for index scans but not range scans** (section “Bloom filters”). In Cassandra-like storage engines, Bloom filters are typically used to test whether a partition key may exist in an SSTable, allowing the engine to skip SSTables that definitely do not contain it. They are not accurately characterized as a general index-scan feature.
12. **The SSTable layout is simplified to a set of key-value pairs with values representing columnar data** (section “SSTables”). In Cassandra, SSTables store partition-oriented data, with rows/columns and clustering order within partitions; the source's generic key-value description hides important storage-engine structure.
13. **Tombstones are said to increase garbage-collection pauses during compaction** (section “Tombstones for soft delete”). This appears to conflate SSTable compaction/tombstone processing with runtime garbage collection (for example, JVM GC). Tombstones can increase read/compaction work and disk usage, but the source should identify which kind of GC or pause it means rather than presenting this as a generic consequence.
14. **Neo4j is described as horizontally scaling by distributing a graph across multiple machines in a cluster** (section “Scalability and performance”). This overstates what clustering provides: replication and cluster-level availability/read scaling are not equivalent to automatic graph partitioning or sharding across machines. The source should specify the Neo4j deployment/product capability and version being discussed.
15. **The chapter describes BASE as a direct alternative to ACID and suggests ACID can hinder performance/scalability in distributed environments** (sections “BASE” and “Advantages”). ACID and BASE are not mutually exclusive database categories, and ACID is not synonymous with relational databases or necessarily incompatible with distribution. The discussion should frame these as different design/consistency properties rather than a binary choice.
16. **“Soft state” is explained mainly as state changing because of failures, delays, or concurrent updates** (section “BASE”). This is an imprecise account of the BASE acronym. Soft state refers to the possibility that system state may change over time even without new input, often as replicas converge or state expires; it is not simply the existence of mutable state or failures.
17. **The document-store discussion implies that all nodes independently handle reads and writes** (section “Availability in Document Stores”). This is not a general property of document databases and conflicts with the later primary/secondary replica-set description. The text should identify the specific distributed architecture rather than generalize across document stores.

## Low

1. **The “columnar” terminology is used inconsistently** (headings and body text). The chapter alternates among columnar, column-family, and wide-column as though they were exact synonyms. Even if the author retains the current framing, the terminology should be standardized and the intended data model explicitly defined.
2. **The phrase “linear scalability” for Cassandra is too absolute** (section “Linear scalability”). Adding nodes can increase throughput under suitable workload and data-distribution conditions, but coordination, replication, hot partitions, and workload shape can prevent linear gains.
