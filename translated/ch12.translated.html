AWS 消息传递、编排、监控与访问管理服务

在大规模系统中，多个组件通过交互与协调来完成任务， 这称为编排。应用程序组件之间的通信与协调可由不同的 AWS 服务管理，我们可以根据具体使用场景选择合适的服务。本章将深入介绍核心编排服务，例如 Amazon Simple Notification Service（SNS），它可向多个订阅者广播消息；以及 AWS Step Functions，它可按特定顺序协调和执行不同的 AWS 服务或自定义服务。

我们将首先讨论有助于在 AWS 云环境中实现发布/订阅设计模式的 AWS 服务，例如 Amazon Managed Streaming for Apache Kafka（MSK）、Amazon Kinesis、Amazon SQS和 Amazon SNS。随后，我们将介绍监控、授权与身份验证服务，如 Amazon CloudWatch、AWS IAM 以及 Amazon Cognito。

Amazon Managed Streaming for Apache Kafka

我们     在#ch08_architectural_designs_and_patterns_1734552289324317中讨论了发布/订阅架构、消息代理和消息队列；本章将介绍 AWS 在这些概念基础上所提供的各类服务。Apache Kafka 是 一种开源消息代理和事件流平台，被广泛用于设计事件驱动架构。AWS 提供了 Apache Kafka 的托管服务——Amazon MSK（Amazon Managed Streaming for Apache Kafka），以降低运维负担。MSK 向客户提供控制平面操作（如创建、更新和删除集群）以及数据平面操作（如生产和消费事件）。

在配置 MSK 集群时，您需要指定代理节点的数量和类型，以及每个可用区的存储容量。为确保集群高可用性，至少需要选择两个可用区。MSK 会自动检测代理节点故障，并用具有相同 IP 地址的健康节点替换故障节点。与 AWS 环境中的许多其他服务一样，MSK 提供两种容量模式：无服务器模式和预置模式。您可以选择无服务器模式，将基础设施配置交由 AWS 负责；预置模式则允许您自行选择节点和存储配置。代理节点之间的协调与同步通过 ZooKeeper 节点管理，MSK 会为我们创建这些节点。MSK 还在较新的 3.7.x 版本中支持 KRaft 模式，KRaft 可承担 ZooKeeper 的功能。

配置 MSK 集群的下一组设置与网络、安全性和监控相关。您应选择启动代理节点所在的可用区和子网，然后定义安全措施。首先，让我们讨论客户端访问 MSK 集群的方式：

未认证访问

顾名思义，您可以允许客户端无需任何身份验证即可直接访问集群，但这不是配置访问控制的推荐方式。

基于 IAM 角色的访问

对 MSK 集群的访问由 IAM 角色及其关联的 IAM 策略进行管理。

SASL/SCRAM 认证

SASL/SCRAM 是简单身份验证与安全层/加盐质询响应身份验证机制（Simple Authentication and Security Layer/Salted Challenge Response Authentication Mechanism）的缩写。  您可以使用客户端登录凭证（用户名和密码）进行身份验证，并将这些凭证存储在 AWS Secrets Manager 中，与相应的密钥资源关联。这提供了一种安全的集群访问方式，而 Secrets Manager 则负责凭证的审计、更新和轮换。您可以根据需要在不同集群之间共享相同的凭证。

TLS 认证

您可以使用 TLS 身份验证来控制客户端访问，并将这些证书存储在AWS Certificate Manager（ACM）中。

为保障数据安全，您可以对静态数据和传输中的数据进行加密。静态数据加密可使用 AWS 托管密钥或客户托管密钥启用。对于传输中的数据，您可以使用 TLS 加密保护集群内部通信，而代理节点与客户端之间的通信则可以使用明文传输、TLS 加密传输，或同时支持这两种方式。

实时流数据可能有多种形式，需要近实时分析。MSK 用于从数据源获取数据，然后将这些数据输送至其他目标，如 Kinesis Data Firehose、AWS Lambda 或 Apache Flink，以进行分析。接下来，让我们    探讨 Amazon Kinesis 的各项服务。

Amazon Kinesis

Amazon Kinesis    可用于流数据处理、数据分析和 ETL 等多种场景。Kinesis 包含四项子服务：Kinesis Data Streams（KDS）、Kinesis Data Firehose（KDF）、Kinesis Data Analytics（KDA）和 Kinesis Video Streams（KVS）。我们先介绍 KDS。

Amazon Kinesis Data Streams

延续实时捕获用户交互的示例，假设   有多台由用户操作的设备，这些设备称为 数据源。KDS 随后采集并存储这些设备产生的交互数据流。数据流进入 Kinesis 后，可以根据需求进行处理，例如使用 EMR 集群上的 Spark。最终，处理结果可以写入 DynamoDB 等目标，也可以使用任意分析工具进行分析，如#ch12_figure_1_1734552291610648所示。简而言之，借助 Kinesis 数据流处理，我们无需承担任何管理开销，就能大规模采集、处理和分析海量数据。

分片（shard）是 KDS 的基本吞吐量单位，也是数据流中具有唯一标识的数据记录序列。一个分片每秒最多可采集 1 MB 数据，支持每秒最多 1,000 条记录，并可每秒向消费者输出最多 2 MB 数据。如果这些限制影响业务需求，可以考虑 Apache Kafka 等替代方案。您可以根据单个分片支持的记录写入速率，以及业务场景中的数据生产和消费速率来配置分片数量。KDS 的预置模式需要进行此项配置。您也可以考虑按需模式，由 AWS 负责容量管理并根据需求自动扩展。

生产者将数据记录发布到数据流，每条数据记录由序列号、分区键和数据块组成：

序列号

序列号由 KDS 自动分配，在所属分片内，对同一分区键的每条记录都是唯一的。

分区键

分区键用于在分片级别对数据进行分组，决定每条数据记录归属哪个分片。选择分区键时，应尽量使数据均匀分布在各个可用分片之间。

数据块（blob）

数据块是承载数据内容的不可变字节序列，大小不得超过 1 MB。

以下是使用 KDS 的主要注意事项：

  • 为解决分片级别 2 MB/s 的共享读取吞吐量限制，KDS 提供了增强型扇出（EFO）功能。该功能为每个消费者提供独立的数据传输通道，使其在每个分片上都能获得最高 2 MB/s 的专用读取吞吐量。

  • KDS 会临时存储数据，保留期限为 24 小时至 7 天。在此期间，可以重放数据以支持不同的重试策略。

  • 可使用 AWS KMS 对进入 KDS 的敏感数据进行加密。

  • KDS 支持多种分片操作，例如更新分片数量、拆分分片或将多个分片合并为一个，从而提高分片容量的利用率。更新分片数量时，系统可以在内部执行分片合并操作，以达到所需的分片数量。当某个分片过“热”或过“冷”，即接收的流量过高或过低时，拆分或合并分片会很有帮助。如果流量过高，可以拆分分片以均衡负载；如果流量过低，则可以合并分片，优化分片 数量。

业务场景

随着时间推移，MSK 与 KDS 的功能差距逐渐缩小，MSK 生态系统也不断发展，能够在无需连接器的情况下直接集成 AWS 服务。例如，可以将 MSK 主题配置为 Lambda 的事件源，通过 KDF 与 S3 集成，并在 Redshift 和 OpenSearch 中消费数据流。

Kinesis 同样提供与多种 AWS 服务的直接集成。选择 MSK 还是 KDS，主要取决于团队此前的技术积累。

运维操作

MSK 的基本逻辑单元是分区，启动集群时需要配置代理节点的数量。采用无服务器计算选项时，客户无需配置代理节点的数量和类型，相关资源由 AWS 全面托管。

KDS 的基本逻辑单元是分片。在预置模式下，需要根据工作负载指定分片数量。此外，KDS 还提供按需容量模式，客户无需自行配置分片，由 AWS 负责容量管理。

延迟

消息写入主题后即可立即获取。与 KDS 相比，延迟可能更低。

KDS 具有低延迟特性：消费者可在 200 毫秒内获取数据。启用增强型扇出（EFO）后，延迟通常低于 200 毫秒。

消息有序性

主题分区内的消息保持有序。

单个分片内的事件保持有序。

消息传递

MSK 支持恰好一次（exactly-once）消息传递语义，这有助于处理金融交易数据流，无需在应用程序代码中显式处理重复数据。

KDS 提供至少一次（at-least-once）消息传递语义。如果系统不允许出现重复记录，应用程序应具备去重处理机制。

定价

费用取决于代理实例的数量和类型、实例运行时长，以及分配给代理节点的存储容量。

对于无服务器选项，费用取决于集群的运行时长、创建的分区数量，以及主题数据读写和存储的使用量。

客户按分片数量和向数据流写入数据的 PUT 操作次数计费。读取 7 天以内的数据不收费。

对于按需模式，费用根据数据流的读写数据量（按 GB 计）及数据流数量计算。数据保留超过 24 小时、使用增强型扇出（EFO）等功能时，还需支付额外费用。

数据保留

可根据代理节点的可用存储容量配置数据保留量，最高不超过其存储容量上限。

如果需要将数据保留超过一年，MSK 可能是更合适的选择，但也应考虑 AWS 提供的归档存储方案。

数据默认可保留 24 小时，可延长至最多一年。

迁移工作量

如果您已在 Amazon EC2 实例或本地数据中心自行管理 Kafka 集群，那么迁移到 MSK 可能是不错的选择，有助于减少切换到其他流处理方案所需的迁移工作量。

对两种服务均不熟悉的团队，应参考其他参数来决定哪种服务更能满足业务需求。

Amazon Kinesis Data Analytics

Amazon KDA    是一项提供 Apache Flink 功能的全托管服务，客户无需承担管理开销，并可根据传入数据所需的吞吐量自动扩展。KDA 能够近实时地处理、查询和分析流数据，并将结果发送到配置好的数据目标，例如 KDS、MSK、S3 和 OpenSearch。

在介绍 KDA 之前，我们先简要了解 Apache Flink。Apache Flink 是一个用于实时数据流处理的开源分布式处理引擎框架，支持  有界和无界流处理。有界（Bounded）指批处理；无界（Unbounded）指实时流数据处理。Flink 在内存中执行有状态计算，以实现低延迟。有状态计算使 Flink 能够保证对流数据事件进行恰好一次处理。通过将状态异步保存为检查点并写入持久存储，Flink 能够在系统发生故障后恢复状态。Flink 支持 SQL 和 Table API、DataStream API 以及有状态函数，便于访问数据。SQL 和 Table API 提供最高程度的抽象，而 DataStream API 和有状态函数则为用户提供更细粒度的控制和更高的可见性。此外，Flink 支持 Java、Scala、Python 和 SQL。

应用部署和基础设施管理可能给客户带来很大负担，而且需要掌握 Flink 的核心概念。KDA 是一项无服务器服务，让客户能够专注于业务逻辑，而端到端的管理工作则由 AWS 负责。以下是 KDA 的一些特有功能：

  • 由于 KDA 在 AWS 环境中运行，它可与其他 AWS 服务轻松集成，例如 Amazon KDS、Amazon MSK、Amazon S3、Amazon OpenSearch、Amazon CloudWatch、Amazon DynamoDB、Amazon KDF 和 AWS Glue 架构注册表。

  • KDA 可通过 Apache Flink 连接器与开源工具轻松集成，并支持为当前尚未支持的使用场景构建自定义连接器。

  • 与 AWS Glue 数据目录的集成有助于跨多个应用程序存储和共享元数据。

  • KDA 提供 KDA Studio，这是对 Apache Flink SQL 和 Table API 的封装，可通过 Apache Zeppelin 无服务器笔记本以交互方式分析流数据。KDA Studio 支持 SQL、Scala 和 Python 语言。

笔记本（Notebook） 是 一种基于 Web、可在浏览器中运行的交互式开发环境。开发人员可以使用受支持的编程语言编写查询或代码，完成数据转换、可视化和分析等任务。

KDA 本质上是 Apache Flink 的全托管版本。作为一项 AWS 云服务，它可以轻松与其他 AWS 服务集成。接下来，我们讨论另一种使用场景：只需将实时流数据加载到目标位置。这一需求    可以通过 Amazon KDF 来满足。

Amazon Kinesis Data Firehose

Amazon KDF   是一项将实时流数据传输到不同目标的服务，支持的目标包括 Amazon S3、Amazon OpenSearch、Amazon Redshift、Splunk，以及用于集成第三方数据存储服务的自定义 HTTP/HTTPS 端点。KDF 是一项全托管服务，因此客户无需负责基础设施和服务维护。KDF 本身不提供独立的数据存储功能，因此无法像 KDS 那样重放消息。您可以配置 KDF，在交付数据前对其进行转换。KDF 提供一些内置转换功能，例如将数据转换为 Apache Parquet 格式。您也可以通过 AWS Lambda 函数添加自定义转换。

以下是使用 KDF 的注意事项：

  • 生产者向 KDF 传输流发送的单条数据记录不应超过 1,000 KB。

  • 为提高安全性并减少目标存储系统中的空间占用，您可以在加载数据前对其进行批量处理、压缩和加密。

  • KDF 会先缓冲传入的流数据，当数据量达到指定大小（缓冲区大小）或经过指定时间（缓冲区间隔）后，再将其传输到目标。对于 S3，缓冲区大小范围为 1 至 128 MB；对于 Amazon OpenSearch，为 1 至 100 MB；对于 AWS Lambda，为 0.2 至 3 MB。这些服务集成的缓冲区间隔范围均为 60 至 900 秒。

  • 当配置的数据目标为 Amazon Redshift 时，KDF 会先将数据传输到 S3 存储桶，然后发出 COPY 命令将数据从 S3 存储桶加载到 Redshift 集群。

  • 选择 S3 作为数据传输目标时，您还可以启用动态分区功能。这样有两个好处：一是便于访问 S3 中的数据并进行查询；二是无需在数据源端或数据存储后另行执行分区操作。您可以指定某个键，或使用在运行时求值的表达式来确定分区键。

  • KDF 在向多个目标传输数据时存在一定限制。单个传输流目前只能将数据传输至以下目标之一：一个 Amazon Redshift 集群或表、一个 S3 存储桶，或一个 Amazon OpenSearch 集群或索引。若需向多个目标传输数据，应分别创建独立的传输流。

  • KDF 支持至少一次（at-least-once）数据交付语义。由于故障处理过程中可能触发重试，目标位置可能收到重复数据。

总而言之，Amazon KDF 是由 AWS 为客户提供的全托管流式 ETL 服务。现在让我们转向另一项 Kinesis 服务   ——Amazon KVS。

Amazon Kinesis Video Streams

Amazon KVS    经过专门优化，可将来自数百万个数据源的实时视频流近实时地传输到 AWS，以供后续处理，例如运行机器学习（ML）算法或执行自定义视频处理。KVS 也可用于离线批处理分析，并支持音频、图像和雷达数据等其他类型的数据流。

KVS 适用于多种场景。下面以家庭安防系统为例，说明它的用途。当住户外出时，可以通过实时、连续的视频画面了解家中情况。为此，安防公司会在住宅内的指定位置安装摄像头。摄像头作为数据源，安装 KVS Producer 库，以便与 AWS 云中的 KVS 建立安全连接。摄像头通过该连接持续向 KVS 传输视频流，数据可以按需存储，也可以转发给消费者。消费者是使用这些数据的应用程序，例如用户通过移动设备查看视频画面，以便及时了解入室盗窃或不速之客到访等情况。整个过程均可实时完成。

以下是使用 KVS 的几个关键注意事项：

  • KVS 提供持久化数据存储，并支持配置数据保留期限。它会自动对静态数据和传输中的数据进行加密，并根据生产者生成的时间戳或服务端时间戳为数据建立索引，便于快速访问。

  • KVS 是一项全托管的无服务器服务，客户无需负责基础设施管理，也不必具备调优相关配置的专业知识。

  • KVS 提供解析器库，使消费端应用程序能够以极低的延迟从视频流中获取数据。该库可在 Java 应用程序中用于解析 Matroska Video（MKV）格式的流数据。

Amazon Simple Queue Service

应用解耦

两个微服务不直接通信，而是通过 SQS 交换消息。这样可以避免服务之间的直接依赖，使一个服务出现故障时不影响另一个服务的运行。

背压控制

客户端可以按照自身的处理速率从 SQS 消费消息。SQS 中消息的保留期限可由客户配置，最长为 14 天。

接下来介绍与 Amazon SQS 相关的重要概念和关键注意事项：

可见性超时

消息 被某个消费者从队列中接收后，并不会立即删除，而是暂时保留在 SQS 中，直到称为可见性超时的时限结束。消费者处理完消息后，应在可见性超时到期前通知 SQS 删除该消息。如果消费者未在期限内删除消息，该消息就会重新对其他消费者可见，以供再次消费。可见性超时的设置范围为 0 秒至 12 小时。

保留期

这是 消息未被任何消费者接收时在队列中保留的时间。取值范围为 1 分钟至 14 天。

死信队列（DLQ）

在某些情况下，  消费者可能无法成功处理消息，但仍需要保留这些消息，以便稍后重试或排查问题。死信队列（DLQ）可用于这种场景：消费者可以将处理失败的消息发送到 DLQ，供后续处理。

最大消息大小

单条消息的 大小上限为 256 KB。对于一般使用场景，这一限制通常已足够；如果需要处理更大的消息，可以考虑使用 S3 或 DynamoDB。消息内容可以存储为 S3 或 DynamoDB 中的对象，再由 SQS 消息引用这些对象。

消息传递

两个消费者无法同时争用同一条消息；同一时刻只能由一个线程处理该消息。这有助于确保系统的可靠性，因为多个生产者可以发送消息，多个消费者也可以接收消息。

SQS 类型

SQS   提供两种队列类型：标准队列和 FIFO 队列。标准队列不保证消息顺序，而 FIFO 队列保证消息顺序。两者的详细对比请参阅#ch12_table_2_1734552291620364。

SQS 常与 SNS 配合使用，无需自行维护基础设施即可满足消息传递需求，例如实现消息扇出。若需将一条消息发送给多个接收方，可以将其发布到一个 SNS 主题，由多个 SQS 队列订阅该主题。每个 SQS 队列都会收到一份消息副本，客户端可以分别从各队列获取并处理消息。接下来，我们将介绍 SNS 的适用场景，以及它与      SQS 的区别。

消息属性

消息属性 是随消息主体一起发送的可选元数据，每个属性由键、值和类型组成。支持的类型包括字符串、字符串数组、二进制和数字。应用程序可以利用这些属性，在不处理消息主体的情况下对消息采取相应操作。消息属性还可以用于在订阅者层面过滤消息。例如，某个 SNS 主题发布亚洲各国的天气状况消息，并在消息属性中包含国家代码。如果应用程序只需处理印度的消息，就可以直接过滤掉其他国家的消息，而无需读取消息内容。

消息持久性

消息传递失败处理

当 订阅者暂时无法接收消息时，SNS 会根据相应的传递协议执行重试策略。如果重试后仍无法成功传递消息，可以配置死信队列（DLQ）来接收这些消息，待系统恢复后再从中获取并处理。

消息安全性

为   保护数据安全或处理敏感数据，您可以指定 AWS KMS 密钥，为 SNS 主题启用服务器端加密。启用后，SNS 会加密收到的消息并以加密形式存储，在向主题订阅者转发消息时再进行解密。由于这种加密仅保护消息主体，因此应避免在主题元数据和消息元数据中存放敏感信息。

消息顺序

为满足 严格的消息顺序需求并防止消息重复，SNS 支持类似 SQS 的 FIFO 主题。若无此类需求，默认使用标准主题即可。

SQS、Lambda 和 SNS 常被组合使用，以支持事件驱动的异步架构（发布/订阅模型）并编排简单的工作流。KDS 也提供类似的模式：生产者将数据发布到数据流，多个消费者可以从中读取数据。主要区别在于，KDS 或 MSK 等流处理方案支持近实时处理。在 SNS 和 SQS 模型中，数据需要先进入特定系统才能进行分析；而使用 KDS，可以在      数据到达时就进行分析。

工作流编排

AWS 提供  两项工作流编排服务：AWS Step Functions 和 Amazon Managed Workflows for Apache Airflow（Amazon MWAA）。Apache Airflow 更为普及，通常更适合批处理工作负载；而 Step Functions 既适用于实时流数据处理，也适用于批处理工作负载（可与AWS Batch集成）。以我们熟悉的 Cafe Delhi Heights 餐厅为例，假设要在线点餐，选好餐品后依次需要：（1）处理付款；（2）向餐厅发送餐品订单；（3）选择配送合作伙伴；（4）跟踪配送进度，如#ch12_figure_2_1734552291610681所示。

这两项服务均由 AWS 全面托管，客户可以专注于应用程序开发，无需承担基础设施维护工作。将应用程序逻辑拆分为多个步骤执行，有助于提高可靠性，因为各步骤可以独立执行（一个组件的问题不会影响其他组件），并能得到妥善的故障处理。Step Functions 是专有服务，而 MWAA 基于开源的 Apache Airflow 构建。接下来，我们将进一步介绍这两项服务。

AWS Step Functions

AWS Step Functions 是一项全托管、无服务器的可视化工作流编排服务，帮助客户轻松创建和运行状态机，以协调分布式应用组件。以下是充分理解 AWS Step Functions 所需掌握的基本术语：

状态机

状态机 使用一系列步骤来表示编排工作流，包括步骤之间的关系，以及各步骤的输入和输出。这些步骤相互协调，并与活动（activity）、Lambda 函数、SQS、DynamoDB 或其他服务等组件交互，以完成特定操作。

任务

任务 是状态机中的单个状态或步骤。任务决定了要执行的操作，例如调用 Lambda 从 S3 存储桶获取对象并对其进行解析。简而言之，单个状态的职责是从上一个状态获取输入，执行指定工作，并将输出传递给下一个状态。

活动

任务 负责执行具体工作，这些工作可以由运行在 EC2 实例、ECS、Lambda 函数中的工作进程，或部署在任何位置且能够建立 HTTP 连接的应用程序来完成。这通过 Step Functions 中称为“活动”（activity）的功能实现。工作流中的相应步骤会等待活动工作进程通过 GetActivityTask API 向 Step Functions 轮询任务。工作进程完成任务后，再通过 SendTaskSuccess 或 SendTaskFailure API 向 Step Functions 回报执行结果。等待回调的超时时间可根据应用程序的特点和使用场景在任务定义中配置。

您可以使用 Amazon States Language（ASL）或   Step Functions 控制台来创建工作流。ASL 是一种基于 JSON 的结构化语言，用于以声明式方式定义工作流状态，如以下代码片段所示：

{
    "Comment": "Amazon States language Example",
    "StartAt": "Hello World",
    "States": {
    "Hello World": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:HelloWorld",
      "End": true
    }
  }
}

AWS Step Functions 始终通过透明的服务器端加密保护静态数据，并使用 TLS 加密 Step Functions 与集成服务之间传输的数据。这样无需额外的运维工作即可保护敏感数据。状态执行的操作取决于其类型。设计状态机时，可以选择以下状态类型：

Pass

Pass 状态不执行任何工作，只是将其输入作为输出传递。该状态主要用于状态机调试，也可用于转换输入，以便将转换后的数据传递给后续状态。

Task

如前所述，Task 状态负责执行状态机中的实际工作。它代表一个工作单元，可以通过 Lambda 函数、活动（activity）或不同 AWS 服务的 API 操作来完成。

Choice

Choice 状态类似于任何编程语言中的 if-else 语句。它是一个条件语句，根据条件是否成立来决定状态机中后续要执行的操作。

Wait

Wait 状态用于在状态机执行过程中暂停工作流。等待时间可以指定为从该状态开始执行时算起的秒数，也可以指定为某个精确时间戳。

Succeed

Succeed 状态是一个终止状态，表示工作流成功结束。

Fail

Fail 状态与 Succeed 状态相反，会以失败结果终止工作流执行。您也可以显式捕获故障并采取相应措施，或者忽略故障，继续执行后续状态。

Parallel

Parallel 状态在状态机中添加多个执行分支，有助于并行执行独立状态以加快工作流处理速度。

Map

Map 状态可以针对数据集中的每个元素并行执行一组工作流步骤，数据集可以是 JSON 数组或 CSV 文件。Map 状态支持内联模式和分布式模式，您可以根据需求选择：

  • 内联模式支持以此前步骤输出的 JSON 数组作为输入，最多可并发处理 40 个元素；执行历史记录不得超过 25,000 条。

  • 分布式模式支持将存储在 Amazon S3 中的 JSON 或 CSV 文件，或上一步骤传入的 JSON 数组作为输入。与内联模式相比，它支持更高的并发度，最多可并行运行 10,000 个子工作流，且执行历史记录不受统一的数量上限约束。

Parallel 状态与 Map 状态的 区别在于对动态并行的支持。Parallel 状态需预先定义多个并行执行的分支，而 Map 状态可根据输入动态创建并行子分支。

您应始终做好应对服务中断及其他故障的准备。在 Step Functions 中，我们建议根据实际需求配置错误处理和重试、重新驱动（redrive）和告警机制，以提高状态机执行的成功率。

Amazon CloudWatch

在 AWS 云基础设施上  部署应用程序只是第一步，还需要确保应用程序持续稳定运行，正常处理客户请求。应用程序指标可帮助我们了解运行状况，例如处理的请求流量、API 延迟和基础设施健康状况。工程师可以根据这些指标设置告警，以检测 API 故障率过高等异常情况，并通过查看日志和指标图表来排查问题。

为监控应用程序的运行状况并排查问题，AWS 提供了 Amazon CloudWatch。CloudWatch 支持存储和搜索应用程序日志、可视化应用程序指标，并提供仪表板和告警功能，帮助发现应用程序的异常行为。

应用程序日志

当   应用程序处理客户请求时会产生日志，包括自定义日志和特定编程语言运行时生成的日志。这些日志有助于排查系统中发生的问题。无论使用哪种计算平台，都可以将日志实时发送到 CloudWatch，并通过其搜索功能或 Logs Insights 查找特定错误日志。以下介绍 CloudWatch Logs 的一些主要功能和术语：

日志存储

CloudWatch 可集中存储应用程序及其他 AWS 服务的日志。日志事件按来源组织成日志流，即来自同一来源的一系列日志事件。具有相似属性（例如来源、保留期限、监控和访问控制设置）的日志流归入同一个日志组。例如，应用程序可以配置为每小时创建一个日志流，其名称可能为 log_stream_2023_05_15_07（日志流名称_年_月_日_小时）。

个人身份信息（PII）数据

我们应  避免在日志中记录个人身份信息（PII），例如社会保障号、病历和信用卡信息。这类敏感数据可能因疏忽而进入生产环境。CloudWatch 可以利用模式匹配和机器学习识别并屏蔽包含此类信息的日志中的敏感内容。

日志搜索

日志搜索能力对于故障排查十分重要。CloudWatch 支持使用模式匹配语法定义多种过滤器。通过这些过滤器，可以识别日志中的特定模式并生成相应指标，例如统计某个 API 的 ERROR 400 日志消息数量。

CloudWatch 还提供 CloudWatch Logs Insights，用于交互式搜索、分析和可视化日志数据。通过其支持的查询语言，单次请求最多可以查询 50 个日志组。例如，可以统计五个微服务日志组中 InternalServerException 的总数。

对于 CPU 利用率或 API 总调用次数等常见的可视化需求，如果不希望通过运行查询来绘制图表，可以使用 CloudWatch 指标直接查看数据，并通过告警功能检测异常行为。

指标与告警

CloudWatch 指标可用于监控应用程序，用户可以搜索指标、绘制指标图表，并根据指标设置告警。例如，可以绘制服务的自定义指标（如 HTTP 500 错误次数），并在连续 15 分钟内每分钟的 HTTP 500 错误次数均超过 10 次时触发告警。接下来，我们将进一步介绍指标和告警。

指标

指标本质上  是按时间顺序排列、发送至 CloudWatch 以供可视化的一组数据点。如前所述，指标可以来自 AWS 资源，也可以是自定义应用程序指标。大多数 AWS 服务会免费发布一些默认指标，您还可以根据需要调整指标的粒度，例如采用分钟级粒度。与 CloudWatch Logs Insights 类似，CloudWatch 的Metrics Insights（指标洞察）功能可以查询已发布的不同指标、发现其中的模式，并据此创建告警。下面介绍与指标相关的一些术语：

命名空间

命名空间 是用于区分不同指标的顶层标识符。例如，EC2 服务的指标记录在 EC2 命名空间中。我们也可以创建自定义命名空间，为同一 AWS 账户中的不同微服务分别组织指标。

维度

维度是 以名称-值对表示的指标标识属性。单个指标最多可关联 30 个维度。例如，要表示某应用程序特定操作的 API 延迟，命名空间为应用程序名称，并带有两个维度：API 名称和指标类型。

指标分辨率

根据使用场景所需的粒度， 您可以在标准分辨率和高分辨率之间选择。标准分辨率下指标的最小粒度为一分钟，高分辨率下为一秒。

统计数据

统计值 可用于汇总一段时间内的数据，例如过去一小时的最大延迟或 API 调用次数总和。您可以根据业务需求从支持的统计值类型中选择，例如最大值、最小值、样本数、总和、平均值和百分位数等。每种统计值还有一个关联的单位，例如次数、百分比或秒。例如，过去一小时的平均 CPU 利用率可能显示为 75%。

为进行进一步分析，可以将 CloudWatch 指标以 JSON 或 OpenTelemetry 0.7.0 格式近实时地传输到指定目标。单个指标流最多可包含 1,000 个过滤器，用于控制需要传输的指标。以下是一些适用场景：

  • 通过 Amazon KDF 传输流将指标发送到 Amazon S3。结合账单数据，可以利用这些指标分析资源性能并寻找成本优化机会。

  • 将第三方服务提供商设为指标传输目标，以便监控应用程序并排查故障。

指标可用于数据可视化和故障排查；如果需要在出现异常行为时触发警报或发送通知，则应配置   CloudWatch 告警。

告警

应用程序监控  对于维持应用程序的正常运行至关重要。告警持续监控应用程序指标，并在指标超过设定阈值时通知用户或其他应用程序采取相应措施。例如，当应用程序的 EC2 CPU 利用率超过 75% 时，可以通过自动扩缩容增加一个实例；当利用率低于 30% 时，则减少一个实例。以下是配置告警时需要考虑的一些重要事项。

指标

可以基于单个指标，或组合多个指标的数学表达式来配置告警。配置告警时，需要指定指标的相关信息，包括命名空间、指标名称和各个维度。

告警条件

当满足特定条件时，告警便会触发。 这些条件由阈值类型、告警条件、触发告警所需的数据点数量以及缺失数据处理方式等参数定义。阈值配置分为两种类型：静态阈值和异常检测。静态阈值可以设置具体数值，支持大于、大于等于、小于和小于等于等比较条件。异常检测则使用一个数值区间作为阈值，支持区间外（高于上限或低于下限）、低于区间下限以及高于区间上限等条件。我们不一定希望仅凭一个指标数据点就触发告警，因此可以根据具体需求配置触发告警所需的数据点数量。

某些情况下，应用程序问题可能导致指标未发送到 CloudWatch，也可能是特定时间段内没有需要发布的指标数据。对于这两种情况，可以配置缺失数据的处理方式。支持四种方式：视为正常（未超过阈值）、视为异常（超过阈值）、忽略（保持当前告警状态），或视为缺失（在无法充分评估告警条件时进入数据不足状态）。

可配置操作

告警 有三种可能的状态：正常（OK）、告警（ALARM）和数据不足（INSUFFICIENT_DATA）。可以配置在告警状态发生变化时执行的操作。支持的操作包括发送通知、自动扩缩容、EC2 实例操作和 Systems Manager 操作。通知操作通过向 SNS 主题发送消息来通知相关人员。自动扩缩容操作可以根据告警阈值，在 Auto Scaling 组（ASG）中增加或减少实例。EC2 实例操作包括重启、停止、终止或恢复实例。您还可以创建 OpsItem 来配置 AWS Systems Manager 操作，供运维团队查看并采取相应措施。

您还可以基于多个告警创建 复合告警。通过仅在复合告警上配置操作、而不为子告警配置相同操作，可以减少运维告警噪音。复合告警根据设定的条件或规则表达式进行评估，例如要求所有子告警都处于告警状态，或其中任意一个子告警处于告警状态时触发。例如，可以将 CPU 利用率、内存使用量和存储空间等指标对应的告警组合起来，监控应用程序的资源使用情况。

#ch12_figure_4_1734552291610724展示了集成 Amazon CloudWatch 以满足监控需求的应用程序架构。应用程序通过 CloudWatch API（PutLogEvents 和 PutMetricData）向 AWS 发送日志和指标，供用户在 AWS 控制台中查看，以便排查问题或监控应用程序。当指标达到设定的告警条件并引起告警状态变化时，便会触发相应告警。AWS 资源的状态变化会由  CloudWatch Events 捕获。

Amazon CloudWatch Events

AWS 服务  或资源会发生状态变化。例如，启动 EC2 实例后，实例在完成初始化和配置后会从待运行（pending）状态转为运行中（running）状态。这些状态变化可以通过 CloudWatch Events 近实时地传递到指定目标，以执行相应操作。CloudWatch Events 还支持使用 cron 表达式或速率表达式来调度自动化操作。例如，在我们的在线餐饮配送场景中，可以每天早上 7 点运行 Lambda 函数，汇总前一天的收入。其他目标包括 Amazon EC2 实例、Amazon KDS、Amazon ECS 任务、AWS Systems Manager Run Command 和Automation、Amazon SQS，以及 Amazon SNS 主题。

AWS 还提供一项与 CloudWatch Events 类似的服务， 名为 Amazon EventBridge。两者采用相同的底层架构，但 EventBridge 提供更多功能。EventBridge 向后兼容 CloudWatch Events API，其工作方式也类似：接收表示状态变化的事件，并根据关联的规则将事件路由到最多五个目标。

在 CloudWatch 控制台中选择规则时，AWS 控制台会自动跳转到 EventBridge 页面。您也可以访问 CloudWatch Events 页面。我们推荐使用 EventBridge，因为它提供了更多功能，例如接收来自软件即服务（SaaS）应用程序的事件。下面进一步介绍这些功能带来的优势：

与 SaaS 提供商集成

例如，PagerDuty 应用程序可以汇集来自多个平台的数据，提供统一视图，以便在发生问题时通知团队成员。假设 PagerDuty 发出告警，提示需要重启某个 EC2 实例，就可以向 EventBridge 发送事件，由 EventBridge 将事件传递给指定目标，从而自动执行重启操作。如果不使用 EventBridge，通常需要通过轮询或自定义 Webhook 从第三方服务提供商获取数据。轮询可能耗费大量计算资源，因为多次请求可能返回空结果；而 Webhook 则需要通过公共互联网进行通信。EventBridge 通过 AWS 私有网络与 SaaS 提供商集成，避免数据暴露在公共互联网上。

自定义事件总线

事件总线为事件发送方和接收方提供通信渠道。CloudWatch Events 中的所有事件都通过 AWS 账户中的默认事件总线进行路由，而 EventBridge 支持创建面向特定客户工作负载的自定义事件总线，并对访问进行控制。

增强规则

EventBridge 允许使用基于内容的过滤来过滤事件中的值。这使您能够在 EventBridge 层面进行过滤，帮助您的应用程序只消费所需的事件流量，同时无需在应用程序中实现过滤逻辑。

架构注册表

EventBridge 存储 AWS 服务、集成的 SaaS 提供商以及自定义事件的架构（Schema），有助于在开发过程中推断事件结构。

CloudWatch 是一项极为重要的 AWS 服务，可用于监控其他 AWS 服务以及部署在 AWS 云环境中的自定义应用程序的运行状况。为防止滥用，保障 AWS 服务和资源的安全也是需要考虑的重要方面。下一节将介绍 AWS IAM 服务，您可以使用它为 AWS     账户实施访问控制。

AWS 身份和访问管理

我们    在本书中已多次提及 IAM 的使用。IAM 通过身份验证和授权，为不同的 AWS 资源乃至整个 AWS 账户实施访问控制和安全措施。首次创建 AWS 账户时，您会使用具有完整管理权限的根用户凭证登录。但在访问不同资源或允许多人登录 AWS 账户时，我们建议仅授予必要的访问权限，以防止滥用。权限的细粒度控制通过 IAM 用户、用户组、角色和策略实现。例如，支持工程师可能只有 CloudWatch 日志的只读权限，而 DevOps 工程师则可能有权创建新日志组或删除现有日志组。

在了解 IAM 的功能和优势之前，让我们先讨论基本术语：

根用户

根用户 是创建 AWS 账户时通过电子邮件地址和密码凭证生成的用户。根用户基本拥有在 AWS 账户中执行任何操作的权限，显式 IAM 策略无法拒绝其访问。服务控制策略（SCP）是一种组织策略，可用于限制成员账户根用户的权限。请创建单独的管理员用户来处理日常任务，仅在执行必须由根用户完成的任务时才使用根用户凭证，例如删除账户、注册 AWS GovCloud（美国）以及注册成为卖家。

IAM 用户

IAM 用户代表具有特定任务执行权限的个人或服务。IAM 用户使用长期凭证，这些凭证不会随时间自动过期。凭证可以是用于登录 AWS 管理控制台的用户名和密码，也可以是用于编程访问的访问密钥 ID（Access Key ID）和秘密访问密钥（Secret Access Key）。应尽可能避免创建 IAM 用户，改用提供临时凭证的 IAM 角色。如果必须创建 IAM 用户，请定期更新密码并轮换 AWS 访问密钥。

IAM 用户组

IAM 用户组将具有相同权限集的用户归为一组。您无法使用用户组名称登录 AWS 账户，但用户组使管理具有相似权限的用户变得更简单。与其重复为每个新用户分配相同权限，只需将新用户添加到用户组即可，从而降低管理负担。

IAM 角色

IAM 角色与 IAM 用户类似，但不与特定个人或服务绑定。个人、服务或另一个 AWS 账户可以临时担任角色来执行任务。例如，在 EC2 实例上运行的应用程序可以通过担任角色，对其他资源发起 API 调用，例如从 S3 下载文件。这样可以确保仅在所需时间内授予临时访问权限，并在期限结束后自动撤销。可以为 IAM 角色设置受限权限，以帮助防止对 AWS 资源环境进行意外更改。对于限定时间内的临时访问，我们建议使用 IAM 角色，而不是 IAM 用户。某些场景可能确实需要使用 IAM 用户，例如无法担任 IAM 角色的第三方工作负载、访问 AWS CodeCommit 或 Amazon Keyspaces，以及为应对紧急情况而创建 IAM 用户；在这些情况下，应确保启用多重身份验证（MFA）。

IAM 策略

IAM 策略是一个 JSON 对象（ACL 策略类型除外，我们曾在#ch10_aws_storage_services_1734552290474903中讨论过这种采用XML 结构的策略），用于定义一组权限，并附加到 IAM 身份（用户、用户组或角色）或 AWS 资源。回顾之前授予 EC2 从 S3 下载对象权限的示例。要让相应角色拥有从 S3 下载对象的权限，需要为该角色附加如下 IAM 策略：

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::samplebucket"]
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": ["arn:aws:s3:::samplebucket/*"]
    }
  ]
}

IAM 策略的 JSON 文档通常包含 Effect（取值为 Allow 或 Deny）、Action（指定资源操作）和 Resource（指定目标资源），以及 Condition、Principal 和 Sid 等其他元素。

在#ch09_aws_network_services_1734552289953244中，我们讨论了如何利用不同的 AWS 存储服务，让 Cafe Delhi Heights 开展线上业务。现在，我们已经创建了一个 AWS 账户，用于托管和运营这家线上餐厅，并聘请了许多人提供协助。所有参与软件应用程序开发和测试的人员都需要访问该 AWS 账户。我们可以通过多种方式提供访问权限：

  • 与团队所有成员共享根凭证。我们不推荐此选项，因为它向所有人提供了完整访问权限。这并非必要，且可能被有意或无意地滥用。

  • 创建 IAM 用户并将其关联到 developer-group、devops-group 和 support-group 等用户组。这可以视为一种较佳选项，但如前所述存在一些缺点。

  • 我们可能已经通过 Google、Facebook 或 Amazon 等身份提供程序（IdP）管理团队成员的身份。我们可以创建 IAM 身份提供程序实体，在 IdP 与 AWS 账户之间建立信任关系。这样，所有用户都可以在有限时间内以受限权限担任 IAM 角色，而无需暴露 AWS 访问密钥。

在不同团队协作时，一个团队可能需要访问另一个团队 AWS 账户中的资源，也可能由多个团队共同拥有同一账户中的资源。对于这些场景，可以通过信任策略和权限策略来管理访问，这种方式称为 权限委派。信任策略指定允许担任角色的受信任账户成员，权限策略则指定受信任用户为执行任务而拥有的权限。

AWS IAM 有助于保护 AWS 资源并管理对这些资源的访问。AWS 还提供 Amazon Cognito 服务，用于管理用户池、充当身份提供程序（IdP），并提供多种    用户身份验证功能。

Amazon Cognito

Amazon Cognito   是一项全托管、高度可扩展的客户身份与访问管理（CIAM）服务，允许客户创建和管理用于身份验证（AuthN）和授权（AuthZ）的身份池。Cognito 全面负责管理支持这些功能所需的计算和存储资源。您可以使用 Cognito 实现新用户注册、现有用户登录、访客用户管理以及访问权限控制。举个简单的例子：我们希望在线餐厅的顾客在提交美食评价时能够上传图片。为了让顾客直接将图片上传到我们 AWS 账户中的 S3 存储桶，可以通过 Cognito 授予临时写入权限。

AuthN 用于确认实体的身份，AuthZ 用于确定该实体可以访问哪些资源。

在 AWS 账户访问方面，AuthN 确认您是否可以登录 AWS 账户，AuthZ 确认您是否可以访问特定的 AWS 资源。

要理解 Cognito 的工作原理，您需要了解以下概念：

身份提供程序

身份提供程序（IdP）  存储和管理用户的数字身份。Cognito 本身可充当身份提供程序（IdP），您也可以将其与第三方 IdP（如 Google、Amazon 和 Facebook）集成（支持的协议包括 OAuth 2.0、SAML 和 OpenID）。例如，您可能会在日常使用的许多应用程序中看到 Google 作为登录选项。IdP 也称为联合身份，因为它可以跨平台用于用户身份验证。在 AWS 与外部 IdP 之间建立信任关系的过程称为联合身份验证。

用户池

用户池 是作为身份提供程序（IdP）的用户目录。无论是通过 Cognito 还是第三方集成 IdP 登录的用户，其用户记录均存储在用户池目录中。它还支持注册、忘记密码、登录、密码长度和策略以及多重身份验证（MFA）等所有功能。

身份池

身份池 通过接受有效令牌（例如 JSON Web 令牌（JWT）或 SAML 令牌）作为输入，为已认证和未认证用户提供应用程序访问的临时凭证。可根据您指定的不同标签为用户分配临时角色。以我们在线点餐的示例为例，用户无需登录即可浏览食物并选择商品，但下单时必须登录。当用户点击"下单"时，可通过重定向到 Amazon Cognito 托管用户界面来实现这一点，然后再重定向到付款页面确认订单。

用户池托管用户界面

我们需要 某种用户界面供用户在我们的应用程序中注册或登录。Cognito 提供一个由 AWS 托管的 URL，用于用户与应用程序之间的交互。该界面可包含电子邮件、密码登录，或任何集成的第三方 IdP，如#ch12_figure_5_1734552291610743所示。用户通过身份验证后，将被引导至指定为重定向 URL 的特定应用程序页面。我们也可以根据需要自定义界面页面，例如添加自定义徽标或 CSS。

触发器

您 可以通过触发器消费 Cognito 事件（例如用户预身份验证或后身份验证），并基于这些事件运行 AWS Lambda 函数。Lambda 触发器为底层应用程序的用户 AuthN 和 AuthZ 运行额外逻辑。例如，您可以运行一组自定义验证规则，例如要求用户访问特定网页的位置必须在印度，用户才能注册该应用程序。

软件应用程序可通过多种方式借助 Cognito 完成身份验证（AuthN）和授权（AuthZ）：

  • 用户通过前端应用程序与 Cognito 交互以获取令牌，并在后续 API 调用中使用相同的令牌。后端应用程序可通过 AWS SDK Amazon Cognito API 与 Cognito 交互，针对用户验证这些令牌。

  • Cognito 提供与 Amazon API Gateway 的原生集成，无需客户进行任何额外工作。当应用程序 API 通过 Amazon API Gateway 提供时，无需手动验证令牌，验证可根据配置自动完成。

  • 为减少您的手动配置工作，可以使用 AWS Amplify 自动创建所需基础设施，然后使用 AWS SDK 与 Cognito 交互。

您始终可以自行构建自定义的 AuthN 和 AuthZ 解决方案，而无需使用 Cognito。我们将在#ch16_designing_a_social_network_and_newsfeed_system_1734552293547861中对这些选项进行更详细的比较。

让我们回到使用 Cognito 为上传对象到 Amazon S3 分配临时凭证的示例。本质上有两种实现方式：

S3 预签名 URL

预签名 URL 可针对 S3 存储桶或特定对象创建特定权限——请注意，创建预签名 URL 的用户必须拥有相应权限。这种方式的一个缺点是需要预先定义对象键名，因此要在运行时创建预签名 URL，需要在中间添加一个计算层。例如，AWS Lambda 从客户端捕获文件名，创建 S3 预签名 URL，并响应客户端以供进一步上传对象。

Amazon Cognito

您可以使用 Cognito 的身份池为用户分配临时凭证，允许他们直接将文件上传到 S3。使用此方式取决于您正在处理的使用场景类型，因为此选项需要完成 Cognito 的配置。如果已经为用户 AuthN 和 AuthZ 设置好相关配置，这可能会简化我们的工作。

这两种方式也可以结合使用：Cognito 负责用户身份验证，AWS Lambda 负责生成预签名 URL。

我们讨论了身份池中基于不同标签的临时角色分配——角色也可以基于令牌和 IAM 策略来分配，即将角色相关信息作为令牌的一部分获取，并用其来分配角色。对于需要动态角色创建的需求，IAM 策略中的访问控制属性可能会有所帮助。

AWS 提供 IAM、Cognito 等 AuthN 和 AuthZ 服务，使开发团队无需从头构建相关解决方案，大幅加快了开发节奏。AWS AppSync 是另一项服务，有助于前后端团队在大规模 API 开发中独立扩展。让我们来看看 AWS AppSync   的功能。

AWS AppSync

要充分  理解 AWS AppSync 的工作原理，我们首先来思考如何在在线点餐平台上向顾客展示食品信息。前端应用程序展示食品信息、价格、餐厅优惠券、评价等内容。这些数据由后端微服务架构中的不同应用程序维护。前端应用程序有两种选择：分别调用每项服务的 API 并收集数据，或使用单个 API 从所有这些不同的后端服务收集数据并返回给前端。

回想 一下，我们在#ch06_communication_networks_and_protocols_1734552288217584中讨论了 GraphQL。AppSync 本质上是一个单一的 GraphQL 端点，可在单次网络调用中查询多个数据库、微服务和 API。在我们的示例中，可以使用 AppSync 向前端暴露单个端点，从不同微服务收集数据。AppSync 也可用于创建发布/订阅 API，通过全托管无服务器 WebSocket 连接向订阅客户端发布通知，例如实时体育赛事更新。

以下是开始使用 AppSync 需要了解的基础组件：

GraphQL 架构

一种数据模型，指定用于数据检索的查询模式。

解析器

在架构与不同数据源之间提供链接的组件。它们将 GraphQL 载荷转换为底层系统协议，并在具备相应 IAM 权限的前提下执行操作。

数据源

解析器可使用访问凭证从中获取数据的数据目标，例如 Amazon DynamoDB、Amazon RDS、AWS Lambda 和 HTTP 端点。#ch12_figure_6_1734552291610763中显示的数据源可位于同一 AWS 账户或不同 AWS 账户中。

合并 API

由多个源 API、GraphQL 架构、解析器和数据源合并操作构建而成的单个 AppSync API。源 API 可由独立团队管理，并通过合并 API 进行协作。

您可能会问：为什么要使用 AppSync，而不是自行部署 GraphQL 基础设施？主要原因是将 AuthN 和 AuthZ、缓存和加密等功能的运维开销从客户身上卸下。AppSync 还简化了聊天应用程序、基于位置的通知、实时游戏计分板以及结合 AWS Amplify 的离线支持等高级使用场景的构建。为提供这些优势，AppSync 是一项全托管无服务器服务，提供构建时合并 API 的组合，以及与 AWS WAF（网站防火墙）、Amazon CloudWatch、Amazon Cognito 和 TLS 加密   等 AWS 服务的便捷集成。

总结

到目前为止，您已了解 AWS 提供了种类繁多的服务，充分理解业务需求以利用最适合的服务实现目标至关重要。您会注意到，某些服务具有类似的功能，例如将 MSK 与 SQS-SNS 或 KDS 进行比较时。

或者考虑这样一点：像 AWS Step Functions 这样的全托管无服务器应用程序不会让我们完全了解工作流在幕后如何编排，但重要的问题是：我们真的需要了解吗？因为 Step Functions 为我们节省了大量的管理和运维成本，同时还提供了通过可视化工作流进行调试的额外能力。

我们还强调了应用程序监控作为确保高可用性的重要方面，以及如何通过在 Amazon CloudWatch 中设置指标、日志和告警来实现这一点。随后，我们深入探讨了 AuthN 和 AuthZ 服务如何帮助保护我们的应用程序，以及 AWS 基础设施环境中的不同组件如何以安全受控的方式相互通信。我们建议遵循最小权限原则：仅为应用程序、用户或另一个 AWS 账户提供执行操作所需的最小权限集。
