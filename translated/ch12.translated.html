在大规模运行的系统中，多个组件相互交互并协调以完成任务， 这称为编排。应用组件之间的通信与协调可由多种 AWS 服务来管理，我们可以根据具体使用场景选择所需服务。本章将深入探讨核心编排服务，如 Amazon Simple Notification Service（SNS），可用于向多个订阅者广播消息；以及 AWS Step Functions，可用于按特定顺序协调和执行不同的 AWS 服务或自定义服务。

Amazon Managed Streaming for Apache Kafka

我们     在#ch08_architectural_designs_and_patterns_1734552289324317中讨论了发布/订阅架构、消息代理和消息队列；本章将介绍 AWS 在这些概念基础上所提供的各类服务。Apache Kafka 是 一种开源消息代理和事件流平台，被广泛用于设计事件驱动架构。AWS 提供了 Apache Kafka 的托管服务——亚马逊 MSK（Amazon Managed Streaming for Apache Kafka），以降低运维负担。MSK 向客户提供控制平面操作（如创建、更新和删除集群）以及数据平面操作（如生产和消费事件）。

在配置 MSK 集群时，您需要指定代理节点的数量和类型，以及每个可用区的存储容量。为确保集群高可用性，至少需要选择两个可用区。MSK 会自动检测代理节点故障，并用具有相同 IP 地址的健康节点替换故障节点。与 AWS 环境中的许多其他服务一样，MSK 提供两种容量模式：无服务器模式和预置模式。您可以选择无服务器模式，将基础设施配置交由 AWS 负责；预置模式则允许您自行选择节点和存储配置。代理节点之间的协调与同步通过 ZooKeeper 节点管理，MSK 会为我们创建这些节点。MSK 还在最新的 3.7.x 版本中支持 KRaft 模式，KRaft 可承担 ZooKeeper 的功能。

配置 MSK 集群的下一组设置与网络、安全性和监控相关。您应选择启动代理节点所在的可用区和子网，然后定义安全措施。首先，让我们讨论客户端访问 MSK 集群的方式：

未认证访问

顾名思义，您可以允许客户端无需任何身份验证即可直接访问集群，但这不是配置访问控制的推荐方式。

基于 IAM 角色的访问

对 MSK 集群的访问由 IAM 角色及其关联的 IAM 策略进行管理。

SASL/SCRAM 认证

SASL/SCRAM 代表简单认证安全层/加盐挑战响应认证机制（Simple Authentication and Security Layer/Salted Challenge Response Authentication Mechanism）。  您实际上是使用登录凭证（用户名和密码）对客户端进行身份验证，并将其存储到与密钥资源关联的 AWS Secrets Manager（云密钥管理） 中。这提供了一种安全的集群访问方式，同时由 Secrets Manager 全权负责凭证的审计、更新和轮换。您可以根据需要在集群之间共享相同的凭证。

TLS 认证

您可以使用 TLS 认证进行客户端访问，并将证书存储在亚马逊证书管理器（Amazon Certificate Manager，ACM）中。

对于数据安全，您可以对静态和传输中的数据进行加密。静态加密可通过 AWS 托管密钥或客户托管密钥启用。对于传输加密，您可以使用 TLS 加密保护集群内部通信，并对代理节点与客户端之间的通信使用纯文本加密、TLS 加密或两者兼用。

实时流数据可能有多种形式，需要近实时分析。MSK 用于从数据源获取数据，然后将这些数据输送至其他目标，如 Kinesis Data Firehose、AWS Lambda 或 Apache Flink，以进行分析。接下来，让我们    探讨 Amazon Kinesis 的各项服务。

Amazon Kinesis

Amazon Kinesis    可支持多种围绕流处理、分析和 ETL 的使用场景。Kinesis 旗下提供四项子服务：Kinesis Data Streams（KDS）、Kinesis Data Firehose（KDF）、Kinesis Data Analytics（KDA）和 Kinesis Video Streams（KVS）。我们先从 KDS 开始介绍。

Amazon Kinesis Data Streams

延续实时捕获用户交互的示例，   您有多台由用户操作的设备，这些设备被称为 数据源。该交互流随后被 KDS 采集并存储。由于数据流现已在 Kinesis 中可用，可根据需求进行处理，例如在 EMR 集群上运行 Spark。最终，处理结果可以写入 DynamoDB 等目标存储，或使用任意分析工具进行分析，如#ch12_figure_1_1734552291610648所示。简而言之，基于 Kinesis 的数据流处理使我们能够在不承担任何管理开销的情况下，大规模采集、处理和分析海量数据。

分片（shard）是 KDS 的基本吞吐量单位，是数据流中具有唯一标识的数据记录序列。一个分片每秒最多可采集 1 MB 数据，支持每秒最多 1,000 次事务（TPS），并可每秒向消费者输出最多 2 MB 数据。如果这些限制影响到您的业务场景解决方案，请考虑替代方案（例如 Apache Kafka）。您可以参考分片所支持的 TPS 以及业务场景的生产和消费速率来配置分片数量。此配置适用于 KDS 的预置模式。您也可以选择按需模式，AWS 将自动进行容量管理并按需扩展。

生产者将数据记录发布到数据流，每条数据记录由序列号、分区键和数据块组成：

序列号

由 KDS 自动分配，在其所属分片内对每个分区键具有唯一性。

分区键

在分片级别对数据进行分组，即决定一条数据记录属于哪个分片。应选择能在可用分片之间实现均匀数据分布的键。

数据块（blob）

由内容或信息构成的不可变字节序列，允许的最大大小为 1 MB。

以下是使用 KDS 的主要注意事项：

  • 为突破分片级别 2 MB/s 的扇出限制，KDS 提供了一项附加功能：增强型扇出（EFO）。该功能可为每个消费者提供专用管道，从而实现 2 MB/s 的读取吞吐量。

  • KDS 会临时存储数据，保留时间为 24 小时至 7 天；在此期间，数据可被重放以支持任意重试策略。

  • 可使用 AWS KMS 对进入 KDS 的敏感数据进行加密。

  • KDS 提供多种分片操作，如更新分片数量、分裂分片或合并分片，有助于确保分片容量的充分利用。更新分片操作可在内部合并已分裂的分片，以配置更新后的分片数量。当分片过"热"或过"冷"（即接收流量过多或过少）时，分裂或合并分片非常有用。若流量过高，拆分分片有助于均衡流量；若流量过低，合并分片有助于优化分片 数量。

Amazon Kinesis Data Analytics

Amazon KDA    是一项基于 Apache Flink 功能的全托管服务，客户无需承担任何管理开销，服务可根据所需吞吐量自动扩展。KDA 可近实时地处理、查询和分析流数据，并将结果发送至配置好的数据目标，如 KDS、MSK、S3 和 OpenSearch。

在介绍 KDA 之前，让我们先大致了解 Apache Flink。Apache Flink 是一个用于实时数据流处理的开源分布式处理引擎框架，支持  有界和无界流处理。有界（Bounded）指批量处理；无界（Unbounded）指实时处理流数据。Flink 在内存中执行有状态计算以实现低延迟。其有状态特性确保了对流数据事件的恰好一次处理。Flink 通过将状态异步检查点写入持久存储来确保系统崩溃后状态得以恢复。它支持 SQL 和 Table API、DataStream API 以及有状态函数，便于数据访问。SQL 和 Table API 抽象程度最高，而 DataStream API 和有状态函数则为客户提供更细粒度的控制和可见性。此外，Flink 支持 Java、Scala、Python 和 SQL 语言。

对于客户而言，部署和基础设施管理可能是巨大的痛点，而深入掌握 Flink 核心概念也需要较高门槛。KDA 是一项无服务器产品，使客户能够专注于业务逻辑，AWS 负责端到端的全部管理。以下是 KDA 的一些特有功能：

  • 由于 KDA 在 AWS 环境中运行，它可与其他 AWS 服务轻松集成，例如 Amazon KDS、Amazon MSK、Amazon S3、Amazon OpenSearch、Amazon CloudWatch、Amazon DynamoDB、Amazon KDF 和 AWS Glue Schema Registry。

  • KDA 可通过 Apache Flink 连接器与开源工具轻松集成，并支持为当前尚未支持的使用场景构建自定义连接器。

  • 与 AWS Glue 数据目录的集成有助于跨多个应用程序存储和共享元数据。

  • KDA 提供 KDA Studio，这是对 Apache Flink SQL 和 Table API 的封装，可通过 Apache Zeppelin 无服务器笔记本以交互方式分析流数据。KDA Studio 支持 SQL、Scala 和 Python 语言。

Notebook 是 一种在浏览器中运行的基于 Web 的交互式开发环境。开发人员可以用支持的语言编写查询或代码，用于数据转换、可视化和分析等各种场景。

KDA 本质上是 Apache Flink 的全托管版本，由于它是 AWS 云服务的一部分，您可以轻松将其与其他 AWS 服务集成。现在，让我们讨论另一个仅需将实时流数据加载到目标位置的使用场景。该需求    可通过 Amazon KDF 来满足。

Amazon Kinesis Data Firehose

Amazon KDF   是一项将实时流数据传输到不同目标的服务，支持的目标包括 Amazon S3、Amazon OpenSearch、Amazon Redshift、Splunk 或任意自定义 HTTP/HTTPS 端点，以便轻松集成第三方数据存储提供商。KDF 是全托管服务，客户无需担心基础设施和服务维护问题。KDF 本身不提供存储能力，因此不具备像 KDS 那样重放消息的功能。您可以配置 KDF 在交付数据前对其进行转换。KDF 提供了一些内置转换功能，例如转换为 Apache Parquet 格式。您也可以使用 AWS Lambda 函数添加自定义转换。

以下是使用 KDF 的注意事项：

  • 生产者发送到 KDF 传输流的数据记录不应超过 1,000 KB。

  • 为提高安全性并减少目标数据存储的占用空间，您可以在加载前对数据进行批量处理、压缩和加密。

  • KDF 会在将传入的流数据传输到数据目标之前，先将其缓冲至一定大小（缓冲区大小）或一定时间（缓冲区间隔）。S3 的缓冲区大小范围为 1 至 128 MB，Amazon OpenSearch 为 1 至 100 MB，AWS Lambda 为 0.2 至 3 MB。所有这些服务集成的缓冲区间隔范围均为 60 至 900 秒。

  • 当 Amazon Redshift 配置为数据目标时，KDF 会先将数据传输到 S3 存储桶，然后发出 COPY 命令将数据从 S3 存储桶加载到 Redshift 集群。

  • 当选择 S3 作为传输目标时，您还可以启用数据动态分区。这在两个方面有所帮助：一是便于在 S3 中访问数据以进行查询，二是无需在数据源端或数据存储后进行分区处理。您可以指定特定键或运行时计算的表达式来标识用于分区的键。

  • 在将数据传输到多个目标时，KDF 存在一定限制。单个传输流目前只能将数据传输到单个 Amazon Redshift 集群或表、单个 S3 存储桶以及单个 Amazon OpenSearch 集群或索引。若需传输到多个目标，应创建多个独立的传输流。

  • KDF 支持至少一次数据传输语义。由于为处理故障而设置的重试机制，传输目标处存在数据重复的可能性。

总而言之，Amazon KDF 是由 AWS 为客户提供的全托管流式 ETL 服务。现在让我们转向另一项 Kinesis 服务   ——Amazon KVS。

Amazon Kinesis Video Streams

Amazon KVS    经过优化，可将来自数百万数据源的实时视频流近实时地传输到 AWS，以供执行任意处理，例如运行 ML 算法或应用自定义视频处理。KVS 也可用于离线批量分析，并支持音频、图像和雷达数据等其他数据流类型。

KVS 可在众多场景中发挥作用，以下通过一个例子说明其如何助力构建家庭安防系统。当人们不在家时，实时、持续地了解家中动态十分有用。为此，安防公司在家中所需位置安装摄像头。这些摄像头作为信息来源，安装了 KVS Producer 库，可与 AWS 云上的 KVS 建立安全连接。该连接持续将视频流传输至 KVS，数据可选择存储或重定向至消费者。消费者是消费这些数据的应用程序，例如用户通过移动设备查看视频流，在发生盗窃或不速之客等情况时尤为有用。上述一切均可实时实现。

以下是使用 KVS 的几个关键注意事项：

  • KVS 为可配置的保留期提供持久化数据存储。它会自动对静态和传输中的数据进行加密，并根据生产者生成的或服务端的时间戳为数据建立索引，以便快速便捷地访问。

  • KVS 是全托管无服务器产品，客户无需担心基础设施管理或调优配置所需的专业知识。

  • KVS 提供解析器库，帮助消费者应用程序以极低延迟从视频流中获取数据。该库可在 Java 应用程序中用于 Matroska Video（MKV）流。

Amazon Simple Queue Service

应用解耦

两个微服务不直接交互，而是通过中间的 SQS 进行通信。这避免了服务依赖，使得一个服务的故障不会影响另一个服务。

背压控制

从 SQS 消费消息的客户端可以按照自己的速率消费消息。SQS 中的消息最多保留 14 天，或按客户配置保留。

接下来介绍与 Amazon SQS 相关的重要概念和关键注意事项：

可见性超时

队列中的消息 在被某个消费者接收后并不会被删除，而是保存在 SQS 所属的临时存储中，直到一个称为可见性超时的超时设置到期。消费者处理完消息后，应在可见性超时时间内通知 SQS 删除该消息。若消费者未在可见性超时内向 SQS 发送删除通知，该消息将重新对其他消费者可见，以供重新消费。可见性超时的取值范围为 0 秒至 12 小时。

保留期

这是 消息未被任何消费者接收时在队列中保留的时间。取值范围为 1 分钟至 14 天。

死信队列（DLQ）

在某些场景下，  消费者可能无法处理某条消息，但您可能需要保留该消息以供稍后重试或调试。死信队列（DLQ）正是为此而设：消费者可将处理失败的消息推送至 DLQ，以便稍后采取进一步措施。

最大消息大小

允许的 最大消息大小为 256 KB。该大小对于所有标准使用场景来说应该足够，但若有更大需求，请考虑使用 S3 或 DynamoDB。消息可以作为 S3 或 DynamoDB 对象存储，并在 SQS 消息中通过引用指向该对象。

消息传递

消息安全性

为   确保数据安全或处理敏感数据，您可以通过指定 AWS KMS 密钥为 SNS 主题启用服务器端加密。启用后，SNS 会对接收到的消息加密并以加密形式存储。消息在转发给主题订阅者时才会解密。此加密仅针对消息主体，因此请避免在主题和消息元数据中存储任何敏感信息。

SQS、Lambda 和 SNS 的组合被广泛用于支持事件驱动的异步架构（发布/订阅模型）以及简单工作流的编排。仔细想想，KDS 提供了类似的模型：数据发布到数据流，多个消费者可从数据流中消费数据。两者的主要区别在于 KDS 或 MSK 流处理方案所提供的近实时处理能力。在 SNS 和 SQS 模型中，数据必须先采集到某个特定系统才能进行分析；而 KDS 则允许在      数据到达的同时进行分析。

工作流编排

AWS 提供  两种工作流编排服务：AWS Step Functions 和亚马逊 Apache Airflow 托管工作流（Amazon MWAA）。Apache Airflow 更受欢迎，更推荐用于批量工作负载，而 Step Functions 则同时适用于实时流处理和批量工作负载（可与亚马逊批处理服务（Amazon Batch）集成）。以我们最喜爱的餐厅——德里高地咖啡馆为例，介绍在线点餐的简单流程。选好食物后下单的步骤顺序为：（1）处理付款，（2）向餐厅发送订单请求，（3）选择配送合作伙伴，（4）跟踪配送，如#ch12_figure_2_1734552291610681所示。

这两项服务均由 AWS 全托管，客户可以专注于构建应用程序，无需担心基础设施维护。以步骤方式执行应用逻辑是提升应用可靠性的主要优势，因为它确保了独立执行（一个组件的问题不会影响其他组件）和妥善的故障处理。Step Functions 是专有服务，而 MWAA 基于开源的 Apache Airflow 构建。让我们更深入地探讨这两个选项。

AWS Step Functions

AWS Step Functions 是一项全托管、无服务器的可视化工作流编排服务，帮助客户轻松创建和运行状态机，以协调分布式应用组件。以下是充分理解 AWS Step Functions 所需掌握的基本术语：

状态机

状态机 将编排工作流表示为一系列步骤，以及这些步骤之间的关系和各自的输入与输出。这些步骤相互协调，并与不同组件交互，例如活动（activity）、Lambda 函数、SQS、DynamoDB 或其他服务，以完成特定操作。

任务

任务 是状态机中的单个状态或步骤。任务决定了要执行的操作，例如调用 Lambda 从 S3 存储桶获取对象并对其进行解析。简而言之，单个状态的职责是从上一个状态获取输入，执行指定工作，并将输出传递给下一个状态。

活动

任务 负责执行某些工作，这些工作可由 EC2 机器、ECS、Lambda 函数上的工作进程或任何能够建立 HTTP 连接的托管在任意位置的应用程序来执行。这通过 Step Functions 的一项称为"活动"的功能来实现。Step Functions 工作流步骤会等待活动工作进程通过 GetActivityTask API 向 Step Functions 轮询任务、完成工作，并通过 SendTaskSuccess 或 SendTaskFailure API 向 Step Functions 发送执行回调。等待回调的超时时间可以根据应用程序的性质和使用场景在任务定义中配置。

您可以使用 Amazon States Language（ASL）或   Step Functions 控制台来创建工作流。ASL 是一种基于 JSON 的结构化语言，用于以声明式方式定义工作流状态，如以下代码片段所示：

{
    "Comment": "Amazon States language Example",
    "StartAt": "Hello World",
    "States": {
    "Hello World": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:HelloWorld",
      "End": true
    }
  }
}

AWS Step Functions 始终使用透明的服务器端加密对静态数据进行加密，并使用 TLS 对从 Step Functions 传递到任何集成服务的所有数据进行加密。这确保了我们的敏感数据在无需任何运维开销的情况下得到保护。状态执行的操作由状态类型决定。设计状态机时可选择的不同状态类型如下：

Pass

Pass 状态不执行任何工作，只是将其输入作为输出传递。该状态主要用于状态机调试，也可用于转换输入，以便将转换后的数据传递给后续状态。

Task

如前所述，Task 状态在状态机中执行实际工作。Task 状态通过 Lambda 函数、活动或不同 AWS 服务的 API 操作来表示一个工作单元。

Choice

Choice 状态类似于任何编程语言中的 if-else 语句。它是一个条件语句，根据条件是否成立来决定状态机中后续要执行的操作。

Wait

Wait 状态在状态机工作流执行期间执行暂停操作。超时值可以是从状态开始时间算起的相对秒数，也可以是以精确时间戳表示的绝对时间。

Succeed

Succeed 状态是成功停止工作流执行的终止状态。

Fail

Fail 状态与 Succeed 状态相反，它以失败状态停止工作流执行。您也可以显式捕获故障以采取特定操作，或直接忽略故障并继续执行后续状态。

Parallel

Parallel 状态在状态机中添加多个执行分支，有助于并行执行独立状态以加快工作流处理速度。

Map

Map 状态针对 JSON 数组或 CSV 文件中的数据集的每个元素并行运行一组工作流步骤。Map 状态支持内联和分布式两种操作模式，您可根据需求选择：

  • 内联模式支持从上一步骤传入的 JSON 数组作为输入，最多可运行 40 个并发执行；执行历史记录不应超过 25,000 条。

  • 分布式模式支持存储在 Amazon S3 中的 JSON 或 CSV 文件，或来自上一步骤的 JSON 数组。与内联模式相比，该模式支持更高并发度，最多支持 10,000 个并行执行，且对执行历史记录数量没有硬性限制。

Parallel 状态与 Map 状态的 区别在于对动态并行的支持。Parallel 状态需预先定义多个并行执行的分支，而 Map 状态可根据输入动态创建并行子分支。

您应始终为服务中断做好准备，以应对各类故障场景。在 Step Functions 中，我们建议根据实际情况添加错误处理和重试机制、重驱动机制以及告警机制，以提高状态机的成功率。

Amazon CloudWatch

在 AWS 云基础设施上  部署应用程序只是第一步，您还需要确保应用程序持续运行并正常处理客户流量。应用指标有助于了解应用程序的状态，例如应用程序处理的流量、API 延迟以及基础设施健康状况。工程师可以在这些指标之上设置告警，用于检测异常（例如某个 API 高频失败），然后通过查看日志和指标图表来调试问题。

为监控应用程序健康状况并调试发生的问题，AWS 提供了 Amazon CloudWatch。CloudWatch 提供对应用日志的存储和检索能力、应用指标的可视化，以及针对任何意外应用行为的仪表板和告警功能。

应用程序日志

当   应用程序运行以处理客户请求时，会产生日志；这些可以是自定义日志或特定于语言运行时的日志。这些日志有助于我们调试系统中出现的问题。您可以实时将任意计算平台上的日志发布到 CloudWatch，并通过 CloudWatch 的搜索功能或 Insights 功能查找特定的错误日志。以下是与 CloudWatch 日志相关的一些关键功能和术语：

日志存储

CloudWatch 可作为所有应用程序或其他 AWS 服务日志的中央存储库。日志属于日志流，日志流是共享同一数据源的日志事件序列。所有具有相似属性（例如来源、保留期、监控和访问控制设置）的日志流属于同一个日志组。例如，软件应用程序配置为每小时创建一个日志流，即每小时会创建一个类似 log_stream_2023_05_15_07（日志流名称格式为年_月_日_小时）的日志流。

个人身份信息（PII）数据

我们应  避免记录任何个人身份信息（PII），例如社会保障号、病历和信用卡详情。此类数据可能会被意外推送到生产环境。为检测此类日志，CloudWatch 可利用模式匹配和机器学习来识别并屏蔽相关日志语句。

日志搜索

调试时，您需要具备对日志的搜索能力。CloudWatch 支持遵循模式匹配语法的多种过滤器。您可以使用这些过滤器识别日志中的特定模式，并为其发布指标，例如统计特定 API 的 ERROR 400 消息数量。

CloudWatch 还提供日志洞察作为附加功能，用于对日志数据进行交互式搜索、分析和可视化。您可以通过支持的查询语言在单次请求中搜索多达 50 个日志组，例如统计五个微服务日志组中 InternalServerException 的总数。

对于一般可视化需求，例如 CPU 利用率或 API 总调用次数，在不需要运行查询来绘制图表的情况下，使用 CloudWatch 指标和告警来对任何意外行为发出告警是一种有效方法。

指标与告警

CloudWatch 指标有助于应用程序监控，使用户能够搜索和绘制指标图表，并在指标之上创建告警。例如，它可以绘制服务自定义指标（如 500 HTTP 错误码的数量），并在连续 15 分钟内每分钟 500 HTTP 错误总数超过 10 时触发告警。让我们更深入地了解指标和告警。

指标

指标本质上  是发送到 CloudWatch 用于可视化的时序数据点集合。如前所述，指标可以是 AWS 资源指标或自定义应用指标。大多数 AWS 服务会免费发布一些默认指标，您也可以根据需要进一步调整——例如精确到分钟级粒度。与日志洞察类似，CloudWatch 的指标洞察功能可用于查询和发现不同发布指标的模式，并为其创建告警。以下是与指标相关的一些术语：

命名空间

命名空间 是用于区分不同指标的根级标识符。例如，EC2 服务指标记录在 EC2 命名空间中。我们也可以创建自定义命名空间；例如，同一 AWS 账户中的多个微服务可通过命名空间加以区分。

维度

维度是 以名称-值对表示的指标标识属性。单个指标最多可关联 30 个维度。例如，要表示某应用程序特定操作的 API 延迟，命名空间为应用程序名称，并带有两个维度：API 名称和指标类型。

指标分辨率

根据使用场景所需的粒度， 您可以在标准分辨率和高分辨率之间选择。标准分辨率下指标的最小粒度为一分钟，高分辨率下为一秒。

统计数据

统计数据 可用于在一段时间内进行数据聚合。例如过去一小时内的最大延迟和 API 调用总次数。您可以根据业务需求从支持的统计数据列表中选择，例如最大值、最小值、样本计数、总和、平均值、百分位等。每种统计数据还有一个关联的单位，例如次数、百分比或秒。例如，过去一小时的平均 CPU 利用率可能显示为 75%。

为进行进一步分析，CloudWatch 指标可以近实时地以 JSON 或 OpenTelemetry 0.7.0 格式流式传输到我们选择的目标。单个指标流最多可包含一千个过滤器，让您可以控制要流式传输的指标。以下是一些适用场景：

  • 通过 Amazon KDF 传输流将指标传输到 Amazon S3。这与账单数据结合使用，可用于寻找成本优化和资源性能提升的机会。

  • 选择第三方服务提供商作为监控和故障排查应用程序的目标。

指标适用于可视化和调试目的，但若要根据意外行为触发告警或发送通知，我们应设置  告警。

告警

应用程序监控  是维护应用程序健康状况的重要方面。告警监控应用指标，并在配置的阈值被突破时通知用户或其他应用程序采取相应措施。例如，当应用程序的 EC2 CPU 利用率大于 75% 时，可通过自动扩缩操作添加一个实例；当利用率小于 30% 时，移除一个实例。以下是设置告警时需要考虑的一些重要事项。

指标

告警基于单个指标或多个指标的数学表达式来设置。要设置告警，您需要提供所有指标信息，例如指标命名空间、指标名称和所有维度。

告警条件

当满足特定条件时触发告警， 这些条件由阈值类型、告警条件、触发告警的数据点数以及缺失数据处理方式等参数定义。支持两种阈值配置类型：静态和异常检测。静态配置可用于配置具体阈值，支持大于、大于等于、小于和小于等于的告警条件。异常检测允许使用数值区间作为阈值，支持的条件包括区间外（大于或小于）、小于和大于。我们可能并不总是希望仅凭一个指标数据点就触发告警。这是一个可配置属性，可根据告警的需求进行设置。

在某些场景下，应用程序问题可能导致指标未推送到 CloudWatch，或特定时间段内确实没有指标需要发布。在这两种情况下，我们可以定义缺失数据的处理方式。支持的处理行为包括：将缺失数据视为正常（在阈值范围内）、异常（突破阈值）、忽略（维持当前告警状态）以及缺失（将告警转换为数据不足状态以进行告警条件评估）。

可配置操作

告警 可处于三种状态：正常（OK）状态、告警中（in-alarm）状态或数据不足以评估告警。可配置告警操作在状态发生转换时触发。支持的告警操作包括：通知、自动扩缩操作、EC2 操作和 Systems Manager 操作。通知操作通过向 SNS 主题发送消息，提醒相关人员。自动扩缩操作使您能够根据告警阈值从 Auto Scaling 组（ASG）中添加或移除实例。EC2 操作允许执行重启、停止、终止或恢复 EC2 实例等操作。您还可以通过创建 OpsItem 来设置 AWS Systems Manager 操作，运维团队可以查看并采取相应措施。

您还可以在多个告警之上创建告警，称为 复合告警。这有助于通过在复合告警上配置操作并跳过子告警上的操作来减少运维噪音。复合告警根据配置的条件或规则表达式触发，例如当所有子告警均处于告警状态时触发，或当其中任意一个处于告警状态时触发。例如，您可以针对应用程序资源利用率设置复合告警，涵盖 CPU 利用率、内存使用量和存储空间。

Amazon CloudWatch Events

AWS 服务  或资源会在不同状态之间转换。例如，当您启动 EC2 实例时，它在完成设置和配置后从挂起状态转换为运行状态。这些状态变化可通过 CloudWatch Events 近实时地流式传输到所需目标，以便采取相应操作。CloudWatch Events 还可使用 cron 或速率表达式来调度自动化操作。例如，对于我们的在线外卖餐厅，我们可以每天早上 7 点（类似于 cron 表达式）运行一个 Lambda 函数来汇总前一天的收入。其他目标包括 Amazon EC2 实例、Amazon KDS、Amazon ECS 任务、AWS Systems Manager Run Command 和自动化、Amazon SQS 以及 Amazon SNS 主题。

AWS 提供了一项与 CloudWatch Events 类似的服务， 称为 Amazon EventBridge（事件总线）。两项服务具有相同的底层架构，但 EventBridge 为客户提供了更多功能。EventBridge 提供对 CloudWatch Events API 的向后兼容，并基于与 CloudWatch Events 类似的概念运行：接收状态变化的事件，并应用关联的规则将该事件路由到最多五个目标。

在 CloudWatch 控制台中选择规则后，AWS 控制台会自动重定向到 EventBridge 页面。您也可以使用 CloudWatch Events 页面。我们建议使用 EventBridge 以获取更多功能，例如从软件即服务（SaaS）应用程序接入事件。让我们更详细地介绍一些额外优势：

与 SaaS 提供商集成

例如，PagerDuty 应用程序可用于收集来自多个平台的数据，提供统一视图以告知团队成员任何问题的发生。假设根据 PagerDuty 告警，需要重启一台 EC2 机器，可以通过向 EventBridge 发送事件来自动化此操作，EventBridge 可将该事件操作传递到特定目标。如果从中移除 EventBridge，通常会使用轮询和自定义 Webhook 从第三方提供商获取数据到我们的软件应用程序。轮询可能非常耗费计算资源——您可能多次收到空响应——而 Webhook 需要通过公共互联网进行通信。为此，EventBridge 允许通过私有 AWS 网络与 SaaS 提供商集成，而无需将数据暴露到公共互联网。

自定义事件总线

事件总线提供从事件发送方到接收方的通信方式。CloudWatch Events 中的所有事件都通过 AWS 账户中存在的默认事件总线进行路由，而 EventBridge 支持创建针对客户工作负载的自定义事件总线并进行受控访问。

增强规则

EventBridge 允许使用基于内容的过滤来过滤事件中的值。这使您能够在 EventBridge 层面进行过滤，帮助您的应用程序只消费所需的事件流量，同时无需在应用程序中实现过滤逻辑。

架构注册表

EventBridge 存储 AWS 服务、集成的 SaaS 提供商以及您自定义事件的架构（Schema），便于开发过程中掌握事件结构。

CloudWatch 是一项极为重要的 AWS 服务，确保对其他 AWS 服务以及部署在 AWS 云环境中的自定义应用程序的健康监控。AWS 服务和资源的安全性是另一个需要考虑的重要方面，以防止任何滥用。下一节将探讨 AWS IAM 服务，您可以使用它为您的 AWS     账户实施访问控制机制。

AWS 身份和访问管理

我们    在本书中多处提到了 IAM 的使用。IAM 针对不同 AWS 资源或整个 AWS 账户，在身份验证和授权方面实施访问控制并强制执行安全措施。首次创建 AWS 账户时，您通过根用户凭证（具有完整管理员权限）登录，但在访问不同资源或允许多人登录并访问 AWS 账户时，我们建议您仅提供所需的访问权限，以避免任何滥用。这种权限粒度通过 IAM 用户、用户组、角色和策略来定义。例如，支持工程师可能只有 CloudWatch 日志的只读权限，而 DevOps 工程师可能有权创建新的日志组或删除现有日志组。

在了解 IAM 的功能和优势之前，让我们先讨论基本术语：

根用户

根用户 是您使用电子邮件和密码凭证创建 AWS 账户时生成的用户。根用户本质上拥有在 AWS 账户中执行任何操作的所有权限，任何显式 IAM 策略均无法拒绝其访问。服务控制策略（SCP）是一种组织策略，可用于限制成员账户根用户的权限。请创建单独的管理员用户以执行日常任务，并仅在需要执行只有根用户才能完成的任务时使用根用户凭证，例如删除账户、注册 AWS GovCloud（美国）以及注册成为卖家。

IAM 用户

IAM 用户代表具有一组特定权限以执行任务的个人或服务。IAM 用户拥有长期凭证，不会随时间过期。凭证可以是用于登录 AWS 控制台的用户名和密码，或用于编程方式登录的访问密钥 ID（Access Key ID）和秘密访问密钥（Secret Access Key）组合。在可能的情况下，请避免创建 IAM 用户，转而使用具有临时凭证的 IAM 角色。如果必须创建 IAM 用户，请定期更新密码并轮换 AWS 密钥。

IAM 用户组

IAM 用户组将具有相同权限集的用户归为一组。您无法使用用户组名称登录 AWS 账户，但用户组使管理具有相似权限的用户变得更简单。与其重复为每个新用户分配相同权限，只需将新用户添加到用户组即可，从而降低管理负担。

IAM 角色

IAM 角色类似于 IAM 用户，但不与特定的个人或服务绑定。角色由个人、服务或另一个 AWS 账户临时担任，以执行任何任务。例如，在 EC2 实例上运行的应用程序会担任角色，以对其他资源（例如从 S3 下载文件）进行 API 调用。这确保了仅在需要的时间内提供临时访问，并在之后自动撤销。IAM 角色可创建为限制访问权限，有助于防止对 AWS 资源环境的任何意外更改。我们建议在限定时间段内使用 IAM 角色而非 IAM 用户进行临时访问。某些使用场景可能明确需要 IAM 用户，例如无法担任 IAM 角色的第三方工作负载、AWS CodeCommit 访问、Amazon Keyspaces 访问，或为紧急情况创建的 IAM 用户；在这些情况下，您应确保启用多重身份验证（MFA）。

IAM 策略

IAM 策略是一个 JSON 对象（ACL 策略类型除外，我们在#ch10_aws_storage_services_1734552290474903中讨论过，它基于 XML 结构），表示一组权限，附加到 IAM 身份（用户、用户组或角色）或 AWS 资源。回顾一下之前关于如何授予 EC2 从 S3 下载对象权限的示例。要使该角色具有 S3 下载权限，您需要附加如下 IAM 策略：

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket"],
      "Resource": ["arn:aws:s3:::samplebucket"]
    },
    {
      "Effect": "Allow",
      "Action": [
        "s3:GetObject"
      ],
      "Resource": ["arn:aws:s3:::samplebucket/*"]
    }
  ]
}

IAM 策略的 JSON 文档本质上包含 Effect（值为 Allow 或 Deny），以及 Action（指定所有资源操作）和 Resource（指定相关资源），以及 Condition、Principal 和 Sid 等附加元素。

在#ch09_aws_network_services_1734552289953244中，我们讨论了在不同 AWS 存储服务的背景下将德里高地咖啡馆上线的过程。假设我们已创建了一个 AWS 账户用于托管和运营这家在线餐厅，并雇用了许多人员协助运营。所有参与软件应用程序开发和测试的人员都需要访问 AWS 账户。提供访问权限的方式有多种：

  • 与团队所有成员共享根凭证。我们不推荐此选项，因为它向所有人提供了完整访问权限。这并非必要，且可能被有意或无意地滥用。

  • 创建 IAM 用户并将其关联到 developer-group、devops-group 和 support-group 等用户组。这可以视为一种较佳选项，但如前所述存在一些缺点。

  • 我们可能已通过某个身份提供程序（IdP）（例如 Google、Facebook 或 Amazon）管理团队。我们可以创建一个 IAM 身份提供程序实体，在 IdP 与 AWS 账户之间建立信任关系。这使所有用户能够以有限权限临时担任 IAM 角色，而无需暴露 AWS 访问密钥。

随着不同团队协同工作，始终会存在一个团队需要访问另一个团队 AWS 账户资源的使用场景，或者多个团队在同一账户中共享资源。对于这些场景，可通过信任策略和权限策略来管理访问，这被称为 委派权限。信任策略指定允许担任角色的受信任账户成员，权限策略指定受信任用户执行任务所具有的权限。

AWS IAM 有助于保护和管理对不同 AWS 资源的访问。AWS 还提供另一项服务——Amazon Cognito，用于用户池管理，作为身份提供程序（IdP）使用，并为    用户身份验证提供许多其他功能。

Amazon Cognito

Amazon Cognito   是一项全托管、高度可扩展的客户身份和访问管理（CIAM）服务，使客户能够建立和管理用于身份验证（AuthN）和授权（AuthZ）的身份池。Cognito 全权负责管理支持此功能所需的计算和存储。您可以使用 Cognito 进行新用户注册、现有用户登录、访客用户维护和访问控制定义。来看一个简单的示例：我们希望在线餐厅的顾客能够在提交食品评价时上传图片。为了允许顾客直接将图片上传到我们 AWS 账户的 S3 存储桶，我们可以通过 Cognito 提供临时写入权限。

AuthN 用于确认实体的身份，AuthZ 用于确定该实体可以访问哪些资源。

在 AWS 账户访问方面，AuthN 确认您是否可以登录 AWS 账户，AuthZ 确认您是否可以访问特定的 AWS 资源。

要理解 Cognito 的工作原理，您需要了解以下概念：

身份提供程序

身份提供程序（IdP）  存储和管理用户的数字身份。Cognito 本身可充当身份提供程序（IdP），您也可以将其与第三方 IdP（如 Google、Amazon 和 Facebook）集成（支持的协议包括 OAuth 2.0、SAML 和 OpenID）。例如，您可能会在日常使用的许多应用程序中看到 Google 作为登录选项。IdP 也称为联合身份，因为它可以跨平台用于用户身份验证。在 AWS 与外部 IdP 之间建立信任关系的过程称为联合身份验证。

用户池

用户池 是作为身份提供程序（IdP）的用户目录。无论是通过 Cognito 还是第三方集成 IdP 登录的用户，其用户记录均存储在用户池目录中。它还支持注册、忘记密码、登录、密码长度和策略以及多重身份验证（MFA）等所有功能。

身份池

身份池 通过接受有效令牌（例如 JSON Web 令牌（JWT）或 SAML 令牌）作为输入，为已认证和未认证用户提供应用程序访问的临时凭证。可根据您指定的不同标签为用户分配临时角色。以我们在线点餐的示例为例，用户无需登录即可浏览食物并选择商品，但下单时必须登录。当用户点击"下单"时，可通过重定向到 Amazon Cognito 托管用户界面来实现这一点，然后再重定向到付款页面确认订单。

用户池托管用户界面

我们需要 某种用户界面供用户在我们的应用程序中注册或登录。Cognito 提供一个由 AWS 托管的 URL，用于用户与应用程序之间的交互。该界面可包含电子邮件、密码登录，或任何集成的第三方 IdP，如#ch12_figure_5_1734552291610743所示。用户通过身份验证后，将被引导至指定为重定向 URL 的特定应用程序页面。我们也可以根据需要自定义界面页面，例如添加自定义徽标或 CSS。

触发器

您 可以通过触发器消费 Cognito 事件（例如用户预身份验证或后身份验证），并基于这些事件运行 AWS Lambda 函数。Lambda 触发器为底层应用程序的用户 AuthN 和 AuthZ 运行额外逻辑。例如，您可以运行一组自定义验证规则，例如要求用户访问特定网页的位置必须在印度，用户才能注册该应用程序。

软件应用程序可通过多种方式借助 Cognito 完成身份验证（AuthN）和授权（AuthZ）：

  • 用户通过前端应用程序与 Cognito 交互以获取令牌，并在后续 API 调用中使用相同的令牌。后端应用程序可通过 AWS SDK Amazon Cognito API 与 Cognito 交互，针对用户验证这些令牌。

  • Cognito 提供与 Amazon API Gateway 的原生集成，无需客户进行任何额外工作。当应用程序 API 通过 Amazon API Gateway 提供时，无需手动验证令牌，验证可根据配置自动完成。

  • 为减少您的手动配置工作，可以使用 AWS Amplify 自动创建所需基础设施，然后使用 AWS SDK 与 Cognito 交互。

您始终可以自行构建自定义的 AuthN 和 AuthZ 解决方案，而无需使用 Cognito。我们将在#ch16_designing_a_social_network_and_newsfeed_system_1734552293547861中对这些选项进行更详细的比较。

让我们回到使用 Cognito 为上传对象到 Amazon S3 分配临时凭证的示例。本质上有两种实现方式：

S3 预签名 URL

预签名 URL 可针对 S3 存储桶或特定对象创建特定权限——请注意，创建预签名 URL 的用户必须拥有相应权限。这种方式的一个缺点是需要预先定义对象键名，因此要在运行时创建预签名 URL，需要在中间添加一个计算层。例如，AWS Lambda 从客户端捕获文件名，创建 S3 预签名 URL，并响应客户端以供进一步上传对象。

Amazon Cognito

您可以使用 Cognito 的身份池为用户分配临时凭证，允许他们直接将文件上传到 S3。使用此方式取决于您正在处理的使用场景类型，因为此选项需要完成 Cognito 的配置。如果已经为用户 AuthN 和 AuthZ 设置好相关配置，这可能会简化我们的工作。

这两种方式也可以结合使用：Cognito 负责用户身份验证，AWS Lambda 负责生成预签名 URL。

我们讨论了身份池中基于不同标签的临时角色分配——角色也可以基于令牌和 IAM 策略来分配，即将角色相关信息作为令牌的一部分获取，并用其来分配角色。对于需要动态角色创建的需求，IAM 策略中的访问控制属性可能会有所帮助。

AWS 提供 IAM、Cognito 等 AuthN 和 AuthZ 服务，使开发团队无需从头构建相关解决方案，大幅加快了开发节奏。AWS AppSync 是另一项服务，有助于前后端团队在大规模 API 开发中独立扩展。让我们来看看 AWS AppSync   的功能。

AWS AppSync

要充分  理解 AWS AppSync 的工作原理，我们首先来思考如何在在线点餐平台上向顾客展示食品信息。前端应用程序展示食品信息、价格、餐厅优惠券、评价等内容。这些数据由后端微服务架构中的不同应用程序维护。前端应用程序有两种选择：分别调用每项服务的 API 并收集数据，或使用单个 API 从所有这些不同的后端服务收集数据并返回给前端。

回想 一下，我们在#ch06_communication_networks_and_protocols_1734552288217584中讨论了 GraphQL。AppSync 本质上是一个单一的 GraphQL 端点，可在单次网络调用中查询多个数据库、微服务和 API。在我们的示例中，可以使用 AppSync 向前端暴露单个端点，从不同微服务收集数据。AppSync 也可用于创建发布/订阅 API，通过全托管无服务器 WebSocket 连接向订阅客户端发布通知，例如实时体育赛事更新。

以下是开始使用 AppSync 需要了解的基础组件：

GraphQL 架构

一种数据模型，指定用于数据检索的查询模式。

解析器

在架构与不同数据源之间提供链接的组件。它们将 GraphQL 载荷转换为底层系统协议，并在具备相应 IAM 权限的前提下执行操作。

数据源

解析器可使用访问凭证从中获取数据的数据目标，例如 Amazon DynamoDB、Amazon RDS、AWS Lambda 和 HTTP 端点。#ch12_figure_6_1734552291610763中显示的数据源可位于同一 AWS 账户或不同 AWS 账户中。

合并 API

由多个源 API、GraphQL 架构、解析器和数据源合并操作构建而成的单个 AppSync API。源 API 可由独立团队管理，并通过合并 API 进行协作。

您可能会问：为什么要使用 AppSync，而不是自行部署 GraphQL 基础设施？主要原因是将 AuthN 和 AuthZ、缓存和加密等功能的运维开销从客户身上卸下。AppSync 还简化了聊天应用程序、基于位置的通知、实时游戏计分板以及结合 AWS Amplify 的离线支持等高级使用场景的构建。为提供这些优势，AppSync 是一项全托管无服务器服务，提供构建时合并 API 的组合，以及与 AWS WAF（网站防火墙）、Amazon CloudWatch、Amazon Cognito 和 TLS 加密   等 AWS 服务的便捷集成。

总结

到目前为止，您已了解 AWS 提供了种类繁多的服务，充分理解业务需求以利用最适合的服务实现目标至关重要。您会注意到，某些服务具有类似的功能，例如将 MSK 与 SQS-SNS 或 KDS 进行比较时。

或者考虑这样一点：像 AWS Step Functions 这样的全托管无服务器应用程序不会让我们完全了解工作流在幕后如何编排，但重要的问题是：我们真的需要了解吗？因为 Step Functions 为我们节省了大量的管理和运维成本，同时还提供了通过可视化工作流进行调试的额外能力。

我们还强调了应用程序监控作为确保高可用性的重要方面，以及如何通过在 Amazon CloudWatch 中设置指标、日志和告警来实现这一点。随后，我们深入探讨了 AuthN 和 AuthZ 服务如何帮助保护我们的应用程序，以及 AWS 基础设施环境中的不同组件如何以安全受控的方式相互通信。我们建议遵循最小权限原则：仅为应用程序、用户或另一个 AWS 账户提供执行操作所需的最小权限集。
