AWS 存储服务

#ch02_storage_types_and_relational_stores_1734552286519892 和 #ch03_nonrelational_stores_1734552286860587 介绍了多种存储类型与解决方案。本章将介绍 AWS 提供的各类存储服务，以及它们与市场上不同存储解决方案的对应关系。我们将从块存储等传统存储服务入手，再介绍不同类型的数据库，并结合业务需求和技术需求探讨如何选择合适的解决方案。

回顾 #ch09_aws_network_services_1734552289953244 介绍的 Cafe Delhi Heights 案例。这家连锁餐厅正准备拓展线上业务，让顾客能够浏览餐品并在线下单。为提供良好的客户体验并支持线上餐饮配送服务，Cafe Delhi Heights 计划使用 AWS 存储服务来保存餐厅图片、菜单、营销活动信息等数据。Cafe Delhi Heights 已委托我们完成这项工作。接下来，我们需要明确其存储需求，并选择最合适的 AWS 存储方案。具体来说，我们需要能够：

  • 存储顾客的个人资料和登录凭证，例如用户名和密码

  • 存储餐品信息，例如当前供应的菜单项

  • 存储各类媒体内容，例如餐品图片和顾客上传的评价

  • 通过大数据分析改善客户体验，例如区分正面评价和负面评价

  • 建立美食社区，让用户能够在社交圈中交流互动

  • 根据名称、餐厅位置、评分等多个条件搜索餐品

  • 在应用程序日志和指标产生 90 天后将其归档，并保留一年

AWS 存储服务使客户能够存储、保护和分析数据，同时减少相关的运维负担。本章将分为两大部分：云存储和数据库。首先，我们将介绍云存储，包括块存储、文件存储和对象存储服务。

AWS 云存储

AWS    提供多种云存储服务，包括提供块存储的 Amazon Elastic Block Store（Amazon EBS）、提供文件存储的 Amazon Elastic File System（Amazon EFS），以及提供对象存储的 Amazon Simple Storage Service（Amazon S3）。#ch02_storage_types_and_relational_stores_1734552286519892 已经介绍了这些存储类型的基本概念。本节将进一步介绍 AWS 提供的相应服务。由于各项服务适用于不同的存储需求，接下来我们将分别探讨它们的优势。

亚马逊弹性块存储

Amazon EBS 是一种块存储服务，    其作用类似于连接到个人计算机的物理硬盘。EBS 卷可以挂载到 Amazon EC2 实例（EC2 的更多内容见 #ch11_aws_compute_services_1734552290903110），其生命周期独立于 EC2 实例。EBS 还具有较高的灵活性，允许在生产工作负载运行期间修改卷配置，例如：

  • 动态扩容

  • 调整预置的每秒输入/输出操作次数（IOPS）

  • 更改 EBS 卷类型

EBS 卷能够以较低的延迟访问存储在卷中的数据，适用于需要频繁进行磁盘访问的场景，例如：

  • 自行部署和维护数据库，而非使用 AWS 托管的数据库服务

  • 创建操作系统启动卷

对于需要临时块存储、且希望获得比 EBS 更高 I/O 性能的场景（例如缓存和设备缓冲区），AWS 提供了另一种存储方案——实例存储（Instance Store）。 实例存储直接连接到 EC2 实例，而 EBS 则通过网络连接。实例存储中的数据可能因底层磁盘故障或 EC2 实例停止、休眠、终止等状态变化而丢失。与 EBS 卷相比，实例存储的灵活性较低，例如无法随意挂载到其他 EC2 实例，也不支持动态扩容。

AWS  提供多种 EBS 卷类型，可根据成本、性能等因素选择适合的类型。下面将介绍不同 EBS 卷类型的适用场景：

固态硬盘（SSD）

此类卷包括  通用型 SSD 和预置 IOPS SSD，针对事务性工作负载进行了优化，适合处理单次读写数据量较小的 I/O 请求。

硬盘驱动器（HDD）

此类卷包括  吞吐量优化型 HDD 和冷存储 HDD，针对大规模流式工作负载进行了优化，主要以吞吐量衡量其性能。

磁性磁盘

此类 卷主要适用于对性能要求不高的小型工作负载，例如需要低频访问磁盘数据的场景。

使用 EBS 卷时，需要注意以下几点：

  • 一个 EC2 实例可以同时挂载多个 EBS 卷。

  • EBS 卷仅能挂载到同一可用区（AZ）内的 EC2 实例。例如，位于 us-east-1a 的 EBS 卷无法挂载到 us-east-1b 的 EC2 实例。通过创建 EBS 卷的时间点快照（备份），可以在其他可用区或区域恢复数据，为跨可用区或跨区域的高可用性及灾难恢复方案提供支持。

  • EBS 卷最初不支持在多个 EC2 实例之间共享。后来，AWS 推出了 EBS 多重挂载（Multi-Attach）功能，允许将一个预置 IOPS SSD 卷同时挂载到同一可用区内最多 16 个 基于 Nitro 系统的 EC2 实例，供 Linux 应用程序使用。

  • EBS 卷会在可用区内自动复制，以降低单个硬件组件故障造成数据丢失的风险。

EBS 卷存在一些限制，例如卷的挂载受可用区约束，而跨 EC2 实例共享也受到限制。对于需要跨实例共享文件的场景，AWS 提供了另一种存储方案——Amazon EFS。    

亚马逊弹性文件系统

EFS 是一种共享文件系统，    支持同一 AWS 区域内的多台服务器以及本地数据中心的服务器共享文件数据。EFS 是一项完全托管的无服务器存储服务，可与 Amazon EC2、Amazon ECS 和 AWS Lambda 等 AWS 计算服务配合使用。用户无需预先分配存储容量，存储费用主要根据实际使用量计算。

Amazon EFS 通常用于大数据分析、机器学习和内容管理等业务场景。EFS 和 EBS 都能提供低延迟的数据访问，但实际性能还取决于延迟、吞吐量和每秒 I/O 操作次数（IOPS）等因素。

EFS 提供多种存储类别，可根据业务需求选择合适的 存储类别：

EFS 标准版和标准低频访问版（Standard IA）

这两种存储类别均支持跨 AWS 区域内多个可用区的高可用性。EFS Standard 适用于频繁访问数据的场景，而 Standard Infrequent Access（Standard IA）则更适合低频访问数据的场景，有助于降低存储成本。不过，IA 存储类别的首字节读取和写入延迟相对较高。

EFS 单区版和单区低频访问版（One Zone IA）

EFS One Zone 与区域级 EFS 存储方案在可用性和成本方面有所不同。One Zone 将文件系统数据存储在单个可用区内，而区域级方案则跨多个可用区存储数据。因此，One Zone 的成本通常较低，但无法抵御整个可用区发生故障的风险。可以使用 AWS Backup 备份 One Zone 文件系统的数据，以增强数据保护能力。

在托管企业业务应用程序方面，云仍是一项相对较新的技术，因此有些场景仍依赖 Windows 文件服务器等其他文件系统。针对这些场景，AWS 提供了托管服务 Amazon FSx，可自动扩展，并减轻运维负担。借助 FSx，可以运行常见的开源和商业授权文件系统，而无需自行负责底层硬件的维护和配置。以下介绍其中两种 FSx 类型：

FSx for Windows File Server

FSx for Windows File Server  基于 Windows Server 构建，支持 Windows、Linux 和 macOS 系统通过服务器消息块（SMB）协议访问。它支持数据去重、终端用户文件共享，以及与 Microsoft Active Directory（AD）集成等功能。

FSx for Lustre

FSx for Lustre  基于高性能文件系统 Lustre 构建，适用于机器学习、高性能计算和视频渲染等计算密集型工作负载。它还可以与 Amazon S3 集成，使用户能够通过文件系统接口和 S3 API 访问与处理相关数据。

需要注意的是，EBS 和 EFS 通常需要通过计算实例或客户端来访问其中的数据。相比之下，Amazon S3 是 AWS 提供的可扩展对象存储服务，用户可以通过公共互联网或 AWS 私有网络，直接使用 S3 API 访问对象，而无需额外部署中间文件服务器。   

亚马逊简单存储服务

AWS     提供的 Amazon S3 是一种高度可扩展的对象存储服务，适用于网站、媒体文件存储、备份和大数据分析等多种场景，可用于存储和保护数据。S3 将对象存放在称为存储桶（bucket）的容器中。下面介绍使用 S3 时需要了解的几个关键概念：

存储桶

存储桶 是通过唯一名称标识的容器。创建存储桶时，需要指定名称和 AWS 区域，还可以配置版本控制等选项。

对象

对象 是存储在存储桶中的数据单元，通常由上传的文件形成。每个对象都有一个键名（key），用于在存储桶内标识该对象。

版本控制

S3 版本控制功能允许 保留同一对象的多个版本，使用户能够访问和恢复以前的版本，在应用程序故障或意外修改数据等情况下尤其有用。每个对象版本都有对应的版本 ID。

S3 存储类

不同 业务场景对数据存储和访问方式的要求各不相同，因此 S3 提供了多种存储类别。可以根据业务需求选择合适的存储类别，例如考虑数据是否需要频繁访问，或者是否需要长期归档。

要以尽可能低的成本充分利用 S3，关键在于明确业务需求，并选择最合适的 S3 存储类别。下面将根据对象的访问方式和冗余需求，介绍三种存储类别。

频繁访问对象

面向频繁访问对象的 存储类别适用于对访问延迟敏感、需要毫秒级响应的场景。根据所需的数据冗余程度，可分为以下两种：

S3 标准版

新上传对象的默认存储类别

低冗余存储

适用于非关键性数据的存储场景，其冗余程度低于 S3 Standard

AWS 建议优先选择 S3 Standard，而不是低冗余存储（Reduced Redundancy Storage），因为前者的成本效益更高。

低频访问对象

面向低频访问对象的 存储类别适用于需要长期保存、但访问频率较低的数据，例如备份数据。根据数据冗余需求，可分为以下两种：

标准低频访问（Standard IA）

数据以冗余方式存储在多个可用区中，因此即使单个可用区发生故障，对象数据仍能得到保护。

单区低频访问（One Zone IA）

数据存储在单个可用区中，因此与 S3 Standard-IA 相比，抵御可用区故障的能力较弱，但存储成本通常也较低。如果数据丢失不会对业务造成重大影响，或者数据可以重新生成，则适合选择此存储类别。

归档对象

面向归档对象的 存储类别支持以较低成本长期保存数据，其数据持久性与 S3 Standard 相近。根据数据检索需求，可分为以下三种：

S3 Glacier 即时检索

此存储类别适用于访问频率极低、但仍需要毫秒级检索的数据。与 S3 Standard-IA 相比，其存储成本较低，但数据访问成本较高。

S3 Glacier 灵活检索

此存储类别适用于需要在数分钟内（1 至 5 分钟）检索数据的场景。该类别的最短计费存储时长为 90 天，即使对象提前删除或转移到其他存储类别，存储费用仍按完整的 90 天计算。

S3 Glacier 深度归档

此存储类别的存储成本最低，最短计费存储时长为 180 天，标准检索通常可在 12 小时内完成。此外，也可以选择批量检索，通常可在 48 小时内完成。

生命周期配置

假设 某个业务场景中的数据在最初 30 天需要频繁访问，之后访问频率逐渐降低。可以使用 S3 生命周期配置来满足这一需求。生命周期配置由应用于存储桶中对象的一组规则构成，可定义以下两类操作：

转换操作

定义对象的存储类别转换操作，例如在 30 天后将对象从 S3 Standard 转换到 S3 Standard-IA。

过期操作

定义对象的过期操作。S3 会根据配置的生命周期规则自动处理已过期的对象。

智能分层

S3  提供智能分层（Intelligent-Tiering）功能，可根据对象的访问模式，自动将其转移到不同的访问层，从而减少存储管理的运维工作。下面介绍对象在各访问层之间自动转换的过程：

频繁访问

新上传或转换到 S3 Intelligent-Tiering 存储类别的对象，最初都会进入频繁访问层。

低频访问

如果对象连续 30 天未被访问，S3 会自动将其转移到低频访问层。

归档即时访问

如果对象连续 90 天未被访问，S3 会自动将其转移到归档即时访问层。此外，S3 还提供两个可选的归档访问层。启用相应选项后，连续至少 90 天未被访问的对象可转移到归档访问层，而连续至少 180 天未被访问的对象可转移到深度归档访问层。

选择 S3 存储类别时，需要考虑数据的访问模式和冗余需求。除此之外，在 S3 中存储对象时，数据安全也是一个重要的考虑因素。 

Amazon S3 数据安全

默认情况下，S3 存储桶中的对象  仅允许存储桶所有者访问。S3 提供了多种安全机制，用于保护数据并管理存储桶及对象的访问权限：

加密

默认情况下，S3  使用 S3 托管密钥进行服务器端加密（SSE-S3），也可以选择其他加密方式，例如使用 AWS Key Management Service（AWS KMS）密钥的服务器端加密（SSE-KMS）。此外，还可以在客户端对数据进行加密，以满足特定的安全需求。

对象锁定

对象锁定（Object Lock）功能可以在 启用版本控制的 S3 存储桶上启用。该功能采用一次写入、多次读取（WORM）模型，有助于满足组织的合规要求。对象锁定可以通过设置固定保留期限或法律保留（Legal Hold），防止受保护的对象版本在保留期内或法律保留生效期间被删除或覆盖。

阻止公共访问

此 功能用于集中管理 S3 存储桶的公共访问权限，也可以在 AWS 账户级别进行配置，使相关设置适用于账户中的所有 S3 存储桶。一般情况下，除非业务确有需要，例如提供可公开访问的媒体文件，否则不应开放存储桶的公共访问权限。可以使用 S3 访问分析器（Access Analyzer for S3）识别允许公共访问的存储桶。

IAM 策略

可以通过IAM 策略向用户或用户组  授予访问 S3 资源的权限，例如读取或写入对象。

Amazon Macie

Amazon Macie 可以发现 S3 存储桶中的敏感数据，例如信用卡号，并帮助识别相关的数据安全风险。它还可以评估存储桶级别的访问控制情况，例如识别允许公共访问的存储桶，其作用在这方面与访问分析器类似。

访问控制列表（ACL）

S3 访问控制列表（ACL）是附属于存储桶或对象的子资源，  用于管理其他用户的访问权限。ACL 默认处于禁用状态，通常建议保持禁用，除非确实需要对各个对象分别设置访问权限。一般情况下，可以使用策略代替 ACL 管理访问权限。

存储桶策略

存储桶策略用于管理对  S3 存储桶及其中对象的访问权限。例如，可以通过存储桶策略允许账户 A 读取账户 B 所拥有的 S3 存储桶中的对象。存储桶策略的大小上限为 20 KB。

前面介绍了多种云存储服务。借助这些服务，我们可以像使用个人计算机上的存储设备一样保存         和处理数据。接下来，我们将介绍 AWS 提供的数据库服务。#ch02_storage_types_and_relational_stores_1734552286519892和 #ch03_nonrelational_stores_1734552286860587分别介绍了关系数据库和非关系数据库，相信读者已经了解数据库存储数据的基本方式。

AWS 数据库

AWS 提供  多种数据库及相关数据服务，包括 Amazon RDS、Amazon DynamoDB、Amazon DocumentDB 和 Amazon ElastiCache 等，以满足不同业务场景的需求。这些托管服务可以减少软件和硬件管理方面的运维负担，并提供业务所需的扩展能力。我们将首先介绍关系数据库服务 Amazon RDS，它支持 Oracle、Microsoft SQL Server、MySQL、PostgreSQL、MariaDB 和 Amazon Aurora 等数据库引擎。

Amazon RDS

如果不使用      Amazon RDS，而是自行运行#ch02_storage_types_and_relational_stores_1734552286519892介绍的 MySQL 或 PostgreSQL 等关系数据库引擎，可以采用不同的部署方式。例如，要在本地计算机上运行 MySQL，需要自行下载安装软件。也可以在 AWS 云中的 EC2 实例上安装数据库，但随后仍需自行负责数据库维护、EBS 卷的挂载和管理等工作。

RDS 可以减轻数据库部署和维护方面的运维负担，让用户通过简单的操作创建并使用数据库实例。您可以参考创建 RDS 数据库实例的文档完成设置。在创建数据库时，还需要注意以下几个重要事项：

引擎类型

您可以根据需求选择合适的数据库引擎。选定引擎后，还需要指定其他配置，例如数据库版本类别（edition）和引擎版本。

模板

创建数据库时，可以使用模板预先选定一组配置。可选模板包括生产环境、开发/测试环境和免费套餐。

设置

配置内容包括数据库实例标识符（在同一 AWS 账户的同一区域内必须唯一），以及用户名、密码等登录凭证信息。

数据库实例类

数据库实例类别决定实例的计算能力和内存容量。您可以根据工作负载对计算和内存资源的需求，选择标准型、内存优化型或突发性能型实例。

存储

在存储配置中，您可以选择 SSD、HDD 或磁性存储等存储类型，指定分配的存储容量，并选择是否启用存储自动扩展功能。

可用性和持久性

为提高生产数据库的可用性，RDS 提供多可用区（Multi-AZ）部署选项，可在不同的可用区中创建备用数据库实例。当数据库实例或可用区发生故障时，可以通过故障转移机制减少服务中断。

连接

在连接配置中，您可以指定数据库实例所在的虚拟私有云（VPC），并配置数据库子网组、安全组、是否允许公开访问、可用区以及数据库端口等选项。

此外，您还可以配置备份、监控和维护窗口等选项。

Amazon 还  提供了自主研发的数据库引擎 Aurora，兼容 MySQL 和 PostgreSQL。根据 AWS 的性能比较，Aurora 的运行速度最高可达在相同硬件上运行的 MySQL 的 5 倍、PostgreSQL 的 3 倍。Aurora 还可以根据应用程序需求自动扩展。它将数据的 6 个副本分布在三个可用区中，并持续备份到 Amazon S3。此外，Aurora 支持跨区域数据复制，以改善全球用户的数据访问体验。对于负载难以预测的应用程序，或不需要持续运行数据库实例的开发场景，可以考虑使用 Aurora Serverless。

使用 Aurora 时，需要注意以下几点：

  • 与常规 RDS 数据库实例不同，Aurora 无需预先分配存储容量，而是由系统自动管理和扩展存储空间。

  • Aurora Serverless 使用 Aurora 容量单位（Aurora Capacity Unit，ACU）来配置最小和最大容量，而不是像常规 RDS 实例那样依赖固定的实例类别。

  • RDS 数据库实例部署在 VPC 中。常规 RDS 实例可以配置为允许通过公共互联网访问，也可以限制为仅允许特定 IP 地址连接。对于这里介绍的 Aurora Serverless 配置，数据库不支持直接通过公共互联网访问，但可以通过 Data API，或使用与 Aurora 位于同一 VPC 中的 EC2 实例进行连接。

  • 为保障数据安全或满足静态加密方面的合规要求，RDS 和 Aurora 均支持对数据库中的数据进行静态加密。

  • Aurora 数据库集群最多可以包含 15 个 Aurora 只读副本。通过多个只读副本分担读取负载，可以扩展读取能力并降低读取延迟。当写入实例发生故障时，Aurora 可以将符合条件的只读副本提升为新的写入实例，从而提高集群的可用性。

如果业务需要存储关系型结构化数据，并要求事务满足 ACID 特性，那么 RDS 是一种合适的选择。许多现代应用程序并不要求严格的 ACID 事务保证、完整的关系模型支持或固定的数据模式。对于这类场景，NoSQL 数据库也是可行的选择，可以提供良好的可扩展性和性能，同时减少运维负担。#ch03_nonrelational_stores_1734552286860587 已经介绍了多种 NoSQL 数据库。本章将进一步介绍 AWS 提供的相应服务，     首先从键值数据库 Amazon DynamoDB 入手。

为满足事务性工作负载对关系数据库计算和存储扩展能力的需求，AWS  推出了 Aurora DSQL。Aurora DSQL 是一种兼容 PostgreSQL 的分布式关系数据库，支持 ACID 事务，并通过托管服务模式减少维护工作。

Amazon DynamoDB

Amazon DynamoDB      是一种键值数据库，旨在为不同规模的工作负载提供个位数毫秒级的访问延迟。DynamoDB 使用表来组织数据，并采用灵活的数据模式。#ch03_nonrelational_stores_1734552286860587 介绍过主键、分区键和排序键，以及如何利用这些键唯一标识数据项。在 DynamoDB 中，  主键可以仅由分区键组成，也可以由分区键和排序键共同组成。用户可以通过 AWS CLI、AWS 管理控制台，或所用编程语言的 AWS 软件开发工具包（SDK）查询数据。DynamoDB 使用主从节点架构，并在内部将数据存储于称为分区的存储单元中。

DynamoDB 使用以下两种键来组织和定位数据：

分区键

创建表时必须指定分区键 。DynamoDB 将分区键的值传入内部哈希函数，以确定数据存储的物理分区。如 #ch10_figure_1_1734552290456045 所示，请求路由器（RR）负责将请求路由到相应分区。RR 是一项无状态服务，会查询分区元数据服务来确定目标分区，再将请求转发过去。PUT 请求由主节点处理，而 GET 请求可以由主节点或从节点处理，具体取决于所需的读取一致性。

排序键

创建表时可以选择是否定义排序键 。如果定义了排序键，主键就由分区键和排序键共同组成；否则，主键仅包含分区键。同一表中，分区键与排序键的组合必须唯一。具有相同分区键的数据项会按排序键值排序，并在内部组织为一个数据项集合。建议根据应用程序的读写访问模式设计分区键和排序键，以便尽可能直接满足查询需求，减少对全局二级索引（GSI）的依赖。

DynamoDB 是一项完全托管的数据库服务，无需用户自行配置服务器或预先分配存储空间。用户可以为每张表选择适合的容量模式，以管理读写吞吐量。DynamoDB 使用     读取容量单位（RCU）和写入容量单位（WCU）衡量读写容量需求。实际费用取决于所选容量模式、读写用量，以及一致性和事务处理等因素，详见定价。下面介绍 DynamoDB 提供的容量模式：

预置容量

在预置容量模式下，用户可以为 DynamoDB 表指定 RCU 和 WCU 数值，DynamoDB 则负责管理相应的底层资源。对于流量较为稳定、能够合理预测读写容量需求的应用程序，这种模式通常比较合适。

自动扩展

对于流量变化较大、难以确定固定预置容量的工作负载，可以启用自动扩展功能，为 RCU 和 WCU 设置最小值和最大值。DynamoDB 会根据实际流量需求自动调整预置的读写容量。

按需

在按需容量模式下，用户无需预先指定 RCU 和 WCU 数值。DynamoDB 会根据实际请求量自动管理读写容量，无需用户自行调整预置容量。这种模式适用于工作负载难以预测或应用程序流量波动较大的场景。

DynamoDB 表可能需要支持多种业务场景，仅依靠主键设计未必能满足所有场景的查询性能需求。为此，DynamoDB 提供了二级索引功能，以提高查询效率。可以将二级索引理解为根据基础表中的部分属性构建的辅助数据结构。DynamoDB      支持两种二级索引：本地二级索引（LSI）和全局二级索引（GSI）。两者的区别见 #ch10_table_1_1734552290462351。

生命周期

LSI 必须在创建基础表时一并定义，且不能单独删除；删除基础表时，LSI 也会随之删除。

可以在基础表创建后，根据需要新增或删除 GSI，无需重新创建基础表。

LSI 与基础表使用相同的分区键，因此称为“本地”索引。对于具有 LSI 的表，每个分区键值对应的数据项集合大小上限为 10 GB。

GSI 使用独立于基础表的键结构和分区方式，因此称为“全局”索引。GSI 不受 LSI 所特有的每个数据项集合 10 GB 大小限制。

预置容量

LSI 与基础表共享预置的读取容量和写入容量。

GSI 可以独立于基础表配置预置的读取容量和写入容量。

读取一致性

支持强一致性读取和最终一致性读取。

仅支持最终一致性读取。

传统关系数据库与现代 NoSQL 数据库的一个重要区别在于事务支持。事务是关系数据库的常见内置能力，但并非所有 NoSQL 数据库都支持事务。DynamoDB 支持 事务操作，可以根据应用程序的需求使用相应的读写 API。另一个需要考虑的方面是读取一致性：DynamoDB 支持最终一致性读取和强一致性读取，但 GSI 仅支持最终一致性读取。用户可以在支持该选项的读取操作中指定所需的一致性级别。

前面介绍了 DynamoDB 如何根据分区键确定数据的物理分区，以及如何通过不同的容量模式配置表的读写吞吐量。吞吐量容量在表级别配置，并由 DynamoDB 分配给各个分区；系统还可以通过自适应容量机制调整分区之间的容量分配。单个分区每秒最多可支持约 3,000 个读取容量单位（RCU）或 1,000 个写入容量单位（WCU），也可以处理一定比例的读写混合负载。如果请求超过分区可提供的吞吐量，就可能发生限流。此外，每个物理分区的存储容量上限为 10 GB。因此，在设计数据模式时，需要结合查询模式和 DynamoDB 的分区机制，合理分布数据及访问负载。

当某个分区承受过高的访问负载时，就可能形成热分区（hot partition）；如果某个分区键值承受的读写请求远高于其他键值，则可能形成热键（hot key）。 了解应用程序的查询和访问模式，是合理设计 DynamoDB 表结构的关键。可以使用 CloudWatch Contributor Insights 分析访问频率较高或发生限流的数据项及分区键值，帮助识别热点问题。

下面介绍一些 DynamoDB 分区键设计的最佳实践，以降低出现热分区问题的风险：

  • 设计表结构时，应尽量选择基数较高的分区键，即具有较多不同取值的属性。这有助于将数据和访问负载分散到不同分区，从而改善读写性能。

  • DynamoDB API 及 AWS SDK 通常会返回包含错误信息的异常，应用程序可以据此采取相应措施。如果热分区问题只是偶尔发生，可以采用指数退避策略进行重试。对于频繁出现的热分区问题，则需要进一步分析原因，寻找更稳定的解决方案。

  • 对已有数据的表重新设计结构可能需要投入大量工作，还必须考虑数据迁移期间的停机时间和应用程序代码修改等问题。对于热分区引起的读写限流，可以考虑以下缓解措施。这些措施既可以作为临时方案，也可能根据业务场景长期使用：

    • 对于读取请求，可以考虑使用缓存（参见 #ch10_amazon_elasticache_1734552290476591 一节）来降低访问延迟，并减少直接发送到 DynamoDB 热点分区的读取请求，从而缓解热分区问题。

    • 对于写入请求，可以采用写入分片（write sharding）技术，在分区键值后附加随机或按特定规则计算的后缀，例如 1 到 100 之间的数字，以分散写入负载。采用这种方式后，读取操作需要额外的应用程序逻辑来确定应查询哪些键值：如果使用随机后缀，可能需要查询全部 100 种后缀；如果后缀可以根据规则推导，则只需查询相应的键值。

合理分析数据访问模式，有助于更充分地利用 DynamoDB，在控制成本的同时     减少运维负担。

Amazon DocumentDB

Amazon DocumentDB      是 AWS 提供的一项文档数据库服务，以类似 JSON 的文档形式存储和查询数据。文档通常由可以嵌套的键值对构成，适用于存储餐品信息等场景，例如 Cafe Delhi Heights 的线上商店。下面展示一个顾客订单的文档示例：

{
  "Name": "Mandeep Singh",
  "orderId": "1234-1234-4567",

    {
      "itemName": "Biryani",
      "qty": 1
    },
    {
      "itemName": "Nuggets",
      "qty": 2
    }

我们可以根据需要为餐品文档添加或删除属性，而不必像使用固定模式的关系数据库那样预先定义所有字段。其他业务场景还包括内容管理、实时大数据处理和用户资料维护。

DocumentDB 与 MongoDB  具有一定的兼容性，支持灵活的即席查询（ad hoc queries），也提供事务支持。与 MongoDB 相比，DocumentDB 在某些功能方面具有不同的实现特点，例如其 CRUD 操作可以提供原子性和一致性保证，包括涉及多个文档的操作。有关 MongoDB 与 DocumentDB 的具体功能差异，请参阅 AWS 文档。

AWS 还提供数据库迁移服务（AWS Database Migration Service，AWS DMS）等迁移工具，帮助将部署在本地环境或 EC2 实例上的 MongoDB 工作负载迁移到      Amazon DocumentDB。

Amazon Neptune

回到      Cafe Delhi Heights 的案例。餐厅开展线上业务时，其中一项需求是建立顾客美食社区，以记录和分析顾客对不同餐品的喜好。例如，餐厅可能希望了解某道菜是否受到社区中所有顾客的欢迎。

对于这类包含大量关联关系的数据，可以使用 AWS 的完全托管图数据库服务 Amazon Neptune 进行大规模存储和查询。Neptune 经过优化，能够存储和管理数十亿条关系，并支持以毫秒级延迟查询和遍历图数据。对于属性图，可以使用 Apache TinkerPop Gremlin 或 openCypher 进行查询；对于资源描述框架（RDF）数据，则可以使用 SPARQL。AWS 还建议参阅 GitHub 仓库 AWS Reference Architectures for Using Graph Databases，了解图数据模型、典型应用场景、查询语言和部署架构示例。

Neptune 的另一个应用场景是分析云基础设施中不同服务和资源之间的关联关系。例如，可以识别哪些实体使用了某个 IAM 角色（如 #ch10_figure_2_1734552290456078 所示），或查找可能授予过多权限的 IAM 策略，例如在资源权限中使用通配符 * 的策略。例如，我们可能不希望组织中的所有用户都拥有修改网络安全组的权限。

有关创建集群的详细步骤，请参阅 AWS 文档。下面介绍配置图数据库集群时需要注意的几个要点。

计算

创建 Neptune 集群时，需要选择相应的数据库实例类别。一个集群最多可包含一个写入实例和 15 个只读副本。写入实例可以通过纵向扩展提高处理能力，而只读副本既可以纵向扩展，也可以通过增加实例数量进行横向扩展。建议至少配置一个只读副本，以提高应用程序的可用性和读取性能。如果写入实例发生故障，Neptune 可以将符合条件的只读副本提升为新的写入实例；故障实例恢复后，也可以重新作为只读副本加入集群。如果集群只有一个写入实例且没有只读副本，在实例恢复期间，数据库服务可能中断数分钟。

Neptune 还提供无服务器配置（Neptune Serverless），适用于负载变化较大的应用程序。用户可以设置容量范围，系统会根据实际负载在该范围内自动调整计算容量。

存储

Neptune 在三个可用区中保存六份数据副本。其存储层与计算层相互独立，并可随着数据量增长自动扩展。创建集群时，系统会为存储卷分配初始的 10 GB 空间，此后按需扩展，在大多数受支持的区域中最高可达 128 TiB。

流量分发

Neptune   提供独立的写入端点和读取端点。写入端点（也称为集群端点）指向当前的主实例，主要用于写入操作，也可以用于读取查询。读取端点通过轮询方式将新的连接分配给只读副本，适合处理读取请求。Neptune 还提供实例端点 ，用于直接连接特定数据库实例，以及用于访问指定实例组的自定义端点。需要注意，读取端点并不在实例之间对每条查询进行负载均衡；如果需要更细粒度的请求分配，应由应用程序自行实现。

缓存

Neptune 提供 三种类型的缓存支持以提高性能：

缓冲区缓存

用于提高查询性能的内存缓存。Neptune 将实例内存的三分之二分配给缓存。

查找缓存

用于提高重复查找属性值或 RDF 字面量的查询读取性能的实例级缓存。对于R5d 实例（专为在内存中处理大型工作负载而构建），默认启用此缓存，并使用实例的基于 NVM Express（NVMe）的 SSD 存储这些值以实现快速访问。

查询结果缓存

Gremlin 只读查询结果可以被缓存，以便在重新运行查询时获得更快的响应。要清除缓存，可以为查询指定 TTL（生存时间）、在查询级别清除缓存，或清除     整个缓存。

亚马逊 ElastiCache

内存数据库     被广泛用作缓存解决方案，以提升系统性能。亚马逊 ElastiCache 是 AWS 提供的托管服务，作为分布式缓存环境，支持   Redis 和 Memcached 引擎，两者均在 #ch04_caching_policies_and_strategies_1734552287178593 中详细介绍。Redis 和 Memcached 都是内存键值缓存解决方案，但存在相关差异，了解哪种缓存引擎满足业务需求至关重要。Memcached 是一种简单的键值缓存解决方案，支持多线程，可有效减轻主数据源的读取压力。Redis 具备支持长期数据的持久化、高级数据类型（如列表和集合）、在内存中对数据集进行排序和排名、地理空间支持、消息代理等多种功能。以下是 ElastiCache 中每种缓存引擎的一些关键注意事项。

子网

如 #ch09_aws_network_services_1734552289953244 中所述，可用 IP 地址的数量 基于子网 CIDR。在创建集群的第一步，应创建与 Amazon VPC 关联的子网，并支持所需数量的 IP 地址，因为这些 IP 地址将分配给集群中的节点。

数据分层

数据可以 在内存和 NVMe SSD 存储之间分层以优化成本，适用于定期访问最多 20% 数据的应用程序。此功能适用于 R6gd 实例系列的 ElastiCache for Redis，当内存（DRAM）完全占用时，低频访问数据将异步移至 SSD，如 #ch10_figure_3_1734552290456102 所示。单个集群的存储可扩展至 1 PB。

Redis 和 Memcached 均可水平和垂直扩展。Redis 基于主节点和只读副本的概念，可以两种配置启动：

禁用集群模式

最多可有一个主节点和最多五个副本节点。此配置针对读取水平扩展，针对写入垂直扩展。

启用集群模式

最多可有 500 个节点，每个节点最多关联 5 个副本。

冗余与复制

ElastiCache for Redis  具有类似于 RDS 的多可用区部署支持。每当主节点出现故障，只读副本（1 到 5 个只读副本分布在不同可用区）将被提升为主节点，即使整个可用区出现故障也能确保高可用性。只读副本上的数据复制还确保了读写工作负载的分离。

多线程

Redis 是 单线程进程，按顺序处理传入请求，而 Memcached 是多线程的，能够充分利用具有多核的较大 Amazon EC2 实例。

持久化

Redis 可以作为 应用程序的独立数据库使用，因为它支持长寿命数据的持久化。Memcached 是纯粹的缓存解决方案，通常部署在数据库（如 RDS）之前充当缓存层，以提高读取性能。

加密与合规

Redis 支持 支付卡行业数据安全标准（PCI DSS）、健康保险可携带性和责任法案（HIPAA）以及 联邦风险和授权管理计划（FedRAMP）要求，并具备加密功能。Memcached 对身份验证和加密的支持不够完善，因此建议在没有公共连接的私有子网中启动 Memcached 节点，以确保更高的安全性。

有关创建集群的分步指南，请参阅 AWS Redis 和 Memcached 页面。

Amazon DynamoDB Accelerator

如前所述，  您可以使用 Memcached 或 Redis 来卸载数据库（如 RDS 或 DynamoDB）的读取查询。DynamoDB 还提供自定义内存缓存方案——DynamoDB Accelerator（DAX），以提高读取性能。DAX 是一个由主节点和只读副本组成的集群，运行在 VPC 内部，如 #ch10_figure_4_1734552290456122 所示。要访问 DAX，需要在服务器的应用程序旁边安装 DAX 客户端，将应用程序的 DynamoDB API 请求定向到 DAX 集群。

以下是在 DAX 集群和 DynamoDB 同时存在的情况下，读写 API 的执行方式：

读取 API

最终一致性读取 API 调用（GetItem、BatchGetItem、Query 和 Scan）由 DAX 提供服务。在缓存未命中的情况下，请求会传递给 DynamoDB 以检索响应。DynamoDB 返回结果时，也会将结果写入主节点上的 DAX 缓存。

写入 API

对于写入 API 调用（BatchWriteItem、UpdateItem、DeleteItem 和 PutItem），数据首先写入 DynamoDB 表，然后写入 DAX 集群。只有在 DynamoDB 和 DAX 上的写入均成功时，API 才返回成功。    

亚马逊 OpenSearch 服务

您可能    希望根据用户搜索查询向用户显示搜索结果；在 Cafe Delhi Heights 的示例中，这些搜索结果可以是食品项目、餐厅位置或任何支持的筛选条件。搜索食品项目应返回提供该餐品的所有餐厅位置，而搜索餐厅位置应显示该位置提供的所有菜肴。如何在数据库中对这类数据建模以实现更快的检索？对于这类业务使用场景，AWS 提供了搜索数据库——OpenSearch。

OpenSearch 是一个从 Elasticsearch 派生的开源项目，与大多数运行在专有软件上的 AWS 服务不同。OpenSearch 广泛用于全文搜索、日志分析、数据摄取管道和机器学习等场景。AWS 在搜索引擎之上提供 OpenSearch 控制面板，帮助可视化数据。以下是关于 OpenSearch 架构的几个关键注意事项，以及我们作为客户如何充分利用它：

集群设置

OpenSearch 可以作为单节点或多节点集群运行。由于这是一个开源项目，您也可以按照这些步骤自行设置集群。OpenSearch 是一种托管服务，帮助您避免设置的运维开销，可以基于实例（集群管理器节点和数据节点）或无服务器模式运行。AWS 建议为生产 OpenSearch 集群设置奇数个集群管理器节点，最少为三个节点。集群管理器节点的类型可以根据域中数据节点的数量来决定，例如对于 1 到 10 个数据节点，可以设置 m5.large.search 或 m6g.large.search。对于开发用途可以跳过设置专用集群管理器节点以节省成本（其中一个数据节点承担集群管理器节点的职责），但建议在生产场景中配置专用节点，以提高集群稳定性并为集群管理任务提供专用节点。

存储

您可以选择 EBS 或实例存储卷与实例关联；可用的卷类型取决于所选择的实例类型。

集群访问

对于集群访问和网络，您可以选择 VPC 访问或公共访问。VPC 访问允许您在 VPC 内运行集群，以及配置子网、安全组和 IAM 角色。

部署

OpenSearch 支持在运行中的集群上进行配置更新，例如增加 EBS 存储空间或升级实例类型。这些配置通过蓝绿部署的方式部署到新集群，以避免任何影响。建议在非高峰时段执行此类更新。

控制面板身份验证

OpenSearch 提供    通过安全断言标记语言（SAML）身份验证或 Amazon Cognito 身份验证为控制面板配置身份验证的选项。

亚马逊 Timestream

亚马逊 Timestream    是一种完全托管的无服务器数据库服务，适用于需要时序数据操作的使用场景，如 DevOps 分析数据。Timestream 自动扩展，每天可处理数万亿个事件，成本仅为关系数据库的十分之一，速度是关系数据库的一千倍。

以下是使用 Timestream 时需要注意的几点：

  • 由于 Timestream 是无服务器的，使用简单，无需分析实例数量或类型。

  • Timestream 提供内置的分析支持，包括插值和平滑函数，可使用标准 SQL 识别趋势、规律和异常。

  • 数据默认使用标准密钥或客户自有 KMS 密钥进行加密。

  • Timestream 支持基于配置时间的数据保留策略，并支持按策略将数据移至不同存储层。它支持两种存储层：内存层（适用于对延迟敏感的查询）和磁性磁盘层（适用于分析查询）。

  • 记录需要时间戳作为必填维度，存储到 Timestream 的数据无法删除或更新。数据的删除应通过配置保留策略来处理。

Amazon Keyspaces

我们在      #ch03_nonrelational_stores_1734552286860587 中讨论了宽列数据库，并了解了其开源变体 Apache Cassandra。满足类似需求的 AWS 托管解决方案是 Amazon Keyspaces。

Keyspaces 是一种高度可扩展、高可用的托管宽列数据库服务，与开源 Apache Cassandra 数据库兼容。Keyspaces 以无服务器服务形式提供，意味着您无需担心资源预置，只需专注于构建应用程序。以下是考虑使用 Keyspaces 的几个使用场景：

  • 您希望将本地 Cassandra 集群或运行在 EC2 实例上的集群迁移到完全托管的 AWS 服务。这有助于减少大量集群管理开销，例如管理部署、为工作负载找出最佳配置（如针对垃圾回收的 Java 虚拟机 (JVM) 调优）、了解 Cassandra 内部机制、为预期工作负载预置容量、升级至新版本、修补和维护集群基础设施等。

  • 您有与开源 Cassandra 兼容的业务需求。

  • 与客户自行管理相比，Keyspaces 与 AWS 服务（如用于监控的 Amazon CloudWatch 或用于身份验证的 AWS IAM）的集成更好。

由于 Keyspaces 抽象了基础设施管理，您无法访问低级别集群管理控制平面 API。Keyspaces 为表的读写工作负载提供两种类型的容量模式，类似于 DynamoDB：带自动扩展的预置容量和按需模式。Keyspaces 表中的所有数据默认加密，并在多个可用区中复制，以实现高可用性和持久性。请参阅 AWS 指南了解 Cassandra 和 Keyspaces 之间的功能       差异。
