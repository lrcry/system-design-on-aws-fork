# Chapter 5 — Technical concerns

This file records technical issues in the English source that may materially mislead readers. These are source-content concerns, not translation corrections.

## High

### 1. Incorrect OSI-layer classification of protocols

The source groups IP, TCP, FTP, and UDP as protocols handled at Layer 4. This is incorrect: IP operates at Layer 3, TCP and UDP at Layer 4, and FTP at Layer 7. The distinction matters because the chapter uses OSI layers to explain Layer 4 and Layer 7 load balancing.

**Suggested correction:** Describe Layer 4 load balancing as operating primarily on transport-layer protocols such as TCP and UDP, over IP. Mention FTP only when discussing application-layer protocol handling.

## Medium

### 2. Conflating load-balancing algorithms with session state

The source suggests that both static and dynamic load-balancing algorithms must maintain state to retain client-session information. Algorithm selection and session persistence are separate concerns. Session affinity is optional; for example, deterministic client-IP hashing can provide affinity without storing per-session state in the load balancer.

**Suggested correction:** Explain session persistence as a separate feature that can be implemented through cookies, source-IP affinity, or other mechanisms. Avoid implying that every balancing algorithm requires session state.

### 3. Overgeneralization about hash-based algorithms and server membership changes

The source says hash-based algorithms are rarely used because adding or removing servers requires remapping requests and can create uneven load. This describes a limitation of simple modulo-style hashing, but not all hash-based approaches. Consistent hashing is specifically designed to limit remapping when the server set changes.

**Suggested correction:** Qualify the statement as applying to simple hashing schemes, and briefly distinguish consistent hashing.

### 4. Incorrectly stating that Layer 4 load balancers do not terminate TCP connections

The source states that Layer 4 load balancers do not terminate TCP connections. This is not universally true. Transparent forwarding or direct-server-return designs may preserve the client-to-backend connection, while TCP proxy load balancers commonly terminate the client-side TCP connection and establish a separate backend connection.

**Suggested correction:** Explain that TCP termination depends on the load balancer's operating mode and architecture, rather than being an inherent property of Layer 4 load balancing.

### 5. Nginx health-check capabilities are presented without edition distinctions

The source describes Nginx as continuously monitoring backend health through configurable health checks. Nginx Open Source primarily provides passive health checks based on observed requests and responses. Active health checks are an Nginx Plus capability.

**Suggested correction:** Distinguish passive health checks available in Nginx Open Source from active health checks available in Nginx Plus.

### 6. Nginx configuration changes are described as automatically applied

The source implies that Nginx dynamically updates its configuration without manual intervention. Nginx Open Source typically requires a configuration reload for file-based changes to take effect (with graceful worker replacement). Dynamic upstream reconfiguration through the API is associated with Nginx Plus.

**Suggested correction:** Clarify the distinction between graceful reloads in Nginx Open Source and API-based dynamic reconfiguration in Nginx Plus.

### 7. Mischaracterizing the role of SSL/TLS certificates

The source says backend servers do not need to maintain SSL certificates for request verification when TLS is terminated at the load balancer. Certificates authenticate endpoints and help establish secure TLS connections; they are not ordinarily used to verify each application request. If traffic from the load balancer to the backend is also encrypted, backend-side TLS configuration and certificates may still be required.

**Suggested correction:** Explain that TLS termination at the load balancer can remove the need for backend servers to handle the client-facing TLS connection, but backend-to-load-balancer encryption and authentication are separate design choices.

### 8. VIP is presented as if it provides failover by itself

The source implies that packets sent to a Virtual IP (VIP) are automatically redirected to a failover machine. A VIP is an address, not a failover mechanism. High availability requires an additional mechanism—such as VRRP or an equivalent cloud/network failover capability—to transfer VIP ownership or redirect traffic when a node fails.

**Suggested correction:** State that VIP-based failover depends on a high-availability mechanism that moves or advertises the VIP from the failed node to a healthy standby node.

### 9. ECMP description risks implying per-packet distribution

The source describes hashing packet headers to select a path “for each packet” and suggests traffic is evenly distributed. In common ECMP implementations, hashing is generally performed on flow-identifying fields so packets belonging to the same flow follow the same path. Per-packet distribution can cause packet reordering, and hashing does not guarantee perfectly even traffic distribution.

**Suggested correction:** Describe flow-based hashing as the common approach, explain that it aims to distribute flows across equal-cost paths, and avoid promising an even split of bytes or packets.
