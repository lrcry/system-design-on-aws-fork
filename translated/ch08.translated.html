变更数据捕获

CDC 是   一种先进的数据集成方法，能够实时追踪并捕获源数据库中的数据变更，并将这些变更推送至各类目标系统，包括其他数据库、数据仓库或实时处理引擎。CDC 的核心价值在于它能够向组织各部门提供最新数据，从而确保所有系统始终反映最新信息。

对实时数据处理的需求促使组织纷纷采用 CDC。在数据如同石油一样宝贵的时代，拥有最新数据能够显著提升运营效率和决策能力。传统的批处理方法虽然可靠，但无法满足当今快节奏业务环境对即时性的需求。批处理往往需要安排停机时段，且在数据提取过程中会影响系统性能，不利于实现实时响应。

在需要实时分析的场景中，CDC 可将事务数据库（如 RDBMS）与数据仓库（如 Snowflake、Redshift）同步。这使得数据管道能够持续将事务系统中的最新数据推送至数仓，无需繁重的 ETL（提取、转换和加载）批处理作业即可获得最新洞察。我们将在 #ch16_designing_a_social_network_and_newsfeed_system_1734552293547861 讨论新帖创建的设计处理时，进一步深入探讨 CDC。

与批量加载相比，CDC 具有诸多优势，尤其体现在实时性能方面：

降低延迟

CDC 能够实现近乎即时的数据更新，使企业能够迅速响应变化，这对于动态定价、库存更新或个性化客户交互至关重要。

降低成本与带宽占用

CDC 仅传输上次传输后发生的变更，从而最大限度地减少所需带宽，降低数据传输相关成本。

提高系统效率

由于 CDC 在变更发生时即刻捕获，对源系统的影响极小，避免了批处理过程中密集的资源占用。

软件架构师可以使用多种技术实现 CDC，每种技术适用于不同的系统架构和性能需求：

基于审计列的 CDC

基于时间戳的审计列 是一种简单而有效的 CDC 实现方式。通过在数据库表中添加 created_at 和 updated_at 等时间戳列，可以追踪每条记录的插入或最后修改时间。这种方法特别适用于需要历史审计跟踪的应用场景，其主要优势在于简单且开销低，充分利用了大多数 RDBMS 的内置能力。

基于日志的 CDC

基于日志的 CDC  通过读取数据库维护的事务日志来运作。由于这些日志本就是为数据恢复和完整性而记录所有变更的，因此无需对数据库本身增加额外开销，是捕获数据变更的可靠来源。这种方式支持近实时的数据集成，适用于高可用系统以及需要跨平台即时一致性的场景。Debezium 等工具可以透明地与这些日志对接，将数据变更无缝传输至 Kafka 和数据库等各类数据接收端。

基于流的 CDC  是基于日志的 CDC 的扩展，它将日志数据格式化为更易于消费的流，使应用程序更容易实时处理变更。其中一个典型示例是 Amazon DynamoDB Streams，它可将 DynamoDB 表中的数据更新发布至不同的目标系统。

表快照比对法

表快照比对法 通过比较不同时间点的表快照来捕获变更。这种方式思路直接：通过定期对表进行全量快照并加以比较，即可推导出发生的变更。然而，这种方法可能引入延迟且资源消耗较大；因此，通常适用于事务量较低或不需要实时同步的系统。尽管存在上述缺点，对于资源和处理窗口规划合理的批处理场景，它仍是一种可行的选择。

基于触发器的 CDC

基于触发器的 CDC  利用数据库触发器来捕获变更，即在表中发生事件（INSERT、UPDATE、DELETE）时自动执行预定义的存储过程或 SQL 命令。这种方式可以即时捕获数据变更并进行自定义处理，便于在数据捕获阶段实现复杂的转换或即时校验。虽然这种方式灵活且能实时运行，但在大规模系统中管理数据库触发器会增加负载和复杂性。

在实际应用中，CDC 不仅是一种数据集成工具，更是企业提升数据敏捷性和可及性的整体战略的重要组成部分。随着云平台对 CDC 内置支持的日益完善，CDC 的应用也愈发便捷。组织可以借助 CDC 在分布式环境中保持数据同步更新，从而在不   引入大量开销或复杂性的前提下提升分析能力。

发布-订阅架构

发布-订阅架构    是事件驱动编程中的一种基础模型，它促进了系统各部分之间的异步通信。这种模式对于需要组件之间高效交互而无需直接关联的应用场景至关重要，从而实现了松耦合和可扩展的设计。

尽管发布-订阅架构常与观察者模式混淆，但它在设计理念和运作方式上有其独特之处。两者的核心区别在于路由机制。在观察者设计模式中，观察者了解主题对象，可以直接向其注册以接收更新。通信通常是同步的，所有观察者通过直接方法调用同时收到通知。

而发布-订阅模型则通过消息代理或事件总线将发布者与订阅者解耦，由其负责消息或事件的传递。发布者向事件通道发送消息，无需了解订阅者的详情；订阅者则监听该通道，无需知晓发布者是谁。这种设计支持异步通信，并能比观察者模式更顺畅地支持复杂的多对多交互。

发布-订阅架构涉及消息代理和消息队列，下面我们来详细了解这两个组件。

消息代理

消息代理是发布-订阅架构中的关键组件， 负责管理生产者（发布者）与消费者（订阅者）之间的消息传递。即便在复杂的分布式系统中，消息代理也能确保消息被正确路由、维护和投递。

如图 #ch08_figure_1_1734552289299606 所示，典型的消息代理架构包含用于临时存储消息的队列，以及对消息进行分类的主题。发布者将消息发送至特定主题，订阅者则注册自己感兴趣的一个或多个主题。随后，消息代理确保将相关主题的消息投递给对应的订阅者。

高级消息队列协议（AMQP）  是一种用于应用程序或组织间传递消息的开放标准，注重高互操作性和可靠性。AMQP 规定了消息提供方和消息代理的行为，以确保消息的一致性投递，因此成为需要健壮性和功能可预测性的系统的首选协议。 

消息队列

消息队列是消息基础设施的基本组成部分，  如图 #ch08_figure_1_1734552289299606 所示，它充当消息从发布者路由至订阅者过程中的临时缓冲区。

Apache Kafka 是消息队列系统的典型代表（我们将在本章最后一节详细介绍），它专为处理高数据量和支持高吞吐量应用而设计。Kafka 及类似技术充分展示了消息队列在现代系统架构中日益增强的能力，尤其在高效处理大规模实时数据流方面表现突出。

发布-订阅架构借助 Kafka 等先进消息代理和队列系统，代表了构建解耦、可扩展、高效应用的强大范式。这种架构不仅支持关注点分离，还增强了软件系统各组件之间处理异步通信的能力。这种方式在当今的分布式系统中越来越具有现实意义，因为高效可靠地管理数据流比以往任何时候都更加   关键。

编配与编排

在分布式系统（尤其是采用微服务的系统）设计中，管理服务交互的方式——即编配与编排——在定义系统行为和能力方面发挥着举足轻重的作用。

编配

编配采用  去中心化的工作流管理方式。在这种模型中，每个服务根据其消费的事件知晓自己该做什么以及何时去做，无需中央协调器；服务根据接收到的事件通知独立履行各自的职责。这种方式将服务设计为响应事件而非中央机构的直接命令，从而实现松耦合，并因服务独立运行而提升了系统的可扩展性和弹性。

缺乏中央控制器可能使得执行某些业务规则和监控整体流程变得困难。由于架构的分布式特性将日志条目和错误报告分散在各个服务中，错误处理和调试也可能变得更加复杂。

编配的一种子模式是 编配异步事件。在这种模式中，服务通过中央消息总线发布和消费事件，构建出一个松耦合的系统，使服务无需了解彼此的操作细节即可独立运行。这种模式在写操作量大的系统中尤为适用，例如 IoT 数据处理或实时通知系统。

其优势包括：因解耦特性带来的可扩展性，以及各服务可自主运行所带来的针对服务故障的弹性。然而，挑战也随之而来：由于工作流分散在多个服务中，管理整体系统状态、追踪和调试工作流变得更加困难。编排范式可以解决这些挑战。

电商平台的订单处理系统和酒店预订系统等设计问题，可以通过服务间的编配来解决。我们将在 #ch18_designing_a_hotel_reservation_system_1734552294615548 中讨论类似的预订确认和支付流程管理模式。预订系统等待客户支付，并响应 PaymentProcessed 等事件，以 BookingConfirmed 事件确认预订。此事件进一步被账单系统等其他服务用于生成发票。

编排

与编配相对，编排  依赖中央协调器（即编排器） 来控制服务间的交互，由其决定流程走向，并指示各服务何时行动。这种方式简化了业务逻辑的监控和管理，对于需要精确协调和严格遵守工作流的复杂业务流程尤为有利。由于编排器可以跟踪流程状态并据此做出决策，错误处理和恢复也得以简化。

目前有多种编排解决方案，既有开源软件，也有云服务商提供的托管服务，包括 Netflix 设计的 Conductor 和 Maestro、Temporal 工作流编排器、AWS Step Functions 以及 Apache Airflow。我们将在 #ch12_aws_messaging_orchestration_monitoring_and_acce_1734552291639018 中讨论 Step Functions 和 Airflow。

编排可能导致服务间耦合度增加，因为服务依赖中央节点进行指令调度。这也可能成为单点故障，影响系统的弹性和可扩展性。编排可以通过多种模式实现，每种模式适用于不同的工作流需求和系统架构。

视频上传功能（如 YouTube 和 Netflix）的设计问题可以通过编排平台轻松管理。工作流中的每个步骤都会调用特定服务来执行任务，例如验证、编码和分发视频。我们将在 #ch20_designing_a_video_processing_pipeline_for_a_stream_1734552295245731 中对此进行更详细的讨论。

编排式同步顺序模式

在这种 模式中，编排器以顺序方式向服务发送同步请求，在进入下一步之前等待每个响应。这种方式适用于涉及多个步骤且需要按特定顺序完成的复杂工作流，例如电商结账流程。

该模式的优势包括：集中控制便于管理复杂工作流，以及因工作流在编排器中有明确定义而便于调试。然而，系统也可能面临挑战，如编排器成为单点故障，以及任务顺序执行导致的潜在性能瓶颈。

编排式同步并行模式

与顺序方式类似，但对独立任务进行并行执行，从而提升性能、降低延迟。在可以同时调用多个服务的场景中效果显著，例如数据聚合服务。

该模式的优势包括：通过缩短工作流完成的总时长来提升性能，以及在同时涉及并行和顺序步骤的工作流管理中具有灵活性。然而，其挑战在于并行操作管理的复杂性增加，以及服务未针对并行 执行优化时可能出现的资源竞争风险。

编排式异步顺序模式

在这种 模式中，编排器发送异步请求，允许服务独立处理任务，并通过回调或消息队列返回结果。这种方式非常适合长时间运行任务的系统，其中服务无需等待响应即可继续处理，例如批处理系统。

该模式的优势包括：更好地处理长时间运行的流程而不阻塞资源，以及因服务可在失败时重试操作而提升系统弹性。然而，其挑战在于管理异步响应的复杂性增加，以及需要额外机制来处理最终一致性和故障恢复。

混合编排与编配模式

该模式 结合了编配和编排的优势：对显式工作流使用编排，对隐式的事件驱动操作使用编配。它适用于某些工作流需要严格控制、而另一些工作流受益于去中心化执行的复杂系统，例如大规模分布式应用。

在一个大型电商平台中，订单处理服务充当编排器，控制工作流的主要步骤：验证支付、预留库存、确认订单和发起配送。这种显式编排确保核心订单工作流受到严格控制，每个步骤按特定顺序执行，这对于事务完整性和可靠性至关重要。与编排核心并行的是，各类辅助服务采用去中心化的事件驱动方式。例如，当订单发货时，系统发布一个事件。通知服务和分析服务等独立服务监听此事件并各自执行任务（向客户发送通知和更新配送统计数据），无需直接协调，从而实现了灵活性和可扩展性。

该模式的优势包括：灵活处理多样化的工作流需求，以及通过同时利用集中式和去中心化方式提升系统弹性。然而，其挑战在于确保编排和编配操作之间边界清晰的复杂性，以及职责重叠导致效率低下的风险。

在编配与编排之间做出选择

选择使用  编配还是编排，很大程度上取决于具体的项目需求。编配更适合需要高可扩展性和弹性、且业务流程可通过去中心化方式有效处理的系统。编排则更适合需要跨多个服务进行严格控制和协调的复杂流程，即业务逻辑过于复杂而无法通过去中心化方式有效管理的场景。两种方式在系统设计中都有其用武之地，深入理解它们各自的优势和局限性，对于架构师设计出不仅满足当前需求、还能适应未来业务需求变化的解决方案  至关重要。

随着企业持续产生指数级增长的数据量，用于存储、处理和分析海量数据集的大数据架构策略变得愈发重要，下一节我们将对此进行深入探讨。

大数据架构

大数据架构  旨在有效应对数据的五大挑战——数据量（Volume）、速度（Velocity）、多样性（Variety）、真实性（Veracity）和价值（Value）——确保组织能够获取可操作的洞察并保持性能可扩展性。大数据架构已从传统数据库演进至大型数据仓库和数据湖。我们将根据其演进历程，介绍三种现代大数据架构模型。

Lambda 架构

Lambda 架构如图 #ch08_figure_2_1734552289299641 所示， 是一种混合数据处理模型，结合了批处理和实时处理两种方式。

该架构通过以下三个层次来处理和呈现数据，从而在延迟、吞吐量和容错性之间取得平衡：

批处理层

该层以批量方式处理大量数据，对长期存储的历史数据进行处理。它提供全面且精确的数据视图，但延迟较高。批处理层负责创建预计算视图，存储批处理的结果。

加速层

针对实时数据处理需求，加速层在数据到达时即刻处理，确保低延迟。该层通过提供及时（尽管可能是近似）的数据视图来弥补批处理层的高延迟。

服务层

最后一个组件——服务层——将批处理层和加速层的输出合并，向终端用户呈现连贯一致的结果视图。

Lambda 架构适用于既需要近实时数据视图、又需要处理无法快速处理的海量数据集的场景。批处理层和加速层这两个组件引入了额外的运营管理复杂性。这一局限性可通过 Kappa 架构来解决——Kappa 架构将两者 合并为一个统一系统。

Kappa 架构

作为 Lambda 架构的演进， Kappa 架构通过将所有传入数据视为流来简化运营复杂性。如图 #ch08_figure_3_1734552289299664 所示，该模型提出使用单一的流处理层来同时处理实时数据和历史数据。通过将所有数据视为流，Kappa 架构消除了同时维护批处理和实时处理两套独立代码库和系统的需求，从而简化了开发和维护工作。

该架构利用先进的流处理工具，能够处理时间窗口、事件排序和跨潜在无界数据集的状态管理。Kappa 架构尤其适用于输入数据天然为流式的应用，或数据时效性比复杂的计算密集型批量分析更为优先的场景。

这里的核心思想是将批处理和流处理工作负载简化为单一管道，但具体的实现和生产化方式因组织的使用场景而异。Uber 借助 Kappa 架构解决了多个问题，例如动态定价、欺诈检测和用户体验分析。通过设计单一管道并支持在批处理和流处理工作负载之间轻松切换，来应对这些不同的使用场景。

数据湖架构

数据湖是集中式存储库， 旨在存储、处理和保护大量结构化和非结构化数据。与传统数据仓库通常以结构化、经处理的格式存储数据不同，数据湖以原生格式保留海量原始数据。如图 #ch08_figure_4_1734552289299685 所示，这种方式具有若干独特优势，包括：使用低成本硬件横向扩展、灵活配置数据湖的组织结构、索引和处理逻辑，以及支持存储和分析包括日志、XML、JSON 和二进制格式在内的多种数据类型。数据湖架构不仅支持大数据存储，还与各类大数据处理框架集成，直接在存储数据上实现全面的分析和机器学习。

您也可以使用 Amazon S3 等对象存储解决方案来构建数据湖架构。S3 可与 Amazon EMR、AWS Glue 和 Amazon Athena 等大数据服务轻松集成，以运行大数据工作负载。我们将在 #ch13_big_data_analytics_and_machine_learning_services_1734552292002899 中更详细地讨论这些服务。

通过实施 Lambda、Kappa 和数据湖等大数据架构，组织可以有效管理其数据生态系统，既满足当前的分析需求，又支持未来的数据驱动计划。这确保了基础设施不仅满足大数据处理的技术要求，还与战略业务目标保持一致。

大数据架构主要关注高效处理和管理大量数据，而应用解决方案系统设计则聚焦于创建满足特定业务需求并集成各类组件的系统。下一节将对比解决方案架构设计与以数据为中心的   大数据架构方法。

解决方案架构

解决方案架构  已从单体架构演进至微服务架构，折射出技术与业务需求的变迁。本节将概述这一演进历程及相关架构，探讨其配置方式和设计背后的原则。

单体架构

在 单体架构中（如图 #ch08_figure_5_1734552289299705 所示），应用的所有组件紧密集成并作为单一服务运行。这意味着在应用任何地方做出的变更都可能影响整个系统，从而简化了产品生命周期早期阶段的开发和部署流程。

由于单体架构是单一的可执行或部署单元，因此开发、测试、部署和水平扩展都相对简单。与微服务相比，这具有显著优势，因为省去了不同微服务之间的网络交互，有助于降低延迟并更轻松地处理不稳定网络的问题。

然而，随着应用规模的增长，单体系统可能变得臃肿，难以理解和修改。对应用特定功能（而非整个应用）进行扩展也会变得具有挑战性。从可扩展性角度来看，我们建议保持代码的解耦和模块化，以便在必要时能够单独部署。即使代码部署在单一代码库中，模块化的代码架构也能让您轻松复用组件或添加新功能，并保持良好的代码可读性。下一节将更详细地描述这种 模式。

N 层架构

N 层架构将 应用分解为具有各自职责的逻辑层。通常包括至少三层：表示层（前端）、业务逻辑层（中间层）和数据管理层（后端），即三层架构，如图 #ch08_figure_6_1734552289299723 所示。

这种架构通过分离组件间的关注点来增强可维护性，使系统各部分的管理、更新和扩展更加便捷而不影响其他部分。这种架构选择提供了可扩展性和灵活性，因为每一层都可以根据需求独立扩展。例如，可以在不扩展表示层的情况下，单独扩展数据层以处理更大的数据负载。

N 层架构通过分离关注点相比单体设计有了显著改进，但现代应用往往需要更大的灵活性、可扩展性和容错能力，这正是微服务发挥作用的地方。

微服务

微服务架构 在 N 层系统原则的基础上，将其进一步分解为更小的松耦合服务，如图 #ch08_figure_7_1734552289299743 所示。每个微服务专注于单一功能，可独立开发、部署和扩展。

微服务架构提供了多种优势，也带来了一定挑战。它赋予团队独立开发、测试、部署和扩展服务的自主权，加快了开发周期并改善了故障隔离。它还支持技术多样性，使不同服务能够使用最适合其特定任务的技术栈。

然而，微服务的去中心化特性增加了管理和运营的复杂性，尤其体现在服务间通信、数据一致性和事务管理方面。此外，服务开销也可能增大，因为每个服务可能需要其自己的数据库、库和依赖项，从而增加了资源占用和管理工作量。

从单体架构向微服务架构的过渡并不适合每个项目或组织，需要在清晰认识相关权衡的前提下进行。网络延迟、消息格式、数据完整性和事务管理等问题需要 API 网关、服务网格以及全面的日志和监控系统等健壮的策略，以确保系统的可靠性和性能。通过仔细评估业务需求和团队能力，组织可以选择最合适的架构来支持其目标，确保软件基础设施既能有效满足当前需求，又能适应   未来需求。

另一种实现应用或大数据架构的有趣范式是事件驱动型架构（EDA）。

事件驱动型架构

EDA 是一种   围绕事件的产生、检测和消费来编排行为的范式。这种模型为应用提供了一个动态框架，使其能够在不紧耦合组件的情况下响应分布式系统中的各种状态变化，从而实现可扩展性和响应性。我们将从 EDA 的概念和实现范式入手，然后深入探讨事件溯源的具体细节。

EDA 的概念与实现

事件驱动系统使应用的各组件能够基于事件而非直接调用或共享状态操作进行通信。这通常通过将事件作为消息来实现，这些消息在被处理前可能会持久化存储。此类系统采用状态机方法。以下是这种方法中的主要概念：

状态机

 一种基于行为模型设计算法的数学抽象。状态机读取一组输入，并根据这些输入切换到不同的状态。

状态

 描述系统等待执行转换时的状态。

转换

 从一种状态到另一种状态的变化。转换是在满足某个条件或接收到某个事件时执行的一组动作。

事件

 驱动状态变化的实体。

事件驱动的状态机

 如果状态机从一个状态到另一个状态的转换是由事件或消息触发的（而非基于字符的消费或解析，也非基于条件判断），则该状态机是事件驱动的。

事件驱动实现的范式

EDA 的核心是实现通过发布事件而非（例如）相互进行 RPC/CRUD 调用或操作共享状态来通信的组件。这是一种通信策略（尽管往往依赖于将消息持久化存储相当长一段时间直至被消费）。EDA 的两种主要实现方式是面向状态的实现和事件溯源。

面向状态的实现

这种方法 只捕获当前状态，专注于将随时间发生的状态变更持久化。状态数据在受控范围内被视为可变，只能通过定义的操作进行修改，这使得系统具有响应性，但没有历史追踪，与当前状态条件紧密绑定。

事件溯源

与面向状态的实现不同， 事件溯源将每次状态变更持久化为不可变事件。这些事件是系统的单一事实来源，当前状态可由此重建。这种方式支持历史状态重建、审计，以及回滚和重放事件等复杂系统行为，从而处理错误或系统故障。

事件溯源支持以下能力：

完整重建

通过重放事件，使系统能够从头开始丢弃并重建状态

时序查询

通过重新处理到某一时刻为止的所有事件，查询系统在任意时间点的状态

事件重放

通过在修正事件后或添加新事件后重新处理，纠正错误

事件驱动系统 通常使用事件存储——一种以追加方式将事件按序存储的持久化机制——作为关于应用状态和数据操作的单一事实来源。事件存储确保所有事件以不可变方式被捕获，为触发动作、构建投影或重建历史状态提供可靠的基础。这些系统将数据变更与应用逻辑解耦，使系统能够更灵活地扩展并适应不断变化的业务需求。

基于事件溯源的持久化 将实体建模为事件流，并维护这些事件流的不可变日志。当实体状态或属性发生变化时，它会产生并保存一个新事件。当需要恢复实体状态时，会读取该实体的所有事件，并依次应用每个事件来改变状态，最终达到实体的正确状态。注意，此处的状态是事件流在实体上的纯函数应用结果。

在事件驱动系统中实现事件溯源时，有几个重要因素需要考虑：

最终一致性

由于创建物化视图或投影存在延迟，读操作可能无法立即反映最新写入。在事件发布到视图创建之间的时间段内，事件日志中可能已添加了新事件。

事件日志不可变性

事件日志应保持不可变，即事件一旦写入就不能更新。要更正之前的事件，必须添加新事件。任何对事件 Schema 的修改都必须一致地应用于所有已存储的事件。

事件顺序与线性

维护事件的正确顺序对于数据一致性至关重要，尤其是涉及多个发布者时。为事件添加时间戳或递增标识符有助于解决排序冲突。

消费者幂等性

由于事件可能被多次投递，消费者必须是幂等的，即能够处理重复事件而不会多次应用同一更新，否则可能导致状态变更错误。

快照与物化

定期对事件进行快照和物化是必要的，尤其是处理大型事件流时。这有助于管理按需查询，并确保对模型当前状态的高效访问。

由于应用流程的去中心化控制和事件处理的分布式特性，在构建事件驱动系统时，需要牢记这些关于最终一致性的实践考量，并妥善管理相关复杂性。

事件驱动型架构代表了从传统请求驱动模型的范式转变，提供了一种灵活、可扩展的方式来处理异步系统行为和数据流。这种架构风格尤其适合对可扩展性、响应性和健壮性要求较高的应用，例如微服务环境或需要复杂业务流程    和工作流的系统。

事件溯源和   CDC 都追踪数据变更，但服务于不同目的。事件溯源将所有变更捕获为可随时间重建或还原系统状态的事件，本质上将事件作为事实来源。相比之下，CDC 主要专注于捕获数据库中的变更以进行数据复制或集成，利用数据库的事务日志记录状态变更，但不会固有地存储变更的意图或上下文。

常见云架构模式

在本节  中，我们将探讨构成云环境中可扩展、高弹性、可维护系统基础的核心云架构模式。这些模式——从断路器等弹性技术到 Saga 编排等事务处理策略——将为您提供基础性工具，在 #part3 所呈现的系统设计用例中尤为重要。理解这些模式将使您更有能力将经过验证的健壮解决方案应用于分布式架构中的常见挑战，为做出有效的设计决策奠定基础。

基于事件的模式：CQRS 与 Saga

基于事件的架构利用以下模式来管理分布式事务和操作：

命令查询责任分离（CQRS）

CQRS 是  一种将读取数据的操作（查询）与更新数据的操作（命令）分离到不同接口的架构模式。这种分离允许读写操作以不同方式处理，从而优化性能、可扩展性和安全性。例如，读模型可以独立于写模型进行扩展，这在读操作数量远超写操作数量的系统中尤为有益。

Saga

Saga 模式管理 跨多个服务的事务，其中每个事务步骤都与一个补偿操作配对，以便在需要时进行回滚。Saga 基于编配或编排来实现。在编配方式下，参与 Saga 的每个服务执行其事务并发布触发其他服务后续步骤的事件。在编排方式下，中央协调器（编排器）指导 Saga 的每个步骤，管理执行顺序并在必要时触发补偿事务。

这些模式在需要跨微服务管理分布式事务的环境中至关重要，为可靠、高效地处理复杂操作提供了结构化框架。

容错模式：断路器、带退避的重试与限流器

为提升 系统在面对故障时的弹性，可采用以下模式：

断路器

 断路器模式防止分布式系统中的级联故障。当某个服务或操作的失败次数达到阈值时，断路器"跳闸"，对故障服务的进一步调用将被暂时中止，从而使其得以恢复并维持系统稳定性。

带退避的重试

带退避的重试 涉及以递增的延迟重新尝试失败的操作，每次重试都逐步增加间隔（退避），直到达到最大重试次数。这种模式在处理瞬时故障时特别有用，它为问题的解决提供了等待时间，然后再进行重试。

限流器

限流器模式 控制在指定时间段内对服务的请求数量，防止系统被大量流量或突发需求压垮。限流可以在多个层面应用：按用户、按服务或在系统层面全局应用。这种模式确保服务即使在高负载下也能平稳运行，降低因资源耗尽导致性能下降或系统崩溃的可能性。

这些模式协同工作，防止分布式系统中的级联故障，确保系统某一部分的故障不会导致大面积停机。

领域模式：领域驱动设计与按子域分解

以下 模式专注于使软件设计与业务目标保持一致：

领域驱动设计（DDD）

DDD 专注于  核心领域逻辑及其复杂性，将设计建立在领域的行为和逻辑之上。这种模式鼓励创建融入业务规则和行为的领域模型，从而在软件与其所要实现的业务需求之间建立更直观的关联。

按子域分解

按子域分解 在微服务架构中以 DDD 为基础， 将系统划分为多个子域，每个子域处理特定的业务能力。每个微服务管理一个子域，通过允许微服务根据其独特的业务需求独立演进，提升了可维护性和可扩展性。

这些模式对于构建可随业务需求变化而演进的模块化、可扩展系统至关重要。

API 路由策略与模式

API 路由模式 决定了请求在云环境中如何被定向至相应服务。这些模式对于确保请求高效、安全地到达正确的后端系统至关重要。常见的路由策略包括：

主机名路由

这种 策略根据 URL 中的主机名将请求路由至不同的后端系统。常用于多个服务托管在不同子域或域名下的场景。

路径路由

这种 路由模式使用 URL 路径将请求定向至特定服务或处理程序。它基于 URL 的结构提供清晰、有序的路由，使服务的管理和扩展更加便捷。

HTTP 标头路由

在 这种方式中，利用请求中的 HTTP 标头来做出路由决策。这对于 A/B 测试（将不同用户群定向至不同后端服务）或新功能的灰度发布等场景特别有用。

在基于微服务的系统中，API 路由架构采用 API 网关或服务网格：

API 网关

API 网关 充当所有客户端请求的集中入口点，向一组后端服务提供统一接口。它处理请求路由、组合和协议转换等任务。API 网关可以调用多个微服务来满足单个客户端请求，并将响应聚合为连贯的结果。这种模式在微服务架构中尤为有用，因为它通过集中访问控制和监控简化了客户端交互并增强了安全性。

服务网格

服务网格架构 是一个管理微服务架构内服务间通信的基础设施层。它提供高级路由、负载均衡、服务发现以及相互传输层安全（TLS）认证和流量加密等安全特性。与处理外部客户端到服务通信的 API 网关不同，服务网格专注于内部服务间交互，确保云环境内可靠、安全的通信。它通过边车代理实现，边车代理拦截并管理服务间的网络流量，在无需修改应用代码的情况下提供可观测性和弹性。

这些 API 路由策略和模式，以及 API 网关和服务网格架构，是构建可扩展、安全、可维护的云原生 应用的基础。

其他云架构模式

除上述核心模式外，还有若干云架构模式针对特定挑战并增强系统设计：

防腐层

 防腐层（ACL）作为保护屏障，防止潜在的破坏性数据或请求进入系统的某个部分，从而保护应用核心业务模型的完整性。它充当不同子系统或外部应用之间的翻译器，确保数据交换不会破坏领域模型。

绞杀者模式

该模式 用于通过将特定功能逐步替换为新应用和服务来渐进式改造遗留系统。随着时间推移，这些新组件"绞杀"旧系统，最终完全取而代之。

事务性发件箱

 事务性发件箱模式用于确保服务间的可靠消息传递。当数据库发生变更时，记录同样会在同一事务内被添加到"发件箱"表中。随后，一个独立的进程将这些消息发送至消息队列或其他目标，确保跨服务边界的数据一致性。

边车模式

边车模式 常用于微服务架构。它涉及在服务容器旁部署额外的容器或进程，提供监控、日志记录、配置和网络能力等平台连接服务。边车可以用任何语言编写，与主容器之间没有强依赖性，从而实现解耦。这种模式将基础设施关注点与应用隔离，使应用更简洁、更模块化。

前端专属后端（BFF）

该模式  涉及为不同类型的客户端（如桌面浏览器和移动设备）创建专属的后端服务。它允许开发者针对特定用户界面优化这些后端服务，通过减少数据过度获取或获取不足来提升用户体验。

单元式架构

单元式架构 涉及将系统设计为单元（cell）的集合，每个单元独立运行但可以与其他单元通信。每个单元都是自包含的，拥有自己的数据存储和逻辑，能够自主扩展。这种方式具有高度弹性，因为一个单元的故障不会影响其他单元；同时它支持演进式架构，允许每个单元独立演进。

这些模式分别为开发和管理云原生应用时遇到的常见问题提供有针对性的解决方案，有助于构建更具弹性、灵活性和可扩展性的系统架构。需要注意的是，这里列出的架构模式并不全面；随着系统设计技术不断发展，新的模式也会持续涌现。尽管如此，这些模式仍能为你在设计复杂系统时面临的各种架构挑战提供可靠的解决方案。  

开源分布式系统架构

   分布式系统架构将系统的不同职责分配给多个计算节点，以提升系统的可扩展性、容错能力和运行效率。本节将介绍两类核心组件：分布式文件系统和分布式消息队列，重点讨论它们的开源实现，分别以 HDFS 和 Kafka 为代表。

HDFS

      HDFS 是一种面向通用商用硬件设计的开源文件系统，能够在成本较低的硬件设备上运行，并具有较强的容错能力。它支持以高吞吐量访问应用程序数据，适用于需要处理大规模数据集的应用。HDFS 的主要特性包括：

分布式存储

HDFS 在设计上注重可扩展性，通过将数据分布到集群中的多个节点来实现分布式存储。它把大文件拆分为多个数据块，并在不同机器上保存这些数据块的副本，从而提供数据冗余，并在发生硬件故障时维持数据的可用性。

容错性

HDFS 的一项关键特性是其内置的容错能力。系统会自动复制数据，通常将副本存储在三个不同的节点上。这样，即使其中一个节点发生故障，仍可通过其他节点访问数据。这种副本机制提高了系统的可靠性和可用性，使 HDFS 非常适合大规模数据存储。

可扩展性与灵活性

HDFS 可以通过向集群添加节点来实现横向扩展，从而在无需大幅调整现有基础设施的情况下，存储和管理不断增长的数据量。这种可扩展性，加上对多种数据格式的支持，使 HDFS 能够灵活地满足不同的数据处理需求。

高吞吐量

HDFS 针对高吞吐量进行了优化，更注重大规模数据读写的整体处理效率，而不是单次访问的低延迟。它面向大型数据集设计，尤其适合批处理场景，因此非常适用于需要读写海量数据的大数据应用。

成本效益

通过使用通用商用硬件，HDFS 能够以较低的成本存储和处理海量数据。

与 Hadoop 生态系统的集成

 HDFS 与 Hadoop 生态系统紧密集成，支持 MapReduce、Hive 和 Spark 等多种数据处理框架。借助这种集成，系统可以利用 HDFS 的分布式架构，尽可能在靠近数据存储位置的节点上执行计算，从而减少网络传输瓶颈，提高数据处理和分析的效率。

  AWS 提供 Amazon EMR（Amazon Elastic MapReduce）托管服务，帮助用户更便捷地在 AWS 云上运行 Hadoop 等大数据框架，包括使用 HDFS 进行存储。我们将在 #ch13_big_data_analytics_and_machine_learning_services_1734552292002899 中进一步介绍。Amazon EMR 支持使用 HDFS 或 EMRFS 处理海量数据，并利用其可扩展性、容错能力以及与 Hadoop 生态系统的集成优势。

HDFS 架构

如图 #ch08_figure_8_1734552289299761 所示，HDFS 由多个关键组件构成。这些组件相互协作，共同实现文件系统的分布式存储、容错和可扩展能力。

HDFS 架构主要包含以下组件：

NameNode（名称节点）

 NameNode 是 HDFS 的核心组件，负责管理文件系统的元数据和命名空间。它记录文件的存储位置，并通过协调各个 DataNode 上的数据存储来管理文件访问。NameNode 对 HDFS 的正常运行至关重要；如果 NameNode 发生故障，文件系统可能无法访问。

DataNode（数据节点）

 DataNode 是 HDFS 中负责存储数据的工作节点，保存组成文件的实际数据块。每个 DataNode 都会定期向 NameNode 发送心跳信号和数据块报告，使 NameNode 能够及时了解各节点的运行状态、数据块信息以及数据的可用情况。

辅助 NameNode

 尽管名称中带有“Secondary”，但辅助 NameNode 并不是 NameNode 的备用节点。它与 NameNode 协同工作，主要负责定期将文件系统的元数据镜像与编辑日志合并，生成新的检查点。这有助于减少 NameNode 故障恢复时需要处理的编辑日志数量，从而缩短恢复时间。

数据块

 HDFS 将文件划分为多个数据块进行存储，每个数据块的大小通常为 128 MB。为实现数据冗余，系统通常会将每个数据块的副本分布在三个不同的 DataNode 上。这种基于数据块的存储方式使 HDFS 能够高效处理大文件，并在某个 DataNode 发生故障时，通过其他副本继续提供数据访问。

当客户端需要读取或写入文件时，会先与 NameNode 通信，以确定相关数据块的存储位置或目标 DataNode。对于写操作，NameNode 会向客户端返回用于存储数据块的 DataNode 列表。随后，客户端将数据写入指定的 DataNode，数据块再按照 NameNode 确定的副本放置策略复制到其他节点。

HDFS 具备机架感知能力，能够识别数据中心中各节点所属的机架。NameNode 利用这些信息制定数据块的副本放置策略，将副本分布在不同机架上，以提高系统的容错能力。这样，即使某个机架发生故障，系统仍有机会通过其他机架上的副本访问数据，从而降低数据丢失的风险。

HDFS 通过数据块复制以及 NameNode 对节点状态的定期监测来实现容错。如果某个 DataNode 发生故障，NameNode 会协调将受影响的数据块重新复制到其他节点，以恢复所需的副本数量并维持数据可用性。

这些组件和特性共同构成了一个高度可靠且可扩展的分布式文件系统，使 HDFS 成为 Hadoop 生态系统的核心组成部分。HDFS 的架构能够支持在数千个节点组成的集群中存储和读取海量数据，因此非常适合大数据应用。

HDFS 是 Hadoop 生态系统的重要组成部分，为大数据处理提供关键的存储能力。不过，在评估大数据解决方案时，也应考虑其他平台。Hadoop 生态系统提供了用于管理和处理大型数据集的丰富开源工具，而 AWS 等云平台则提供托管服务，有助于简化系统部署和扩展。接下来，我们将对比 Hadoop 生态系统与 AWS，重点介绍二者的区别、优势及适用场景。

Apache Kafka：分布式消息队列

      Apache Kafka 是一个开源的分布式事件流平台，能够实时处理海量事件，处理规模可达每天数万亿个事件。作为一种可靠且可扩展的消息系统，Kafka 的处理吞吐量可达到每秒数百万条记录，因此适用于事件驱动架构、实时分析以及复杂的数据管道。Kafka 的主要特性包括：

可扩展性

Kafka 通过分区机制将数据分布到多个节点上，从而实现横向扩展。这种架构支持高吞吐量，能够处理大规模数据。

持久性与可靠性

Kafka 通过将消息持久化存储到磁盘，并在多个 Broker 之间保存副本，来提高数据的持久性和可靠性。这种复制机制有助于降低单个 Broker 故障导致数据丢失的风险。

容错性

Kafka 在设计上具备容错能力。当某个 Broker 发生故障时，Kafka 可以利用数据复制机制，由其他 Broker 接管受影响分区的服务，以尽可能维持数据可用性并降低数据丢失的风险。

高吞吐量

Kafka 针对高吞吐量进行了优化，处理能力可达到每秒数百万条记录。因此，它非常适合构建实时数据管道和事件驱动架构。

Kafka 架构

图 #ch08_figure_9_1734552289299781 展示了 Kafka 的架构及其主要组件。

下面进一步介绍这些组件：

生产者

 生产者负责将数据（记录）发布到 Kafka 主题中。生产者将记录发送给 Kafka Broker，由 Broker 在集群内存储数据，并按照复制机制维护数据副本。

消费者

 消费者负责从 Kafka 主题中读取记录。它们可以订阅一个或多个主题，并按照各个分区内记录的存储顺序进行消费。

Schema Registry

 Schema Registry 是一项用于管理 Kafka 生产者和消费者所使用的数据模式（Schema），并根据配置执行模式兼容性检查的服务。它有助于规范数据格式，并在数据结构不断演进的过程中，减少不同版本之间的兼容性问题。

Broker

 Kafka Broker 是负责数据持久化存储和副本管理的服务器。每个 Broker 都会存储一个或多个分区的数据。分区是 Kafka 实现横向扩展的基本单位，通过将不同分区分布到多个 Broker 上，Kafka 可以扩展数据存储和处理能力。

协调器

  过去，Kafka 使用 ZooKeeper 协调集群中的 Broker，负责分区 Leader 选举、集群配置及元数据管理等工作。此后，Kafka 引入了 Apache Kafka Raft（KRaft） 机制，取代 ZooKeeper 承担集群元数据管理和一致性协调职责。

主题

 Kafka 主题（Topic）是用于组织和发布记录的逻辑类别。一个主题可以划分为多个分区，使数据能够分布在不同的 Broker 上。每个分区都包含按顺序排列、写入后不可修改的记录，这些记录会持续追加到分区日志中。

分区

 Kafka 通过将主题划分为多个分区，支持对主题中的记录进行并行处理。不同分区可以分布在不同的 Broker 上，使 Kafka 能够横向扩展并处理海量数据。分区也是 Kafka 进行数据复制的基本单位，有助于提高数据的持久性和容错能力。

键

 在 Kafka 中，记录的键（Key）是决定其目标分区的重要依据。生产者发送记录时，可以为其指定一个键。Kafka 通常使用该键及哈希函数，将记录映射到特定分区。这样，具有相同键的记录通常会被发送到同一分区，从而有助于保持这些记录的顺序。

Kafka 将消息按顺序追加到各个分区的日志中。如果生产者先向同一分区发送消息 M1，再发送 M2，那么在顺序得到正确保障的情况下，M1 的偏移量将小于 M2，因此会在日志中排在 M2 之前。需要注意的是，这种顺序保证仅适用于单个分区内部。用户可以根据数据的分区方式，利用分区内的顺序保证来处理不同的数据集合。

Kafka 的主要配置参数

 Kafka 提供多种配置参数，可根据具体需求对系统进行调整和优化：

复制因子

复制因子决定 Kafka 为每个分区维护多少个副本，并将这些副本分布在不同的 Broker 上。较高的复制因子能够增强容错能力，但也会占用更多的存储空间和网络资源。

确认机制

生产者可以配置 Broker 在何种条件下确认消息已成功写入。例如，设置 acks=all 时，需要满足同步副本（in-sync replicas）的确认要求，Broker 才会向生产者返回成功响应。这种设置通常可以提高消息写入的可靠性，但也可能增加写入延迟。

保留策略

Kafka 支持配置主题中记录的保留策略，例如按时间（如七天）或按数据量（如 100 GB）设置保留限制。这些策略有助于控制历史数据占用的存储空间，提高存储资源的管理效率。

压缩

Kafka 通过消息压缩减少网络传输的数据量以及磁盘空间占用。用户可以根据具体场景选择不同的压缩算法，例如 gzip、snappy 和 lz4。

 Kafka 提供多种消息投递语义，用于控制消息在分布式系统中的传递方式及其可靠性。这些机制对于维护复杂数据管道中的数据一致性和完整性具有重要意义：

最多一次投递

 在最多一次投递语义下，每条消息最多投递给消费者一次。消息可能丢失，但不会因失败而重新投递。通常需要通过相应的重试、确认和消费位置管理方式来实现这种语义。

至少一次投递

 在至少一次投递语义下，系统会尝试确保每条消息至少到达消费者一次。即使发生故障，也可以通过重试等机制完成投递，但同一条消息可能被重复投递。这种语义适用于需要尽量避免消息丢失、且应用程序能够处理重复消息的场景。为避免重复消息产生不必要的影响，消费者应在消息处理逻辑中实现幂等性。

 如果某个操作执行多次与执行一次产生的结果相同，就称该操作具有幂等性。例如，消费者可以记录已处理的消息 ID，以识别重复消息并避免再次处理。这样可以降低重复消息造成意外副作用的风险，帮助应用程序保持数据完整性。

精确一次投递

  Kafka 的精确一次语义（EOS）旨在使每条消息的处理结果只生效一次，即使发生故障，也能够在支持的处理流程中避免重复结果。这一机制依赖幂等生产者和事务 API，使跨多个分区和主题的相关操作能够以原子方式提交。对于金融交易等高度重视数据完整性的应用场景，EOS 尤其有价值。

Kafka 支持多种消息投递语义，并具备较强的容错能力和可扩展性，因此是构建分布式数据流处理系统的可靠选择。凭借低延迟处理大规模数据流的能力，Kafka 已成为现代分布式系统中的一项基础技术。

   AWS 提供 Amazon Managed Streaming for Apache Kafka（Amazon MSK）和 Amazon Kinesis 等用于实时数据流处理的托管服务。Amazon MSK 简化了在 AWS 上部署和运行 Apache Kafka 的工作，而 Amazon Kinesis 则提供用于采集、处理和分析流数据的服务。这两类服务都有助于构建可扩展、可靠的数据流处理系统。我们将在 #ch12_aws_messaging_orchestration_monitoring_and_acce_1734552291639018 中进一步介绍。

结语

本章介绍的架构设计与模式为构建可扩展、易于维护且高效的系统提供了丰富的思路和方法。变更数据捕获（CDC）有助于在分布式环境中同步数据变更，使不同系统中的数据保持更新；发布—订阅架构则支持系统组件之间的解耦通信。Lambda 架构、Kappa 架构和数据湖等大数据架构与技术，为处理和分析海量数据提供了有效的方法。此外，Kafka 和 HDFS 也是分布式系统中的重要基础技术，分别擅长实时事件流处理和大规模数据存储。
