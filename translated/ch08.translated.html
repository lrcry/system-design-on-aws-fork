架构设计与模式

   本章将深入探讨架构设计与模式。这些架构模型和设计模式构成了现代软件系统的基础。我们将介绍它们如何帮助不同类型的应用实现可扩展性、可维护性和高效的数据处理。本章不仅将帮助你掌握相关理论基础，也将启发你在系统设计实践中运用这些知识并探索创新方案。

本章首先介绍变更数据捕获（CDC），这是一项用于捕获数据库中数据变更的关键数据架构技术。接下来，我们将讨论异步通信模式中的发布—订阅架构。在这种架构中，发布者无需知道订阅者的身份，就可以发布事件。我们还将介绍消息代理和消息队列如何管理不同系统之间的数据流，并重点探讨 Apache Kafka 这一高吞吐量的分布式消息系统，说明其架构以及处理大规模数据流的应用场景。

在分布式系统中，如何管理服务之间的交互至关重要。本章将探讨现代云环境中用于构建可扩展、具有弹性且易于维护的系统的关键架构模式。我们将比较编配（choreography，去中心化）与编排（orchestration，集中化）两种管理方式，并分析各自的适用场景。随后，我们将介绍大数据架构，包括 Lambda 架构、Kappa 架构和数据湖架构等基础模型，以及用于处理海量数据集的 Hadoop 分布式文件系统（HDFS）。我们还将比较单体架构、N 层架构和微服务架构，并进一步探讨事件驱动系统如何通过响应实时事件，实现解耦服务之间的通信。

本章最后将介绍一系列重要的云架构模式，包括断路器等提升系统弹性的技术，以及 Saga 编排等事务处理策略，为设计健壮的系统提供一套实用工具。本章介绍的架构模式也将作为设计蓝图，帮助我们应对 #part3 中讨论的各种系统设计场景。

变更数据捕获

   CDC 是一种数据集成技术，通过实时跟踪和捕获源数据库中的数据变更，并将这些变更推送到不同的目标系统，例如其他数据库、数据仓库或实时处理引擎。CDC 的核心价值在于能够为组织的不同部门提供最新数据，从而确保各个系统反映最新的信息。

实时数据处理的需求推动了 CDC 的应用。在数据价值堪比石油的时代，及时获取最新数据能够显著提高运营效率和决策能力。传统的批处理方式虽然可靠，却难以满足当今快节奏业务环境对数据时效性的要求。批处理通常需要安排停机时间，而且在提取数据时可能影响系统性能，因此不利于实现实时响应。

当组织需要进行实时分析时，可以利用 CDC 将事务型数据库（如关系型数据库管理系统 RDBMS）与数据仓库（如 Snowflake、Redshift）进行同步。这样，数据管道便可以持续将事务系统中的最新数据推送到数据仓库，无需依赖资源消耗较大的 ETL（提取、转换和加载）批处理作业，也能获得最新的分析结果。第 16 章在讨论新帖发布功能的系统设计时，我们将进一步介绍 CDC。

与批量加载相比，CDC 具有诸多优势，尤其体现在实时性能方面：

降低延迟

CDC 能够实现近乎即时的数据更新，让企业快速响应变化。这对于动态定价、库存信息更新以及个性化客户互动等场景至关重要。

降低成本与带宽占用

CDC 只传输自上次传输以来发生的数据变更，从而尽可能减少带宽占用，并降低数据传输成本。

提高系统效率

CDC 在数据变更发生时便将其捕获，对源系统的影响很小，从而避免了批处理过程通常伴随的高资源消耗。

软件架构师可以采用多种技术来实现 CDC，不同技术适用于不同的系统架构和性能要求：

基于审计列的 CDC

 使用时间戳审计列是一种简单而有效的 CDC 实现方式。在数据库表中添加 `created_at` 和 `updated_at` 等时间戳列后，便可以追踪每条记录的创建时间和最近一次修改时间。这种方式特别适用于需要保留历史变更审计记录的应用场景。它的主要优势是实现简单、开销较低，因为可以利用大多数关系型数据库管理系统（RDBMS）自身提供的功能。

基于日志的 CDC

 基于日志的 CDC 通过读取数据库维护的事务日志来捕获数据变更。这些日志原本用于记录数据变化，以支持数据恢复并保障数据完整性，因此可以作为可靠的变更数据来源，而无需给数据库本身带来额外开销。这种方式支持近实时数据集成，适用于高可用系统，以及需要跨平台即时保持数据一致性的场景。Debezium 等工具可以直接对接这些日志，将数据变更持续传输到 Kafka、数据库等不同类型的数据接收端。

 基于流的 CDC 是基于日志的 CDC 的一种扩展方式，它将日志数据转换为更便于消费的数据流，使应用程序能够更轻松地实时处理数据变更。Amazon DynamoDB Streams 就是一个例子，它可以将 DynamoDB 表中的数据更新发布到不同的目标系统。

表快照比对法

 表快照比对法通过比较数据库表在不同时间点的快照，识别其中的数据变更。其原理很简单：定期获取整张表的完整快照，再比较不同快照之间的差异，就可以推导出发生了哪些变更。不过，这种方式可能带来较高的延迟和资源开销，因此更适合事务量较低，或对实时同步要求不高的系统。尽管存在这些局限，只要合理规划系统资源和处理时间窗口，它仍然适用于批处理场景。

基于触发器的 CDC

 基于触发器的 CDC 利用数据库触发器捕获数据变更。当数据库表发生 `INSERT`、`UPDATE` 或 `DELETE` 操作时，触发器会自动执行预先定义的存储过程或 SQL 命令。这种方式能够即时捕获和处理数据变更，并支持在数据捕获阶段进行复杂的数据转换或即时校验。虽然这种方式灵活性较高，能够实时捕获变更，但管理数据库触发器可能增加系统负载和复杂性，尤其是在大规模系统中。

在实际应用中，CDC 不仅是一种数据集成工具，也是企业提升数据敏捷性和可访问性的整体战略的一部分。随着越来越多的云平台提供内置的 CDC 支持，采用这项技术也变得更加简单便捷。组织可以利用 CDC，使分布式环境中的数据保持更新，从而在不增加大量额外开销或复杂性的情况下提升数据分析能力。   

发布—订阅架构

   发布—订阅架构是事件驱动编程中的一种基础模型，用于实现系统不同组件之间的异步通信。这种模式使组件无需直接建立联系，也能高效地交换信息，从而实现松耦合、易于扩展的系统设计。

发布—订阅架构经常与观察者模式混为一谈，但两者在设计理念和运行机制上有所不同。它们的核心区别在于消息的路由方式。在观察者模式中，观察者知道被观察对象是谁，并可以直接向该对象注册，以便接收更新通知。通信通常是同步的，所有观察者都会通过直接的方法调用同时收到通知。

相比之下，发布—订阅模型通过消息代理或事件总线，将发布者与订阅者解耦，并由消息代理或事件总线负责传递消息或事件。发布者向事件通道发送消息，无需知道订阅者的具体信息；订阅者则监听该通道，也无需知道消息由谁发布。这种方式支持异步通信，并且比观察者模式更容易处理复杂的多对多交互。

发布—订阅架构涉及消息代理和消息队列，接下来我们将进一步了解这两个组件。

消息代理

 消息代理是发布—订阅架构中的关键组件，负责管理生产者（发布者）与消费者（订阅者）之间的消息传递。即使在复杂的分布式系统中，消息代理也能确保消息得到妥善路由、管理和投递。

如图 #ch08_figure_1_1734552289299606 所示，典型的消息代理架构包括用于临时存储消息的队列，以及用于对消息进行分类的主题。发布者向特定主题发送消息，订阅者则订阅自己感兴趣的一个或多个主题。随后，消息代理负责将相关主题中的消息投递给相应的订阅者。

  高级消息队列协议（AMQP）是一项用于应用程序或组织之间交换消息的开放标准，强调互操作性和可靠性。AMQP 对消息提供方和消息代理的行为作出了规范，以确保消息投递的一致性，因此受到重视系统健壮性和行为可预测性的应用的青睐。 

消息队列

  消息队列是消息传递基础设施的重要组成部分。如图 #ch08_figure_1_1734552289299606 所示，它用于临时存放等待从发布者传递给订阅者的消息。

Apache Kafka 是消息队列系统的一个典型代表，我们将在本章最后一节详细介绍。它专为处理海量数据而设计，能够支持高吞吐量的应用。Kafka 及类似技术展示了消息队列在现代系统架构中不断发展的能力，尤其是在高效处理大规模实时数据流方面。

借助 Kafka 等先进的消息代理和队列系统，发布—订阅架构为构建松耦合、可扩展且高效的应用程序提供了一种有效的模式。这种架构不仅有助于实现关注点分离，还能改善软件系统中不同组件之间的异步通信能力。在现代分布式系统中，这种方式变得越来越重要，因为高效、可靠地管理数据流比以往任何时候都更加关键。   

编配与编排

在设计分布式系统，尤其是基于微服务的系统时，如何管理服务之间的交互至关重要。编配与编排是两种主要的管理方式，对系统的行为和能力具有重要影响。

编配

  编配采用去中心化的工作流管理方式。在这种模式下，每个服务根据自己接收到的事件，决定需要执行什么操作以及何时执行。系统中没有中央协调器，各个服务根据收到的事件通知独立完成各自的任务。由于服务响应的是事件，而不是来自中央协调器的直接命令，这种方式有助于实现松耦合。服务的独立运行也提升了系统的可扩展性和弹性。

由于缺少中央控制器，某些业务规则可能难以统一执行，整个工作流也更难监控。此外，由于这种架构具有分布式特性，日志记录和错误报告分散在不同的服务中，使错误处理和问题排查也可能变得更加复杂。

 编配的一种子模式是编配异步事件。在这种模式下，各个服务通过中央消息总线发布和消费事件，从而实现松耦合。服务之间无需了解彼此的具体操作，也能够独立运行。这种模式特别适用于写入操作量较大的系统，例如物联网（IoT）数据处理系统或实时通知系统。

编配的优势在于，服务之间的解耦有助于提高系统的可扩展性，而各个服务能够独立运行，也使系统在面对服务故障时更具弹性。不过，这种方式也带来了挑战。由于工作流分布在多个服务中，整体系统状态更难管理，工作流的追踪和问题排查也更加复杂。编排模式可以解决这些问题。

电商平台的订单处理和酒店预订等系统设计问题，都可以通过服务之间的编配来解决。我们将在第 18 章讨论一种类似的模式，用于管理预订确认和支付流程。预订系统等待客户完成支付，并在收到 `PaymentProcessed` 等事件后，通过发布 `BookingConfirmed` 事件确认预订。随后，账单系统等其他服务可以利用该事件生成发票。

编排

   与编配不同，编排依赖中央协调器，也就是编排器，来管理服务之间的交互。编排器负责决定工作流的执行顺序，并指示不同服务何时执行相应操作。这种方式简化了业务逻辑的监控和管理，尤其适用于需要精确协调、严格遵循工作流的复杂业务流程。此外，编排器可以跟踪流程状态并据此作出决策，因此也使错误处理和故障恢复变得更加容易。

编排解决方案有很多，包括开源软件以及云服务提供商推出的托管服务。例如，Netflix 设计的 Conductor 和 Maestro、Temporal 工作流编排器、AWS Step Functions 和 Apache Airflow。我们将在第 12 章进一步介绍 Step Functions 和 Airflow。

由于各个服务需要依赖中央协调器的指令，编排可能增加服务之间的耦合程度。中央协调器也可能成为单点故障，进而影响系统的弹性和可扩展性。编排可以采用多种实现模式，以适应不同的工作流需求和系统架构。

对于 YouTube 和 Netflix 等平台上的视频上传功能，可以借助编排平台来管理相关的系统设计流程。工作流中的每个步骤都会调用相应的服务来完成特定任务，例如视频验证、编码和分发。我们将在第 20 章中对此进行更详细的讨论。

编排式同步顺序执行模式

 在这种模式下，编排器按顺序向各个服务发送同步请求，等待当前请求的响应后，再进入下一步。这种方式适用于包含多个步骤、且必须按照特定顺序执行的复杂工作流，例如电商平台的结账流程。

这种模式的优势在于集中式控制使复杂工作流更易于管理，而编排器中明确的工作流定义也有助于调试。不过，这种模式也存在一定挑战，例如编排器可能成为单点故障，以及任务顺序执行可能造成性能瓶颈。

编排式同步并行执行模式

这种模式与顺序执行模式相似，但会并行执行彼此独立的任务，从而提高性能并降低延迟。它适用于能够同时调用多个服务的场景，例如数据聚合服务。

这种模式通过缩短工作流的整体执行时间来提升性能，同时也能灵活管理包含并行和顺序步骤的工作流。不过，并行操作的管理更加复杂，如果服务没有针对并行执行进行优化，还可能出现资源争用的问题。 

编排式异步顺序执行模式

 在这种模式下，编排器向各个服务发送异步请求，使服务能够独立处理任务，并通过回调或消息队列返回结果。这种方式特别适用于包含长时间运行任务的系统，例如批处理系统。在这类系统中，服务无需等待响应便可以继续处理任务。

这种模式能够更好地处理长时间运行的工作流，避免阻塞资源。同时，由于服务可以在操作失败后进行重试，系统的弹性也得到提升。不过，管理异步响应会更加复杂，而且还需要额外的机制来处理最终一致性和故障恢复。

混合编排与编配模式

 这种模式结合了编配与编排各自的优势：对于明确规定的工作流，采用编排方式；对于隐式的事件驱动操作，则采用编配方式。当复杂系统中的部分工作流需要严格控制，而其他工作流更适合去中心化执行时，这种模式就非常适用，例如在大规模分布式应用中。

在大型电商平台中，订单处理服务充当编排器，负责控制工作流的主要步骤，包括验证支付、预留库存、确认订单和发起配送。这种明确的编排方式确保核心订单处理流程受到严格控制，各个步骤按照特定顺序执行，从而保障事务的完整性和可靠性。与此同时，各类辅助服务采用去中心化的事件驱动方式。例如，当订单发货时，系统会发布一个事件。通知服务和分析服务等独立服务监听该事件，并分别执行各自的任务，例如向客户发送通知、更新配送统计数据。这些服务无需直接协调，从而提高了系统的灵活性和可扩展性。

这种模式能够灵活应对不同的工作流需求，并通过结合集中式和去中心化两种方式提升系统弹性。不过，它也带来了新的挑战：如何明确划分编排操作与编配操作之间的边界，以及如何避免职责重叠导致效率下降。

在编配与编排之间做出选择

  选择编配还是编排，很大程度上取决于项目的具体需求。对于需要较高可扩展性和弹性，且业务流程能够通过去中心化方式有效管理的系统，编配通常更为合适。对于需要跨多个服务进行严格控制与协调、业务逻辑又过于复杂而难以通过去中心化方式有效管理的流程，编排则是更好的选择。这两种方式在系统设计中各有其适用场景。架构师只有充分理解它们各自的优势和局限性，才能设计出既满足当前需求，又能够适应未来业务需求和流程变化的解决方案。  

随着企业产生的数据量持续呈指数级增长，如何通过大数据架构来存储、处理和分析这些海量数据，变得越来越重要。下一节将进一步介绍相关架构策略。

大数据架构

  大数据架构旨在有效应对数据的五个 V 所代表的挑战：数据量（Volume）、速度（Velocity）、多样性（Variety）、真实性（Veracity）和价值（Value），帮助组织从数据中获得可付诸行动的洞察，同时保持系统的性能和可扩展性。大数据架构从传统数据库逐步演进，发展出大型数据仓库和数据湖等形式。接下来，我们将结合这一演进过程，介绍三种现代大数据架构模型。

Lambda 架构

 如图 #ch08_figure_2_1734552289299641 所示，Lambda 架构是一种结合了批处理与实时处理的混合数据处理模型。

该架构通过以下三个层次来处理和呈现数据，从而在延迟、吞吐量和容错性之间取得平衡：

批处理层

批处理层负责批量处理大量数据，包括长期积累的历史数据。它能够提供全面、准确的数据视图，但处理延迟较高。该层还负责生成预计算视图，用于存储批处理的结果。

加速层

为满足实时数据处理需求，加速层在数据到达时立即进行处理，以实现低延迟。它通过提供及时的数据视图来弥补批处理层延迟较高的不足，不过这些视图可能只是近似结果。

服务层

作为架构的最后一个组成部分，服务层整合批处理层和加速层的输出，并向最终用户提供统一的结果视图。

Lambda 架构适用于既需要近实时数据视图，又需要处理无法在短时间内完成处理的海量数据集的场景。不过，同时维护批处理层和加速层会增加运营管理的复杂性。Kappa 架构可以解决这一局限，它将两者合并为一个统一的系统。 

Kappa 架构

 Kappa 架构是在 Lambda 架构基础上发展而来的一种架构，通过将所有传入的数据作为数据流处理，降低运营管理的复杂性。如图 #ch08_figure_3_1734552289299664 所示，该架构使用单一的流处理层，同时处理实时数据和历史数据。由于所有数据都通过流处理方式进行处理，因此无需分别维护批处理和实时处理两套独立的代码库及系统，从而简化了开发和维护工作。

Kappa 架构利用先进的流处理工具，能够在可能无限增长的数据集上处理时间窗口、事件顺序和状态管理等问题。对于输入数据本身就是流式数据的应用，或者数据时效性比复杂、计算密集型的批量分析更为重要的场景，Kappa 架构尤其适用。

这种架构的核心思想是将批处理和流处理工作负载整合到一条统一的数据处理管道中，但具体的实现方式和生产环境部署方案会因组织的应用场景而异。Uber 利用 Kappa 架构解决了多种问题，例如动态行程定价、欺诈检测和用户体验分析。通过设计统一的处理管道，并支持在批处理和流处理工作负载之间灵活切换，Uber 能够满足这些不同场景的需求。

数据湖架构

 数据湖是一种集中式数据存储库，用于存储、处理和保护海量结构化与非结构化数据。传统数据仓库通常以经过处理的结构化格式存储数据，而数据湖则以原生格式保留大量原始数据。如图 #ch08_figure_4_1734552289299685 所示，这种架构具有多项优势：可以利用低成本硬件实现横向扩展，灵活配置数据湖的组织方式、索引和处理逻辑，并支持存储和分析多种类型的数据，包括日志、XML、JSON 和二进制格式。数据湖架构不仅能够存储海量数据，还可以与各种大数据处理框架集成，直接对所存储的数据进行全面分析和机器学习。

你也可以使用 Amazon S3 等对象存储服务来构建数据湖架构。Amazon S3 可以方便地与 Amazon EMR、AWS Glue 和 Amazon Athena 等大数据服务集成，以运行大数据工作负载。我们将在第 13 章中进一步介绍这些服务。

通过采用 Lambda 架构、Kappa 架构和数据湖架构等大数据架构，组织可以有效管理自身的数据生态系统，既满足当前的数据分析需求，也为未来的数据驱动型业务计划提供支持。这能够确保基础设施不仅符合大数据处理的技术要求，也与企业的战略业务目标保持一致。

大数据架构主要关注如何高效处理和管理海量数据，而应用解决方案的系统设计则侧重于构建满足特定业务需求、整合不同组件的系统。下一节将比较解决方案架构设计与以数据为中心的大数据架构方法。   

解决方案架构

  解决方案架构从单体架构逐步演进到微服务架构，反映了技术发展和业务需求的变化。本节将回顾这一演进过程，介绍相关架构的组织方式及其背后的设计原则。

单体架构

 如图 #ch08_figure_5_1734552289299705 所示，在单体架构中，软件应用的所有组件紧密集成，并作为单一服务运行。这意味着应用中任何部分的变更都可能影响整个系统，而这种架构在产品生命周期的早期阶段通常有助于简化开发和部署流程。

由于单体应用作为单一的可执行程序或部署单元运行，因此其开发、测试、部署和水平扩展都相对简单。与微服务架构相比，这是一项显著优势，因为单体架构不需要通过网络在不同微服务之间进行通信，从而有助于降低延迟，也更容易应对网络不稳定带来的问题。

然而，随着应用规模不断增长，单体系统可能变得臃肿，难以理解和修改。此外，要单独扩展应用中的特定功能，而不是扩展整个应用，也可能变得更加困难。从可扩展性的角度来看，我们建议保持代码的解耦和模块化，以便在必要时能够将各个模块独立部署。即使所有代码都集中存放在同一个代码仓库中，模块化的代码架构仍有助于复用组件、添加新功能，并保持良好的代码可读性。下一节将进一步介绍这种模式。 

N 层架构

 N 层架构将应用程序划分为多个逻辑层，每一层都有明确的职责。典型的三层结构包括表示层（前端）、业务逻辑层（中间层）和数据管理层（后端）。这种结构称为三层架构，如图 #ch08_figure_6_1734552289299723 所示。

这种架构通过将不同的职责分配给不同组件，提高了系统的可维护性，使各个部分更容易独立管理、更新和扩展，而不会影响其他部分。由于每一层都可以根据需求独立扩展，这种架构还具有良好的可扩展性和灵活性。例如，为了应对更大的数据负载，可以单独扩展数据层，而不必同时扩展表示层。

与单体架构相比，N 层架构通过分离不同组件的职责，在系统设计方面带来了显著改进。不过，现代应用往往需要更高的灵活性、可扩展性和容错能力，而微服务架构正是为了满足这些需求而发挥作用。

微服务

 如图 #ch08_figure_7_1734552289299743 所示，微服务架构进一步发展了 N 层架构的设计原则，将系统拆分为规模更小、彼此松耦合的服务。每个微服务专注于一项特定功能，并且可以独立开发、部署和扩展。

微服务架构既有多项优势，也面临一些挑战。它使各个团队能够自主开展服务的开发、测试和部署工作，而各个服务也可以独立扩展。这有助于缩短开发周期并提高故障隔离能力。此外，微服务架构还支持采用多种技术，使不同服务可以根据各自的需求选择最合适的技术栈。

不过，微服务的去中心化特性也增加了系统管理和运维的复杂性，尤其是在服务间通信、数据一致性和事务管理方面。此外，由于每个服务可能需要独立的数据库、软件库和依赖项，服务本身的开销也可能增加，进而占用更多资源并加大运维工作量。

从单体架构迁移到微服务架构，并不一定适合所有项目或组织，因此需要充分了解其中的权衡取舍。要妥善应对网络延迟、消息格式、数据完整性和事务管理等问题，需要采取完善的技术策略，例如使用 API 网关、服务网格，以及全面的日志记录和监控系统，以保障系统的可靠性和性能。组织应仔细评估业务需求和团队能力，选择最适合自身目标的架构，使软件基础设施既能满足当前需求，也能适应未来的变化。   

事件驱动架构（EDA）是另一种值得关注的架构范式，可用于构建应用系统或大数据系统。

事件驱动架构

   EDA 是一种以事件的产生、检测和消费为中心来组织系统行为的架构范式。它为应用程序提供了一种动态机制，使各个组件无需紧密耦合，就能够响应分布式系统中的各种状态变化，从而提高系统的可扩展性和响应能力。我们将首先介绍 EDA 的基本概念和实现范式，再深入探讨事件溯源的具体机制。

EDA 的概念与实现

在事件驱动系统中，应用程序的各个组件通过事件进行通信，而不是依赖直接调用或对共享状态的操作。这通常通过将事件作为消息传递来实现，消息也可能被持久化保存，直到得到处理。这类系统会采用状态机方法。下面介绍这种方法涉及的主要概念：

状态机

 状态机是一种数学抽象模型，可用于根据行为模型设计算法。它接收一组输入，并根据这些输入转换到相应的状态。

状态

 描述系统当前所处的状况，此时系统可以等待触发条件，以执行状态转换。

转换

 指系统从一种状态转变为另一种状态。当满足特定条件或接收到某个事件时，系统会执行相应的一组动作，以完成状态转换。

事件

 触发状态变化的事件或信号。

事件驱动状态机

 如果状态机的状态转换由事件或消息触发，而不是由字符的读取或解析、条件判断等机制直接驱动，那么它就是事件驱动状态机。

事件驱动架构的实现范式

EDA 的核心是让组件通过发布事件进行通信，而不是依赖组件之间的直接 RPC/CRUD 调用或对共享状态的操作。这是一种通信策略，虽然它通常会依赖消息的持久化存储，而且消息可能需要保存较长时间才能被消费。EDA 主要有两种实现方式：面向状态的实现和事件溯源。

面向状态的实现

 这种方法只记录系统的当前状态，重点在于持久化保存状态随时间发生的变化。状态数据可以在受控范围内修改，但必须通过预先定义的操作进行。这种方式有助于系统及时响应状态变化，但若没有另外保存历史记录，系统就无法追踪过去的状态变化。

事件溯源

 与面向状态的实现不同，事件溯源将每一次状态变化记录为不可变事件，并持久化存储。这些事件构成系统的事实来源，可用于重建当前状态。这种方式支持重建历史状态、执行审计，以及通过状态回滚和事件重放等复杂操作来应对错误或系统故障。

事件溯源支持以下能力：

完整重建

通过重放事件，系统可以丢弃现有状态，并从头重新构建系统状态

时序查询

通过重新处理截至指定时刻发生的所有事件，查询系统在该时间点的状态

事件重放

在修正已有事件或添加新事件后，通过重新处理事件来纠正错误

 事件驱动系统通常使用事件存储作为应用状态和数据操作的单一事实来源。事件存储是一种针对按顺序存储事件而优化的仅追加式持久化机制。它以不可变的方式保存所有事件，为触发操作、构建投影以及重建历史状态提供可靠的基础。这类系统将数据变更与应用逻辑解耦，使系统能够更灵活地扩展，并适应不断变化的业务需求。

 事件溯源持久化机制将实体表示为事件流，并为这些事件流维护不可变日志。当实体的状态或属性发生变化时，系统会生成并保存一个新事件。如果需要恢复实体的状态，系统会读取与该实体相关的所有事件，再依次应用这些事件，逐步重建出实体的最终状态。需要注意的是，这里的状态是将事件流作为纯函数应用于实体后得到的结果。

在事件驱动系统中实现事件溯源时，有几个重要因素需要考虑：

最终一致性

由于物化视图或投影的生成可能存在延迟，读取结果可能无法立即反映最新写入的数据。在事件发布之后、相应视图生成之前，事件日志中可能已经追加了新的事件。

事件日志的不可变性

事件日志应保持不可变，也就是说，事件一旦写入，就不能再修改。若要纠正之前的事件，必须追加一个新事件。对事件 Schema 所做的任何修改，都必须一致地应用于所有已存储的事件。

事件顺序与线性

保证事件按照正确的顺序处理，对维持数据一致性至关重要，尤其是在存在多个事件发布者的情况下。为事件添加时间戳或递增的标识符，有助于解决事件顺序冲突。

消费者幂等性

由于同一个事件可能被重复投递，消费者必须具备幂等性，即使多次收到同一事件，也不会重复应用相同的更新，从而避免错误的状态变化。

快照与物化

定期创建快照并对事件数据进行物化处理十分重要，尤其是在处理规模庞大的事件流时。这有助于提高按需查询的效率，并确保能够快速访问模型的当前状态。

由于应用程序的工作流采用去中心化控制方式，且事件处理具有分布式特性，因此在设计事件驱动系统时，需要充分考虑上述与最终一致性相关的实际问题，并妥善应对由此带来的复杂性。

事件驱动架构标志着从传统请求驱动模型向事件驱动模型的范式转变，为处理异步系统行为和数据流提供了一种灵活且可扩展的方式。这种架构风格尤其适用于对可扩展性、响应能力和健壮性要求较高的应用，例如微服务环境，以及需要处理复杂业务流程和工作流的系统。    

  事件溯源和 CDC 都用于追踪数据变化，但两者的目的不同。事件溯源将状态变化记录为事件，并以这些事件作为事实来源，使系统能够通过事件重建或恢复不同时刻的状态。相比之下，CDC 主要捕获数据库中发生的变更，用于数据复制或集成。它利用数据库事务日志记录状态变化，但这些记录本身不一定包含变更背后的意图或业务上下文。

常见云架构模式

  本节将介绍一些重要的云架构模式，它们是构建可扩展、高弹性且易于维护的云端系统的基础。这些模式涵盖断路器等提高系统弹性的技术，以及 Saga 编排等事务处理策略，为解决分布式系统中的常见问题提供了基础工具。在 #part3 介绍的系统设计案例中，这些模式尤其有用。理解它们有助于你将经过实践验证的可靠方案应用于分布式架构中的常见挑战，并做出更合理的设计决策。

基于事件的模式：CQRS 与 Saga

基于事件的架构可以采用以下模式来管理分布式事务及相关操作：

命令查询职责分离（CQRS）

  CQRS 是一种架构模式，它将读取数据的查询操作与更新数据的命令操作分离，并通过不同的接口处理。这样一来，系统就可以针对读操作和写操作采用不同的处理方式，从而优化性能、可扩展性和安全性。例如，读模型可以独立于写模型进行扩展，对于读取请求远多于写入请求的系统，这一点尤其有益。

Saga

 Saga 模式用于管理跨多个服务的事务。每个事务步骤都配有相应的补偿操作，以便在必要时撤销其影响。Saga 可以通过编配或编排两种方式实现。在编配方式下，参与 Saga 的各个服务分别执行自己的事务，并发布事件来触发其他服务的后续步骤。在编排方式下，中央协调器（编排器）负责协调 Saga 的各个步骤、控制执行顺序，并在必要时触发补偿事务。

在需要协调多个微服务、管理分布式事务的系统中，这些模式具有重要作用，为可靠、高效地处理复杂操作提供了结构化的解决方式。

容错模式：断路器、带退避的重试与限流器

 为增强系统应对故障时的弹性，可以采用以下模式：

断路器

 断路器模式用于防止分布式系统中发生级联故障。当某个服务或操作的失败情况达到设定阈值时，断路器就会“跳闸”，暂时阻止对故障服务的后续调用，为该服务恢复提供时间，并帮助维持系统稳定。

带退避的重试

 带退避的重试模式会在操作失败后再次尝试，并逐步延长相邻两次重试之间的等待时间，直到达到最大重试次数。这种模式特别适合处理瞬时故障，因为延长重试间隔能够为故障恢复留出时间，避免过早再次尝试。

限流器

 限流器模式通过控制指定时间段内向服务发送的请求数量，防止系统因流量过大或请求量突然激增而不堪重负。限流可以在不同层级实施，例如针对单个用户、单项服务，或在整个系统范围内统一限流。这种模式有助于服务在高负载下保持稳定运行，并降低资源耗尽导致性能下降或系统崩溃的风险。

这些模式相互配合，有助于防止分布式系统发生级联故障，避免系统局部故障演变为大范围服务中断。

基于领域的模式：领域驱动设计与按子域分解

 以下模式旨在使软件设计与业务目标保持一致：

领域驱动设计（DDD）

  DDD 关注核心业务领域的逻辑及其复杂性，并以该领域的行为和业务逻辑为基础开展设计。这种模式提倡建立包含业务规则和行为的领域模型，使软件设计能够更直观地反映其所要满足的业务需求。

按子域分解

 在微服务架构中，按子域分解模式以 DDD 为基础，将系统划分为多个子域，每个子域负责特定的业务能力。每个微服务负责一个子域，从而能够根据该子域的业务需求独立演进，提高系统的可维护性和可扩展性。

这些模式对于构建模块化、可扩展且能够随业务需求变化而持续演进的系统至关重要。

API 路由策略与模式

 API 路由模式决定了在云环境中如何将请求转发到相应的服务。这些模式有助于确保请求能够高效、安全地到达正确的后端系统。常见的路由策略包括：

路径路由

 这种路由模式根据 URL 路径，将请求转发到特定的服务或请求处理程序。它利用 URL 的路径结构组织路由规则，使服务更易于管理和扩展。

HTTP 标头路由

在微服务架构中，API 路由通常涉及 API 网关或服务网格：

API 网关

 API 网关作为客户端请求的统一入口，为访问多个后端服务提供一致的接口。它负责请求路由、请求组合和协议转换等任务。API 网关可以针对一个客户端请求调用多个微服务，并将这些服务的响应整合为统一的结果。这种模式特别适合微服务架构，因为它既能简化客户端与后端服务之间的交互，又能通过集中管理访问控制和监控来增强安全性。

服务网格

 服务网格是一个基础设施层，用于管理微服务架构中各服务之间的通信。它提供高级路由、负载均衡和服务发现等功能，以及双向 TLS 身份认证、流量加密等安全能力。API 网关主要处理外部客户端与服务之间的通信，而服务网格则侧重于内部服务之间的交互，以保障云环境中服务通信的可靠性和安全性。服务网格通过边车代理拦截和管理服务间的网络流量，无需修改应用程序代码即可提供可观测性和故障恢复能力。

这些 API 路由策略与模式，以及 API 网关和服务网格架构，为构建可扩展、安全且易于维护的云原生应用提供了重要基础。 

其他云架构模式

除上述核心模式外，还有一些云架构模式可用于应对特定挑战，并进一步优化系统设计：

防腐层

 防腐层（ACL）充当一道保护屏障，防止可能造成干扰的数据或请求影响系统内部组件，从而维护应用程序核心业务模型的完整性。它在不同子系统或外部应用程序之间发挥转换和适配作用，避免数据交换破坏领域模型。

绞杀者模式

 这种模式通过使用新的应用程序或服务逐步替换遗留系统中的部分功能，实现对旧系统的渐进式改造。随着越来越多的功能被新组件接管，旧系统会逐步被取代，最终实现完全替换。

事务性发件箱

 事务性发件箱模式用于保障服务之间的可靠消息传递。当应用程序在数据库中进行数据变更时，会在同一个数据库事务中将相应的消息记录写入“发件箱”表。随后，由一个独立的进程将这些消息发送到消息队列或其他目标系统，从而帮助维护跨服务的数据一致性。

边车模式

 边车模式常用于微服务架构。它通过在主服务容器旁部署额外的容器或进程，为应用程序提供监控、日志记录、配置管理和网络通信等基础设施能力。边车组件可以使用不同的编程语言实现，而不必与主服务在实现技术上紧密耦合。这种模式有助于将基础设施相关的职责与应用程序本身分离，使应用程序的结构更加清晰、模块化程度更高。

前端专属后端（BFF）

  这种模式为不同类型的客户端（例如桌面浏览器和移动设备）分别构建专用的后端服务。开发人员可以根据不同用户界面的需求优化相应的后端服务，减少数据获取过多或不足的情况，从而改善用户体验。

单元式架构

 单元式架构将系统划分为多个独立的单元（cell）。各单元可以独立运行，同时又能够与其他单元通信。每个单元都是自包含的，拥有独立的数据存储和业务逻辑，并且可以单独扩展。这种架构具有较强的弹性，因为某个单元发生故障时，其他单元仍可继续运行。此外，各单元还可以独立演进，从而支持系统架构的持续演化。

这些模式分别为开发和管理云原生应用时遇到的常见问题提供有针对性的解决方案，有助于构建更具弹性、灵活性和可扩展性的系统架构。需要注意的是，这里列出的架构模式并不全面；随着系统设计技术不断发展，新的模式也会持续涌现。尽管如此，这些模式仍能为你在设计复杂系统时面临的各种架构挑战提供可靠的解决方案。  

开源分布式系统架构

   分布式系统架构将系统的不同职责分配给多个计算节点，以提升系统的可扩展性、容错能力和运行效率。本节将介绍两类核心组件：分布式文件系统和分布式消息队列，重点讨论它们的开源实现，分别以 HDFS 和 Kafka 为代表。

HDFS

      HDFS 是一种面向通用商用硬件设计的开源文件系统，能够在成本较低的硬件设备上运行，并具有较强的容错能力。它支持以高吞吐量访问应用程序数据，适用于需要处理大规模数据集的应用。HDFS 的主要特性包括：

分布式存储

HDFS 在设计上注重可扩展性，通过将数据分布到集群中的多个节点来实现分布式存储。它把大文件拆分为多个数据块，并在不同机器上保存这些数据块的副本，从而提供数据冗余，并在发生硬件故障时维持数据的可用性。

容错性

HDFS 的一项关键特性是其内置的容错能力。系统会自动复制数据，通常将副本存储在三个不同的节点上。这样，即使其中一个节点发生故障，仍可通过其他节点访问数据。这种副本机制提高了系统的可靠性和可用性，使 HDFS 非常适合大规模数据存储。

可扩展性与灵活性

HDFS 可以通过向集群添加节点来实现横向扩展，从而在无需大幅调整现有基础设施的情况下，存储和管理不断增长的数据量。这种可扩展性，加上对多种数据格式的支持，使 HDFS 能够灵活地满足不同的数据处理需求。

高吞吐量

HDFS 针对高吞吐量进行了优化，更注重大规模数据读写的整体处理效率，而不是单次访问的低延迟。它面向大型数据集设计，尤其适合批处理场景，因此非常适用于需要读写海量数据的大数据应用。

成本效益

通过使用通用商用硬件，HDFS 能够以较低的成本存储和处理海量数据。

与 Hadoop 生态系统的集成

 HDFS 与 Hadoop 生态系统紧密集成，支持 MapReduce、Hive 和 Spark 等多种数据处理框架。借助这种集成，系统可以利用 HDFS 的分布式架构，尽可能在靠近数据存储位置的节点上执行计算，从而减少网络传输瓶颈，提高数据处理和分析的效率。

  AWS 提供 Amazon EMR（Amazon Elastic MapReduce）托管服务，帮助用户更便捷地在 AWS 云上运行 Hadoop 等大数据框架，包括使用 HDFS 进行存储。我们将在 #ch13_big_data_analytics_and_machine_learning_services_1734552292002899 中进一步介绍。Amazon EMR 支持使用 HDFS 或 EMRFS 处理海量数据，并利用其可扩展性、容错能力以及与 Hadoop 生态系统的集成优势。

HDFS 架构

如图 #ch08_figure_8_1734552289299761 所示，HDFS 由多个关键组件构成。这些组件相互协作，共同实现文件系统的分布式存储、容错和可扩展能力。

HDFS 架构主要包含以下组件：

NameNode（名称节点）

 NameNode 是 HDFS 的核心组件，负责管理文件系统的元数据和命名空间。它记录文件的存储位置，并通过协调各个 DataNode 上的数据存储来管理文件访问。NameNode 对 HDFS 的正常运行至关重要；如果 NameNode 发生故障，文件系统可能无法访问。

DataNode（数据节点）

 DataNode 是 HDFS 中负责存储数据的工作节点，保存组成文件的实际数据块。每个 DataNode 都会定期向 NameNode 发送心跳信号和数据块报告，使 NameNode 能够及时了解各节点的运行状态、数据块信息以及数据的可用情况。

辅助 NameNode

 尽管名称中带有“Secondary”，但辅助 NameNode 并不是 NameNode 的备用节点。它与 NameNode 协同工作，主要负责定期将文件系统的元数据镜像与编辑日志合并，生成新的检查点。这有助于减少 NameNode 故障恢复时需要处理的编辑日志数量，从而缩短恢复时间。

数据块

 HDFS 将文件划分为多个数据块进行存储，每个数据块的大小通常为 128 MB。为实现数据冗余，系统通常会将每个数据块的副本分布在三个不同的 DataNode 上。这种基于数据块的存储方式使 HDFS 能够高效处理大文件，并在某个 DataNode 发生故障时，通过其他副本继续提供数据访问。

当客户端需要读取或写入文件时，会先与 NameNode 通信，以确定相关数据块的存储位置或目标 DataNode。对于写操作，NameNode 会向客户端返回用于存储数据块的 DataNode 列表。随后，客户端将数据写入指定的 DataNode，数据块再按照 NameNode 确定的副本放置策略复制到其他节点。

HDFS 具备机架感知能力，能够识别数据中心中各节点所属的机架。NameNode 利用这些信息制定数据块的副本放置策略，将副本分布在不同机架上，以提高系统的容错能力。这样，即使某个机架发生故障，系统仍有机会通过其他机架上的副本访问数据，从而降低数据丢失的风险。

HDFS 通过数据块复制以及 NameNode 对节点状态的定期监测来实现容错。如果某个 DataNode 发生故障，NameNode 会协调将受影响的数据块重新复制到其他节点，以恢复所需的副本数量并维持数据可用性。

这些组件和特性共同构成了一个高度可靠且可扩展的分布式文件系统，使 HDFS 成为 Hadoop 生态系统的核心组成部分。HDFS 的架构能够支持在数千个节点组成的集群中存储和读取海量数据，因此非常适合大数据应用。

HDFS 是 Hadoop 生态系统的重要组成部分，为大数据处理提供关键的存储能力。不过，在评估大数据解决方案时，也应考虑其他平台。Hadoop 生态系统提供了用于管理和处理大型数据集的丰富开源工具，而 AWS 等云平台则提供托管服务，有助于简化系统部署和扩展。接下来，我们将对比 Hadoop 生态系统与 AWS，重点介绍二者的区别、优势及适用场景。

Apache Kafka：分布式消息队列

      Apache Kafka 是一个开源的分布式事件流平台，能够实时处理海量事件，处理规模可达每天数万亿个事件。作为一种可靠且可扩展的消息系统，Kafka 的处理吞吐量可达到每秒数百万条记录，因此适用于事件驱动架构、实时分析以及复杂的数据管道。Kafka 的主要特性包括：

可扩展性

Kafka 通过分区机制将数据分布到多个节点上，从而实现横向扩展。这种架构支持高吞吐量，能够处理大规模数据。

持久性与可靠性

Kafka 通过将消息持久化存储到磁盘，并在多个 Broker 之间保存副本，来提高数据的持久性和可靠性。这种复制机制有助于降低单个 Broker 故障导致数据丢失的风险。

容错性

Kafka 在设计上具备容错能力。当某个 Broker 发生故障时，Kafka 可以利用数据复制机制，由其他 Broker 接管受影响分区的服务，以尽可能维持数据可用性并降低数据丢失的风险。

高吞吐量

Kafka 针对高吞吐量进行了优化，处理能力可达到每秒数百万条记录。因此，它非常适合构建实时数据管道和事件驱动架构。

Kafka 架构

图 #ch08_figure_9_1734552289299781 展示了 Kafka 的架构及其主要组件。

下面进一步介绍这些组件：

生产者

 生产者负责将数据（记录）发布到 Kafka 主题中。生产者将记录发送给 Kafka Broker，由 Broker 在集群内存储数据，并按照复制机制维护数据副本。

消费者

 消费者负责从 Kafka 主题中读取记录。它们可以订阅一个或多个主题，并按照各个分区内记录的存储顺序进行消费。

Schema Registry

 Schema Registry 是一项用于管理 Kafka 生产者和消费者所使用的数据模式（Schema），并根据配置执行模式兼容性检查的服务。它有助于规范数据格式，并在数据结构不断演进的过程中，减少不同版本之间的兼容性问题。

Broker

 Kafka Broker 是负责数据持久化存储和副本管理的服务器。每个 Broker 都会存储一个或多个分区的数据。分区是 Kafka 实现横向扩展的基本单位，通过将不同分区分布到多个 Broker 上，Kafka 可以扩展数据存储和处理能力。

协调器

  过去，Kafka 使用 ZooKeeper 协调集群中的 Broker，负责分区 Leader 选举、集群配置及元数据管理等工作。此后，Kafka 引入了 Apache Kafka Raft（KRaft） 机制，取代 ZooKeeper 承担集群元数据管理和一致性协调职责。

主题

 Kafka 主题（Topic）是用于组织和发布记录的逻辑类别。一个主题可以划分为多个分区，使数据能够分布在不同的 Broker 上。每个分区都包含按顺序排列、写入后不可修改的记录，这些记录会持续追加到分区日志中。

分区

 Kafka 通过将主题划分为多个分区，支持对主题中的记录进行并行处理。不同分区可以分布在不同的 Broker 上，使 Kafka 能够横向扩展并处理海量数据。分区也是 Kafka 进行数据复制的基本单位，有助于提高数据的持久性和容错能力。

键

 在 Kafka 中，记录的键（Key）是决定其目标分区的重要依据。生产者发送记录时，可以为其指定一个键。Kafka 通常使用该键及哈希函数，将记录映射到特定分区。这样，具有相同键的记录通常会被发送到同一分区，从而有助于保持这些记录的顺序。

Kafka 将消息按顺序追加到各个分区的日志中。如果生产者先向同一分区发送消息 M1，再发送 M2，那么在顺序得到正确保障的情况下，M1 的偏移量将小于 M2，因此会在日志中排在 M2 之前。需要注意的是，这种顺序保证仅适用于单个分区内部。用户可以根据数据的分区方式，利用分区内的顺序保证来处理不同的数据集合。

Kafka 的主要配置参数

 Kafka 提供多种配置参数，可根据具体需求对系统进行调整和优化：

复制因子

复制因子决定 Kafka 为每个分区维护多少个副本，并将这些副本分布在不同的 Broker 上。较高的复制因子能够增强容错能力，但也会占用更多的存储空间和网络资源。

确认机制

生产者可以配置 Broker 在何种条件下确认消息已成功写入。例如，设置 acks=all 时，需要满足同步副本（in-sync replicas）的确认要求，Broker 才会向生产者返回成功响应。这种设置通常可以提高消息写入的可靠性，但也可能增加写入延迟。

保留策略

Kafka 支持配置主题中记录的保留策略，例如按时间（如七天）或按数据量（如 100 GB）设置保留限制。这些策略有助于控制历史数据占用的存储空间，提高存储资源的管理效率。

压缩

Kafka 通过消息压缩减少网络传输的数据量以及磁盘空间占用。用户可以根据具体场景选择不同的压缩算法，例如 gzip、snappy 和 lz4。

 Kafka 提供多种消息投递语义，用于控制消息在分布式系统中的传递方式及其可靠性。这些机制对于维护复杂数据管道中的数据一致性和完整性具有重要意义：

最多一次投递

 在最多一次投递语义下，每条消息最多投递给消费者一次。消息可能丢失，但不会因失败而重新投递。通常需要通过相应的重试、确认和消费位置管理方式来实现这种语义。

至少一次投递

 在至少一次投递语义下，系统会尝试确保每条消息至少到达消费者一次。即使发生故障，也可以通过重试等机制完成投递，但同一条消息可能被重复投递。这种语义适用于需要尽量避免消息丢失、且应用程序能够处理重复消息的场景。为避免重复消息产生不必要的影响，消费者应在消息处理逻辑中实现幂等性。

 如果某个操作执行多次与执行一次产生的结果相同，就称该操作具有幂等性。例如，消费者可以记录已处理的消息 ID，以识别重复消息并避免再次处理。这样可以降低重复消息造成意外副作用的风险，帮助应用程序保持数据完整性。

精确一次投递

  Kafka 的精确一次语义（EOS）旨在使每条消息的处理结果只生效一次，即使发生故障，也能够在支持的处理流程中避免重复结果。这一机制依赖幂等生产者和事务 API，使跨多个分区和主题的相关操作能够以原子方式提交。对于金融交易等高度重视数据完整性的应用场景，EOS 尤其有价值。

Kafka 支持多种消息投递语义，并具备较强的容错能力和可扩展性，因此是构建分布式数据流处理系统的可靠选择。凭借低延迟处理大规模数据流的能力，Kafka 已成为现代分布式系统中的一项基础技术。

   AWS 提供 Amazon Managed Streaming for Apache Kafka（Amazon MSK）和 Amazon Kinesis 等用于实时数据流处理的托管服务。Amazon MSK 简化了在 AWS 上部署和运行 Apache Kafka 的工作，而 Amazon Kinesis 则提供用于采集、处理和分析流数据的服务。这两类服务都有助于构建可扩展、可靠的数据流处理系统。我们将在 #ch12_aws_messaging_orchestration_monitoring_and_acce_1734552291639018 中进一步介绍。
