# Chapter 7 — Technical concerns

This file records material technical issues in the English source that may mislead readers. These are source-content concerns, not translation corrections.

## High

### 1. The image's top layer is incorrectly described as writable at runtime

The source says the top layer of a container image is read-write and that changes can be made to the image at runtime. Container image layers are immutable. When a container is created, the container runtime adds a separate writable layer on top of the image layers. Runtime changes are made to that container's writable layer; they do not modify the underlying image.

**Suggested correction:** Distinguish the immutable image layers from the per-container writable layer. Explain that changes made in a running container are not automatically persisted into a new image.

### 2. Function as a Service (FaaS) is incorrectly equated with serverless deployment

The source says serverless deployments are “also known as” FaaS. FaaS is one serverless computing model, not a synonym for all serverless deployments. Serverless architectures can also use managed databases, event buses, queues, and other managed services without being function-based.

**Suggested correction:** Describe FaaS as one common form of serverless computing, rather than defining all serverless deployment as FaaS.

### 3. AWS Lambda is presented as a Kubernetes serverless platform

The source lists “AWS Lambda on Kubernetes” alongside Knative as a platform through which Kubernetes provides serverless capabilities. AWS Lambda is a managed serverless compute service; it is not ordinarily a workload platform running on a Kubernetes cluster. There are projects and integrations that connect Kubernetes workloads with Lambda, but that is a different architecture.

**Suggested correction:** Use Knative or another Kubernetes-native serverless framework as the Kubernetes example, and discuss AWS Lambda separately as a managed serverless service outside the Kubernetes cluster.

## Medium

### 4. Container processes are said to each have their own namespaces, filesystem, and network stack

The source says each process in a containerized environment has its own namespace, filesystem, and network stack. These isolation boundaries are generally configured for a container (or a group of containers), and processes within the same container share the relevant namespaces and filesystem view. A Pod can also share selected namespaces between its containers.

**Suggested correction:** Say that containers use namespaces and filesystem/network isolation to isolate groups of processes, rather than implying that every process has a separate set of namespaces and network stack.

### 5. Container termination conflates stopping a container with removing it

The source says `docker rm` terminates a container, releases allocated resources, and removes it from the host. `docker rm` removes a stopped container (or a running one when forced); stopping a container is a separate operation. Removing the container also does not necessarily remove separately managed volumes or external data.

**Suggested correction:** Distinguish stopping a container from removing its container instance and writable layer. Clarify that persistent volumes are managed separately and may outlive the container.

### 6. The PID 1 description overstates the role of an init process

The source says every container starts with an init process that manages other processes and handles signals. In many containers, the configured application or entrypoint itself runs as PID 1; it is not necessarily a dedicated init system. PID 1 has special signal and child-reaping responsibilities, which applications do not always handle correctly. A small init such as `tini` may be used when needed.

**Suggested correction:** Explain that the container's main process runs as PID 1. A dedicated init process may be used to forward signals and reap orphaned child processes, but it is not automatically present in every container.

### 7. The Kubernetes node terminology is outdated or imprecise

The source describes “manager or control plane nodes” and says worker nodes are also known as “minions.” Current Kubernetes terminology generally distinguishes control plane nodes and worker nodes; “minion” is historical terminology and is not the preferred term in current Kubernetes documentation. “Manager node” is also not a general synonym for a Kubernetes control plane node.

**Suggested correction:** Use “control plane node” and “worker node” consistently. If “minion” is retained for historical context, explicitly identify it as an older term.

### 8. kube-proxy is presented as a mandatory component on every worker node

The source says kube-proxy runs on each worker node and provides Service networking by maintaining network rules. This describes the common kube-proxy-based implementation, but kube-proxy is not mandatory in every Kubernetes cluster. Some networking implementations replace its functionality, for example with eBPF-based data planes.

**Suggested correction:** Qualify the statement: kube-proxy commonly runs on each node, but some cluster networking implementations provide the required Service forwarding without kube-proxy.

### 9. Readiness probes are presented as if they alone control traffic and guarantee safe rolling deployments

The source says that if a readiness probe fails, traffic is diverted away from a Pod, and describes the rolling deployment process as relying on readiness probes. A failed readiness probe marks a container/Pod as not ready; Kubernetes Service endpoint handling then normally excludes the Pod from ready endpoints. Actual traffic behavior depends on how traffic reaches the workload. Readiness probes do not by themselves guarantee zero downtime or trigger an automatic rollback.

**Suggested correction:** Explain the readiness state and its effect on Service endpoints, and distinguish that from rollout settings such as `maxSurge` and `maxUnavailable`. State that rollback requires an explicit action or an external deployment controller/automation.

### 10. StatefulSet is said to guarantee persistence without explaining its storage configuration

The source says StatefulSet ensures that Pods are “persisted across restarts.” StatefulSet provides stable Pod identity and can associate Pods with persistent volume claims through `volumeClaimTemplates`; it does not itself provide durable storage. Persistence depends on the configured PersistentVolumes, storage class, and underlying storage system.

**Suggested correction:** Explain that StatefulSet provides stable identities and can manage per-Pod persistent volume claims, while actual data durability depends on the storage provisioner and volume configuration.

### 11. Blue/green deployment is said to provide zero downtime as an inherent property

The source says routing traffic to the idle environment enables zero-downtime deployments. Blue/green deployment can reduce deployment downtime, but zero downtime is not guaranteed. Traffic switching, connection draining, database/schema compatibility, background jobs, state migration, and health validation can all affect availability.

**Suggested correction:** Say that blue/green deployment can enable near-zero-downtime releases when traffic switching, health checks, and backward-compatible state changes are designed appropriately.

### 12. Continuous deployment is described with a manual approval gate

The source defines continuous deployment as deploying changes through test and staging to production “without requiring manual intervention,” but then says significant changes may require an approval process before proceeding. This mixes continuous deployment with continuous delivery. A manual production approval gate is generally associated with continuous delivery; continuous deployment automatically releases changes that pass the pipeline's checks.

**Suggested correction:** Either describe the workflow as continuous delivery when production approval is required, or clarify that continuous deployment has no manual release approval after the required automated checks pass.

### 13. Image tags are implied to provide reliable version identity

The source recommends versioning and tagging images to ensure consistency across environments. Tags are mutable references and can be moved to point to a different image. Deploying by tag alone therefore does not guarantee that different environments use exactly the same image content.

**Suggested correction:** Recommend immutable tags or, more reliably, pinning deployments to image digests when exact artifact identity across environments is required.

### 14. VM isolation is described as complete, and container performance as native

The source describes VMs as fully isolated at the OS level and containers as providing native performance. These are broad generalizations. VM isolation depends on the hypervisor and configuration and is not absolute; containers share the host kernel and have a different isolation boundary. Container performance is often close to native, but can incur overhead from namespaces, cgroups, storage, networking, and virtualization layers.

**Suggested correction:** Use qualified language: VMs generally provide a stronger isolation boundary, while containers typically have lower overhead and often near-native performance. Avoid absolute claims.
