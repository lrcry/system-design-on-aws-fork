存储类型与关系型存储

数据存储是现代计算系统的核心组件， 在系统设计中扮演着至关重要的角色。随着企业和组织的发展，其产生和存储的数据量不断增加，因此拥有一个可扩展、可靠的存储基础设施以满足日益增长的需求变得尤为重要。高效、可靠地存储数据是确保应用程序和服务正常运行并为最终用户提供最优性能的必要条件。目前有多种类型的数据存储解决方案可供选择，从传统的文件存储系统到更现代的块存储和对象存储。数据库在存储和管理结构化数据方面也扮演着重要角色，是系统设计中不可或缺的关键要素。

在本章中，我们将在系统设计的背景下探讨不同类型的数据存储解决方案。我们将首先讨论传统的文件存储系统及其局限性，然后转向块存储和对象存储——这两种存储方式因能够处理大量非结构化数据，近年来越来越受到青睐。

本章还将介绍不同类型的关系数据库。（非关系型存储将在#ch03_nonrelational_stores_1734552286860587中介绍。）在研究关系数据库扩展的挑战时，我们将介绍各种技术，例如索引、SQL 优化、反规范化、联邦查询、分区、分片和复制，这些技术可以改善性能，满足大规模应用的需求。

在本章结束时，您将对现有的数据存储解决方案以及不同关系数据库类型的优缺点有深入的了解，并掌握如何利用它们设计高效、可靠且可扩展的系统。本章将为我们后续比较和选择 AWS 关系数据库产品奠定基础，相关内容包括多种版本的亚马逊关系数据库服务（Amazon RDS）和 Amazon Aurora，详见#ch10_aws_storage_services_1734552290474903。

数据存储格式

多年来，数据存储硬件的演进带来了一个颇具挑战性的问题： 如何将数据以某种特定格式存储，使其独立于底层存储硬件，并能在不同硬件上进行读取、写入和修改，即便硬件本身在不断演进。这促使计算机科学家和工程师开发出了设备驱动程序， 尤其是存储驱动程序，这些程序安装在不同的操作系统上，用于与特定存储硬件上的数据进行交互；数据以一种与底层硬件无关的特定格式存储。

基于数据在存储硬件上的逻辑组织方式，出现了三种不同的格式（如#ch02_figure_1_1734552286499796所示）：  文件存储、块存储和对象存储。每种格式都有其各自的功能和局限性。文件存储以文件和文件夹的层次结构来组织和表示数据；块存储将数据切分为任意组织的固定大小的块；对象存储则将数据组织为与关联元数据相连接的对象。下面我们逐一深入介绍这些存储格式。

文件存储

文件存储 是指将数据存储在文件夹中，就像将纸质文件存放在档案柜中一样。需要访问数据时，计算机必须知道找到数据的路径，这可能是一个冗长繁琐的路径字符串。文件存储通常用于存储结构化数据，例如文档、图像、视频和音频文件。

文件中的数据通过元数据进行组织和检索，类似于图书馆的卡片目录。想象一个装满文件柜的储藏室：每份文件都按照某种逻辑层次结构排列——按文件柜、按抽屉、按文件夹、按文件，最后按页面。文件系统为电子文件提供了类似的层次结构，数据以块或页的形式存储在磁盘上。

这是直连系统和网络连接系统中历史最悠久、使用最广泛的数据存储方式。它非常适合存储复杂文件，而且由于具有逻辑层次结构，导航比其他格式更加便捷。当您访问个人计算机上的文件时，就是在使用文件存储——将文件存储实例挂载到计算机或虚拟机后，它会被识别为本地目录。

文件存储的局限性在于，虚拟的"抽屉"只能开到一定程度，就像实体文件柜一样。文件存储系统必须通过横向扩展（增加更多系统）来实现容量增长，而无法通过纵向扩展（增加更多容量）来实现。

亚马逊弹性文件系统（Amazon EFS）   是 AWS 提供的一项可扩展、全托管的文件存储服务，可为亚马逊弹性计算云（Amazon EC2）实例提供共享文件存储，允许多个实例并发访问相同的数据，因此非常适合需要共享文件访问的应用程序。我们将在#ch10_aws_storage_services_1734552290474903中对其进行详细介绍。

块存储

块存储 将数据组织为固定大小的块或页，存储在磁盘或闪存上。每个块都分配有唯一地址，可以对各个块进行读写操作。块存储旨在将数据与用户环境分离，并将其分布到更适合提供数据服务的多个环境中。这意味着部分块数据可能位于 Windows 环境，另一些可能位于 Linux 环境，以此类推。当请求数据时，存储软件会从这些环境中重新组装数据块并提供给用户。块存储通常用于存储区域网络（SAN）环境，需要有正常运行的服务器才能工作。

与文件存储不同，块存储不依赖于数据的单一访问路径，因此数据检索速度更快。每个块独立存在，可以进行分区，以便在不同的操作系统中访问，这赋予用户完全的数据配置自由。它是一种高效可靠的数据存储方式，易于使用和管理。对于执行大型事务和部署大型数据库的企业来说，块存储表现尤为出色——需要存储的数据越多，块存储的优势越明显。

块存储的局限性在于成本较高。它处理元数据的能力有限，这意味着元数据处理必须在应用程序或数据库层面完成，从而给开发人员或系统管理员带来更多的复杂性。

块存储广泛应用于企业存储系统，如存储区域网络（SAN）和网络附加存储（NAS）。由于每个块可以作为独立磁盘运行，使管理员能够灵活地配置和分配存储卷，因此块存储比文件存储提供了更好的性能、可靠性和可扩展性。这使得块存储非常适合大型动态企业环境，在这些环境中，存储需要按需扩展或重新配置。

亚马逊弹性块存储（Amazon EBS）   在 AWS 云上提供可扩展的块存储卷，可挂载到 EC2 实例，为需要低延迟数据访问的应用程序（例如数据库和需要块级存储的应用程序）提供持久、高性能的存储。 我们将在#ch10_aws_storage_services_1734552290474903中对其进行介绍。

对象存储

对象存储是一种 存储架构，其中非结构化数据被分解为称为对象的离散单元，并存储在单一仓库中，而非传统的文件和文件夹结构或服务器块中。这些对象分布存储在多个硬件上，通过唯一标识符和描述数据的元数据进行访问——元数据包含诸如创建时间、安全和访问限制，甚至用于创建视频文件的设备位置等信息。

对象存储卷以模块化单元的形式运作，每个单元都是一个自包含的数据存储库。数据检索通过唯一标识符和元数据完成，这分散了工作负载，使管理员能够应用策略以实现更高效的搜索。对象存储还以其可扩展性、成本效益以及对静态非结构化数据的适用性而著称。它具有简单的 HTTP API，几乎被所有编程语言的客户端所支持。

然而，对象存储也存在局限性。对象一旦写入便无法修改，这意味着数据必须一次性完整写入。此外，对象存储不能很好地与传统数据库配合使用，因为写入对象的速度较慢，而且相比文件存储，将应用程序与对象存储 API 集成的复杂性更高。

选择数据存储格式取决于所存储数据的类型以及系统对性能、可靠性和可扩展性的要求。文件存储最适合结构化数据，而块存储和对象存储更适合非结构化数据。块存储比文件存储提供更好的性能和可靠性，而对象存储则提供更好的可扩展性和成本效益。

亚马逊简单存储服务（Amazon S3）  是 AWS 提供的一种对象存储服务，可通过 API 访问，为各种类型的数据提供高度可扩展、持久的存储。它适用于存储和检索大量数据、备份、静态网站内容以及用于分析的数据湖。更多详情请参阅#ch10_aws_storage_services_1734552290474903。 

我们已经了解了不同的数据存储格式，并从使用场景、成本、性能和可扩展性等维度做了比较。接下来，让我们探讨如何在数据库中存储和组织数据，以便检索和 处理。

关系数据库

数据库是一种   结构化的数据集合，在计算机系统中进行组织和存储，以便访问和管理。它的设计目标是高效地存储、检索和操作大量数据。数据库通常由一张或多张表组成，这些表按行和列进行组织。每行代表数据库中的一条唯一记录，每列代表记录的某一具体属性或信息。

数据库管理系统（DBMS）  则是一套软件系统，位于数据库之上，充当数据库与用户之间的桥梁（如#ch02_figure_2_1734552286499830所示）。DBMS 提供多种接口或 API，使用户能够存储、检索和操作数据。DBMS 还提供与事务、恢复、备份、并发、认证与授权、元数据目录等功能相关的一系列特性。

数据库可以根据其结构、使用方式和功能分为两大类：关系型和非关系型。本章将详细介绍关系数据库，非关系数据库将在#ch03_nonrelational_stores_1734552286860587中介绍。关系数据库使用一组相互关联的表来组织      数据。

关系数据库旨在存储和管理大量结构化数据，是目前最常见的数据库类型。它们 基于由 Edgar F. Codd 在 20 世纪 70 年代提出的关系模型，该模型将数据组织为表格，并通过键将表格相互关联。常见的开源关系数据库包括 MySQL、PostgreSQL 和 MariaDB。Oracle、Microsoft SQL Server、IBM Db2 和 SAP HANA 则是企业级关系数据库的主流选择。

关系数据库中的表按行和列进行组织，类似于电子表格。每行代表一条记录，每列代表记录的某一属性或数据项。列由数据类型定义，规定了该列可以存储的数据种类。#ch02_figure_3_1734552286499854展示了一个用于存储客户订单的数据库逻辑模式设计的示例实现。

数据库模式设计的逻辑组成部分包括：

表

 表是关系数据库的基本单元，以行和列的形式存储和组织数据。每张表代表一个特定的实体或概念，表中的每行代表该实体的一个具体实例，每列代表一个特定的属性。

行

行  （又称记录或元组）表示存储在表中的各条数据实例。每行包含与表列所定义属性相对应的数据值。表中的行是唯一的，通常通过主键进行标识。

列

列  （又称字段或属性）表示存储在表中数据的特定属性或特征。每列都定义了数据类型，用于确定该列可以存储的数据种类，例如整数、字符串、日期或二进制数据。

关联关系

关系数据库的  关键特性之一是能够在表之间创建关联关系，即表之间的关联。这通过键实现，键是能够唯一标识表中每条记录的列。最常见的关联关系类型包括一对一、一对多和多对多。这些关联关系有助于维护数据一致性，并实现相关信息的高效检索。

键

键    用于在表之间建立关联关系并确保数据完整性。主键用于标识表中的每一行，每条记录的主键值必须唯一。外键用于通过引用另一张表的主键来建立表之间的关联关系。通过键在表之间建立关联关系，使得跨多张表的数据检索和更新变得简单高效。键的详细内容将在本节后续部分介绍。

索引

索引 是通过对表内特定数据提供快速访问来增强查询性能的数据结构。索引创建在表的一列或多列上，基于索引值实现更快速的检索操作。

约束

约束 用于规定数据库中数据必须满足的规则和条件。常见的约束包括主键约束、外键约束、唯一约束和检查约束。它们确保数据完整性、保证参照完整性，并防止插入无效或不一致的数据。

视图

视图 是从一张或多张表中存储的数据派生出的虚拟表。它们基于预定义的查询创建，提供一种以自定义或简化方式呈现数据的途径，而无需修改底层表。视图可用于安全控制、数据抽象或简化复杂查询。

事务

关系数据库 使用事务来保持其状态一致性。在 DBMS 中，事务是一个逻辑工作单元，将对数据库的一系列操作作为单一不可分割的整体执行。这些操作可能包括向数据库中的一张或多张表插入、更新或删除数据。事务通过允许多个操作一起执行来确保数据的一致性和完整性。ACID（原子性、一致性、隔离性和持久性）特性规范了事务的行为，我们将在本节后续部分进行详细介绍。

这些逻辑核心组件共同构成了关系数据库模式的基础，提供了一种灵活、高效的方式来存储、组织和检索   结构化数据。

关系数据库概念

现在让我们了解构成现代关系数据库基础的基本概念，包括结构化查询语言（SQL）、ACID 以及实体-关系（E-R）模型。

SQL

关系数据库   使用 SQL 来操作和检索数据。SQL 允许用户通过一组命令来创建、修改和查询数据库。一些常见的 SQL 命令包括 SELECT、INSERT、UPDATE 和 DELETE。查询语言作为一种编程语言，规定了与数据库交互的语法、结构和语义。它提供了一种标准化的方式来存储、访问和操作数据库中的数据。

SQL 可分为以下四种类型，各自服务于不同的目的：

数据定义语言（DDL）

DDL  是一种用于创建和修改数据库对象结构与框架的查询语言，涵盖创建表、定义索引、删除表和删除索引等操作。

数据操作语言（DML）

DML  是一种用于创建、更新、删除和检索数据库信息的查询语言，涉及向表中插入行、更新现有行、删除行和查询数据等操作。

数据控制语言（DCL）

DCL  是一种旨在为客户端授予或撤销数据库内实体和操作访问权限的查询语言，包括向用户授予权限、撤销权限以及管理安全权限等命令。

事务控制语言（TCL）

TCL  是一种专门用于管理和确保一组数据库操作作为单一单元一致执行的查询语言，涵盖提交事务以使更改永久生效或回滚事务以丢弃更改等命令。

这些查询语言共同构成了 SQL 查询类型集合，提供了在数据库系统内定义、操作、控制访问和管理事务所需的必要工具。   

ACID

ACID 模型是一组  确保数据库事务可靠且准确处理的特性。ACID 代表：

原子性

事务必须全部成功或全部失败。

原子性 确保一系列操作被视为单一的逻辑工作单元。工作单元内的所有操作要么全部成功完成，要么一个都不应用。这一保证防止了对数据库的部分更新。当所有操作成功执行时，称为提交（commit）。如果发生故障，所有操作将被回滚，使数据库恢复到其原始状态。原子性使应用程序开发人员能够确信，即使在发生故障的情况下，数据库也始终处于一致状态。它还支持安全的重试操作，而无需担心创建重复数据。

一致性

事务必须维护数据库的一致性。

通过一致性 保证，数据库从一个有效状态转换到另一个有效状态。在转换过程中，数据库确保应用程序定义的规则和约束得到满足，以维护数据完整性。一致性是用户可控的特性，这意味着应用程序必须定义导致一致最终状态的有效规则和约束。例如，应用程序可能定义银行账户余额始终保持为正数的规则。数据库本身不强制执行这些规则，但确保对数据所做的任何更改都符合定义的一致性约束。

隔离性

事务之间必须相互隔离，以确保它们不会相互干扰。

隔离性 确保并发事务之间不会相互干扰，维护数据完整性并防止冲突。多个事务可以同时运行，隔离性保证规定了它们应该如何交互。如果并发执行事务的结果与顺序执行的结果相同，则表明数据库支持隔离性。隔离级别（如读未提交、读已提交、可重复读和串行化）定义了数据库提供的隔离程度。每个级别在并发性和数据完整性之间提供不同的权衡，因此应根据应用程序的要求选择合适的级别。

持久性

事务一旦提交，其更改必须是永久性的，能够在后续故障中存活。

持久性 保证一旦事务提交，其更改将永久存储，并能在系统故障（例如崩溃或断电）中保持存续。通常，这涉及将数据持久化到非易失性存储介质（如磁盘）。持久性确保关键数据长期安全可访问。即使面对灾难性事件，数据库也将保留已提交的更改，并在系统恢复时进行还原。

ACID 特性确保即使在发生故障或并发操作的情况下，数据库事务也能以可靠且一致的方式处理。通过确保这些特性，DBMS 能够维护数据库中存储数据的完整性和可靠性。  

E-R 模型

E-R 模型是一种    概念模型，用于关系数据库设计中描述实体（对象或概念）之间的关系及其属性。它提供了数据库模式的图形化表示，可用于设计、沟通和理解数据库结构。

如#ch02_figure_4_1734552286499874所示，E-R 模型用矩形表示实体，用椭圆表示属性，用菱形表示实体间的关系。关系可以是一对一、一对多或多对多。E-R 模型是设计和沟通数据库结构的有用工具，因为它使设计者能够可视化实体之间的关系以及描述实体的属性。

模式规范化

模式规范化是   指在数据库中组织数据以减少冗余并提高数据完整性的过程。它涉及将大型表分解为更小、更易于管理的表，每张表都有其独特的用途和属性集。模式规范化的目标是最小化数据重复，确保数据库中的每条数据只存储在一个地方。

以我们订单数据库中名为 Customers 的表为例，该表包含以下列：customer_id、customer_name、customer_email、customer_address 和 customer_phone。在该表中，customer_name、customer_email、customer_address 和 customer_phone 对每位客户都重复存储。

为对该模式进行规范化（如#ch02_figure_5_1734552286499895所示），我们可以将 Customers 表分解为两张表：CustomerInfo 和 CustomerContact。CustomerInfo 表将包含 customer_id 和 customer_name，而 CustomerContact 表将包含 customer_id、customer_email、customer_address 和 customer_phone。

通过这样做，我们消除了 Customers 表中客户信息的冗余，将其仅存储在 CustomerInfo 表中一次。这种规范化减少了数据库所需的存储空间，消除了冗余数据可能引起的数据不一致性，并使更新客户信息变得更加便捷，无需在多处进行   修改。

键

键  用于在关系数据库中建立表之间的关系。键是一列或一组列，能够唯一标识表中的每一行。键的类型有以下几种：

候选键

候选键  是表中能够唯一标识该表中每条记录的一列或一组列。之所以称其为"候选"键，是因为它是该表主键的潜在候选。例如，在客户表中，customer_email 可以是候选键，因为每位客户都有唯一的电子邮件地址。

主键

主键  是被选定为表的主要键的候选键。它唯一标识表中的每条记录，并被与该表存在关联关系的其他表作为参照引用。例如，在订单表中，订单 ID 可以作为主键。

外键

外键  是一张表中的一列或一组列，引用另一张表的主键。它用于在表之间建立关系并确保数据完整性。例如，在订单表中，可以有一个外键引用 Customers 表中的 customer ID，以将每个订单与下单客户关联起来。  

现在，让我们讨论 DBMS 架构所需的核心组件。不同实现的具体架构可能有所不同，但核心组件通常保持一致。

关系型数据库管理系统架构

关系型数据库管理系统（RDBMS）    的架构如#ch02_figure_6_1734552286499914所示。

让我们逐一介绍各个组件：

查询处理器

查询处理器  将用户查询转换为适合底层执行引擎的执行格式。它有两个主要子模块：查询解析器和查询优化器：

  • 查询解析器  将用户给定的查询解析为抽象语法树（AST），  作为查询执行的中间表示。查询解析器在生成 AST 的过程中执行解析、词法分析、语法验证、语义分析和树构建操作。

  • 查询优化器  使用查询解析器生成的 AST，为用户查询生成优化的执行计划。通过考虑数据基数、数据分布以及本地和远程执行相关成本等内部统计信息，优化器评估多个执行计划。

执行计划

执行计划 表示一系列以有向依赖图形式组织的步骤，这些步骤必须按特定顺序执行以满足用户查询。利用内部统计信息，查询优化器从备选方案中选择最具成本效益的执行计划，然后将所选计划转发给执行引擎处理。

执行引擎

执行引擎 负责执行查询优化器生成的查询计划。它与存储引擎交互以检索数据，执行必要的连接（join）、过滤和排序操作，并将结果集返回给用户。执行引擎还负责在分布式关系数据库中跨分布式节点协调执行计划。

存储引擎

存储引擎 管理数据的物理存储和检索，包括数据库中数据的访问和操作。它处理数据页管理、文件分配、数据压缩和索引等任务。存储引擎与执行引擎交互，以高效地获取和存储数据。

缓冲区管理器

缓冲区管理器 负责管理内存中的数据缓冲区。它控制磁盘和内存之间的数据移动，优化磁盘 I/O 操作，并确保频繁访问的数据保留在内存中以实现更快的访问。缓冲区管理器通过在内存中缓存数据页来最小化磁盘访问。

缓存管理器

缓存管理器 负责管理和优化数据缓存。它将频繁访问的数据存储在内存中，通过减少磁盘 I/O 操作来提高查询性能。缓存管理器确保最常用的数据在内存中随时可用，以便更快地检索。

事务管理器

事务管理器 在协调和监督存储结构模块内数据结构上的操作方面发挥着至关重要的作用。其主要职责是确保一系列操作要么作为一个整体成功执行，要么完全回滚，不留下任何部分更新。这一关键保证使最终用户能够确信，数据库在执行任何数据库操作前后都能始终保持完整性。为实现这一点，事务管理器与并发控制管理器和恢复管理器紧密协作。通过利用这些组件，事务管理器确保数据库中可见的数据保持一致，并符合最终用户的期望。

并发控制管理器

并发控制管理器 处理多用户或多事务对数据库的并发访问。它确保事务以隔离且一致的方式执行，防止冲突并维护数据完整性。它管理锁机制、事务隔离级别和冲突解决机制。

恢复管理器

恢复管理器 确保数据库在发生故障或崩溃时的持久性和可靠性。它管理事务日志、检查点和崩溃恢复机制，以维护数据完整性和一致性。恢复管理器确保数据库在故障后能够恢复到一致状态。

恢复管理器通过在 DBMS 中维护称为日志文件的不可变数据结构来确保持久性。该日志文件详细记录应用于数据库的每一次写操作，以便恢复。本质上，恢复管理器充当所有写请求可靠且持久的中间存储。

每个写入的页面都被小心保存在主内存中，标记为"脏页"。为确保持久性，恢复管理器将所有脏页批量处理并异步刷写到磁盘。一旦脏页成功刷新到磁盘，它们就被视为"干净页"。此外，在写请求被客户端确认完成之前，它会被追加到一个驻留在磁盘上的仅追加数据结构中。这一步骤可防止在崩溃或系统重启时脏页的数据丢失。

日志文件作为宝贵的检查点，使恢复过程能够为脏页恢复数据。在系统重启时，操作系统将所有剩余脏页刷新到磁盘，并丢弃任何未提交的事务。这确保系统以干净的状态启动，准备好处理后续的写入和读取操作，不存在不完整或不一致数据的风险。

安全管理器

安全管理器 负责数据安全和访问控制。它对用户进行身份验证，管理用户权限和特权，并确保数据的保密性、完整性和可用性。安全管理器保护数据库免受未授权访问，并维护数据隐私。

系统目录

系统目录   （又称数据字典或元数据存储库）存储有关数据库模式、表、列、索引、约束和其他数据库对象的元数据。它提供有关数据库结构和组织的信息，使 RDBMS 能够准确地解释和操作数据。

这些核心组件共同协作，为 RDBMS 中的数据管理和操作提供必要功能。它们确保高效的查询处理、数据存储、并发控制、数据恢复和数据安全。

在下一节中，我们将探讨使用索引类型（包括主索引和二级索引）、SQL 优化、反规范化和联邦查询来优化 RDBMS 中查询性能的不同方法。    

关系数据库优化

优化   关系数据库是任何数据库管理员或开发人员的重要任务，旨在提升运行其上的查询性能。让我们了解优化数据库的各种方法。

索引

优化 SQL 查询的一种方法是使用索引。 索引是一种数据结构，可以提高数据库表上数据检索操作的速度。通过在频繁使用的列上创建索引，优化器可以快速找到执行查询所需的数据，从而比执行全表扫描获得更快的查询执行时间。您查询的列（SELECT、GROUP BY、ORDER BY、JOIN）使用索引后速度可能更快。索引通常以自平衡 B树的形式表示，以排序方式保存数据，并支持在对数时间内完成搜索、顺序访问、插入和删除操作。以下是 RDBMS 中可以创建的两种索引类型：

主索引

主索引 是在表的主键（唯一标识表中每行的一列或一组列）上创建的索引。通过在主键上创建主索引，数据库可以快速找到表中特定行的位置，从而加快数据检索速度。

二级索引

二级索引 是在非主键列或一组列上创建的索引。二级索引可用于提高涉及基于特定列或一组列进行过滤或排序的查询性能。例如，如果查询频繁根据客户的电话号码过滤数据，在电话号码列上创建二级索引可以显著提高查询性能。

B+树 在 RDBMS 中被广泛用作索引结构，以支持快速数据检索和高效查询处理。B+树数据结构为对大量数据的基于键的搜索和范围查询提供高效支持。如#ch02_figure_7_1734552286499934所示，B+树是一种以排序方式存储数据的自平衡树数据结构。它由内部节点和叶节点组成，叶节点包含实际数据记录或指向数据记录的指针。B+树中的每个节点有固定数量的键和指针。内部节点中的键充当分隔符，引导搜索过程，而叶节点则以排序顺序存储数据记录或指向数据记录的指针。

在列上创建索引时，会构建一个 B+树索引，树中的每个节点对应于被索引列的一个值范围。B+树的叶节点包含被索引列的值以及指向实际数据记录的相应指针。B+树还可用于在 RDBMS 中创建多列索引。在这种情况下，B+树中的每个节点包含多个键，支持基于多列的高效搜索和查询。复合索引（又称多列索引）对于涉及复杂条件或多列连接操作的查询非常有益。

B+树提供高效的基于键的搜索和范围查询，这对于提高 RDBMS 中的查询性能至关重要。当查询涉及搜索特定值或值范围时，B+树索引允许数据库系统快速遍历树以找到所需的数据记录。B+树的平衡特性确保树的高度相对较小，从而实现对数时间复杂度的快速搜索操作。

B+树还能在 RDBMS 中实现高效的顺序扫描和范围扫描。B+树的叶节点相互链接，支持对整个索引或特定值范围进行扫描。顺序扫描或范围扫描通常用于涉及排序或聚合的查询，或需要根据特定条件检索数据子集时。

最后，B+树能在 RDBMS 中高效处理更新和插入操作。插入新记录时，B+树索引的更新方式能确保树的平衡性和排序顺序得以维护。同样，更新记录时，B+树索引中的相应条目也会相应调整。这种在不显著降低性能的情况下处理动态更新和插入的能力使 B+树非常适合事务系统。

使用大量索引也有其代价，因为放置索引可能会将数据保留在内存中，需要更多空间。由于索引也需要更新，写操作可能会变慢。当加载大量数据时，禁用索引、加载数据，然后  重建索引可能会更快。

SQL 优化

如 #ch01_guideline_of_performance_metrics_don_t_lie_1734552285983169章节所述，要提高 SQL 查询的性能，首先需要对查询进行基准性能测试和性能分析  以发现瓶颈。基准性能测试涉及模拟高负载和高吞吐量的场景，而性能分析则需要测量查询的 p90 延迟并分析慢查询日志以识别性能问题。基于这些指标，SQL 优化是通过消除瓶颈和优化查询计划来提升 SQL 查询性能的过程。

优化 SQL 查询的一种方法是最小化大型写操作，因为执行写入、修改、删除或导入大量数据等操作可能对查询性能产生重大影响。这些操作甚至可能在涉及更新和操作数据、向查询添加索引或检查约束、处理触发器等类似操作时导致表锁定。此外，写入大量数据将不可避免地导致日志文件大小增加。

另一种优化 SQL 性能的技术是在非高峰时段安排查询执行。这种方法在处理涉及大型表的多个 SELECT 查询或执行带有嵌套子查询、循环查询等复杂查询时尤为有效。在数据库中执行资源密集型查询时，RDBMS 会对相关表加锁，阻止不同事务同时访问。这导致其他用户无法操作这些表，限制了对特定数据的访问。在高峰时段运行繁重查询不仅会给服务器带来压力，还会限制其他用户的数据访问。

向查询添加多张表并执行连接操作可能会加重查询负担并导致性能问题。此外，从大量表中检索数据可能导致执行计划效率低下。JOIN 消除是实现高效查询计划的众多技术之一。将单个查询分成几个可以稍后合并的独立查询，可以消除不必要的连接、子查询和表。这种方法通过删除冗余和多余的元素来简化查询并提高其性能。

提升 RDBMS 性能和优化 SQL 查询是数据库开发人员和管理员的关键任务。他们必须仔细评估各种因素，例如特定运算符的选择、查询涉及的表数量、查询大小、执行计划、统计信息、资源分配以及其他性能指标。这些考量因素在决定查询性能是提升还是下降方面起着关键作用。通过仔细分析和解决这些因素，开发人员和管理员可以有效地调优和改善 查询性能。

反规范化

在 大多数系统中，读操作明显多于写操作，比例可达 100:1 甚至 1,000:1。在读取过程中执行复杂的数据库连接操作可能非常消耗资源，尤其是由于磁盘操作的原因。

反规范化是一种旨在提高读取性能的技术，但可能以降低写入性能为代价。它通过在多张表中复制数据来避免代价高昂的连接操作。一些 RDBMS 提供物化视图，负责存储冗余信息并维护冗余副本之间的一致性。

当数据通过联邦查询和分片等方法进行分布时，管理跨不同数据中心的连接操作会增加更多复杂性。反规范化可以帮助减少此类场景中对复杂连接的需求。然而，反规范化也有其缺点，因为数据重复会导致冗余。维护冗余副本之间的一致性需要使用约束，这进一步增加了数据库设计的复杂性。如果多张表存储客户电子邮件地址的冗余副本——例如在 Customers 表和 Orders 表中——Customers 表中电子邮件的唯一约束有助于防止重复的电子邮件条目。此外，设置触发器或级联更新约束可以确保 Customers 表中电子邮件的更新自动同步到 Orders 表，防止出现不一致的副本。因此，在高写入负载下，反规范化的数据库可能比规范化的数据库表现更差。

总体而言，反规范化可以为读取密集型工作负载提供性能优势，但会在数据冗余和数据库管理复杂性方面带来权衡。 

联邦查询

联邦查询是一种 将大型查询拆分为可以在不同数据库服务器上独立执行的小型查询的技术。这种技术需要模式联合（schema federation）——即跨多个数据库服务器对数据库进行功能性分区。在不同服务器上执行较小的查询可以减少总体查询执行时间，从而获得更快的查询结果。联邦查询对于优化涉及大量数据或复杂连接的查询非常有用。

通过使用这些技术优化关系数据库，数据库管理员可以提高性能，为数据提供更快、更高效的访问。接下来，我们将介绍在实践中用于扩展关系数据库的技术。  

关系数据库扩展

随着  企业的发展和数据需求的增加，有必要扩展数据库以处理增加的工作负载。扩展是指增加数据库容量以适应更多数据、用户和事务的过程。让我们探讨使用分区、分片和复制来扩展关系数据库。

分区

分区是 将大型数据库表划分为称为分区的更小、更易管理的部分的过程。数据库中的每条记录都被分配到特定分区，确保每条记录属于且仅属于一个分区。每个分区作为独立的数据库运行，能够自主执行读写操作。因此，数据库查询可以定向到单个分区以专注于特定数据，或分布在多个分区上进行更广泛的处理。客户端可以将查询定向到特定分区，也可以定向到协调节点，协调节点再将查询转发到正确的分区集，从而对分区进行编排。如#ch02_figure_8_1734552286499953所示，分区有垂直分区和水平分区两种类型，其中水平分区有两种可能的实现方式。

垂直分区 涉及按列拆分表。例如，一张客户表可以拆分为两张表，一张包含客户信息，另一张包含客户联系数据。

水平分区 涉及按行拆分表。例如，一张大型客户表可以拆分为多张更小的表，每张表包含基于姓氏或邮政编码的特定范围的客户记录。水平分区有两种实现方式：哈希分区和范围分区。

哈希分区

按键哈希进行分区 的策略涉及生成键的哈希值并将其均匀分布到各分区中。在此策略中，哈希函数（如 MD5 或 SHA-256）被应用于表的输入键。哈希范围被划分为桶，每个桶被分配到特定分区。值得注意的是，单个主机实例可以容纳多个分区。

为使此策略有效运行，哈希函数必须是确定性的，即相同的键应始终产生相同的哈希值并被定向到相同的分区。此外，每个键应解析为唯一的哈希值，确保数据在各分区之间的均衡分布。

哈希分区的优点是通过使用唯一的确定性哈希策略，消除了范围分区中可能出现的数据热点和分区数据倾斜问题。然而，由于分区基于键的哈希值，此策略无法进行范围查询。如果需要获取一组键，必须查询所有分区，使 DBMS 执行散发-汇聚（scatter and gather） 模式。

范围分区

在范围分区中， 我们将连续的键范围分成独立的桶，这些桶再被分配到特定分区。值得注意的是，单个主机实例可以容纳多个分区。分配给每个桶的键范围可以是连续的，也可以是不连续的，在数据分布方面具有灵活性。

在每个分区内，键以排序顺序存储。这种数据组织方式支持高效的范围扫描查询，因为它简化了在特定键范围内检索数据的过程。系统可以快速访问和检索落在给定范围内的数据。在#ch02_figure_8_1734552286499953所示的示例中，可以轻松按字典序检索所有电子邮件以 P 开头的客户。此外，范围分区策略实现起来相对简单。

然而，如果分区上的访问模式不均匀或不公平，某些分区最终可能拥有比其他分区更多的数据或查询，导致分区数据倾斜并使特定分区承受更大的负载，这可能造成拥塞。这些承受不成比例高工作负载的不平衡分区被称为数据热点。 例如，在#ch02_figure_8_1734552286499953中，如果绝大多数客户的电子邮件以 A 开头，将导致分区 1 因集中于该分区的大量数据和查询而过载。

对数据库进行分区为大型数据集提供了优势，并实现了高吞吐量能力。分区使数据能够通过分片分布在多台机器上，允许处理超出单台机器容量的数据集。通过将数据分散到多个分区，数据库可以适应并管理大规模数据需求。

数据分布在多个分区后，读写查询可以由每个分区独立处理。这种并行处理能力使数据库能够比单台机器处理更高的总体吞吐量。通过利用多台机器的集体力量，分区增强了系统高效处理并发查询和事务的能力。因此，分区可以通过减少执行查询所需扫描的数据量来提高查询性能，从而实现更快的查询响应时间 和更好的可扩展性。

分片

分片是 将大型数据库分布在多台服务器上的过程。每台服务器包含数据的一个子集，查询分布在所有服务器上。分片对于扩展已变得过大而无法在单台服务器上管理的数据库非常有用。例如，在"customers"数据库中，随着客户数量的增长，可以向集群添加更多分片以适应不断增加的负载。对客户表进行分片的常见方式包括使用客户的姓氏、首字母或地理位置。

分片有两种类型（如#ch02_figure_9_1734552286499972所示）：垂直分片和水平分片，其中水平分区有不同的实现方式，包括基于哈希、基于范围和轮询（round-robin）分片。

分片提供了与联邦查询类似的优势，包括减少读写流量、减少复制和提高缓存利用率。它还有助于减小索引大小，从而提高查询性能。在某个分片发生故障时，其他分片仍然可以运行，但实现复制对于防止数据丢失至关重要。分片消除了对写串行化的中央主节点的需求，实现了并行写入并提高了总体吞吐量。

然而，分片也有其缺点。应用程序逻辑需要更新以处理特定分片的操作，可能导致复杂的 SQL 查询。数据分布可能变得不平衡，特别是当某个分片拥有一批高频用户时，会增加该特定分片的负载。重新平衡分片增加了复杂性，尽管使用一致性基于哈希的分片函数可以最小化数据传输量。跨多个分片的数据联接变得更具挑战性，总体而言，分片带来了额外的硬件需求和增加的系统复杂性。

复制

复制是 将数据从一台数据库服务器复制到另一台的过程。存储数据副本的每个节点称为副本（replica）。复制是分布式数据库的关键特性，在增强可用性、负载均衡和降低延迟方面提供了多项优势。通过在不同主机机器上维护多个数据副本，复制提供了以下优势：

高可用性

复制 通过在多台主机机器上存储数据副本来确保高可用性。当某台主机机器发生故障或停机时，数据库可以无缝地将读写操作重定向到其他持有复制数据的运行机器。这种容错机制可以防止服务中断，确保对数据的持续访问，提高系统的整体可用性。

负载均衡

通过复制， 数据库可以将读写查询分发到多台主机机器上。这种负载均衡策略防止单台机器过载，从而提高整体系统性能和可扩展性。通过分散工作负载，复制实现了计算资源的高效利用和对并发用户请求的更好处理，提升了吞吐量和响应能力。

降低延迟

将数据复制到地理上分散的主机机器上， 可以将复制副本放置在距离最终用户更近的位置。这种接近性减少了用户访问数据库时所经历的网络延迟。通过最小化数据与用户之间的距离，复制改善了响应时间并提升了用户体验，尤其适用于低延迟至关重要的场景，例如实时应用或用户位于不同地区的分布式系统。

灾难恢复与数据弹性

复制  是灾难恢复策略的基础。通过维护多个数据副本，分布式数据库可以抵御灾难性事件、硬件故障或自然灾害。在某台主机机器上数据丢失或不可用的情况下，可以利用复制副本进行数据恢复和系统还原。复制确保了数据弹性并最小化数据丢失风险，有助于提高数据库的整体可靠性和健壮性。

可扩展性与性能

复制  在扩展分布式数据库方面发挥着至关重要的作用。随着数据量或用户负载的增加，可以向系统添加额外的主机机器，每台机器都托管数据的复制副本。这种水平扩展方式允许数据库处理更大的工作负载并适应不断增长的用户需求。通过分布数据和查询，复制有助于改善系统性能，实现高效的并行处理并缩短响应时间。

RDBMS 的两种复制类型是单领导者复制和多领导者复制，两者均如#ch02_figure_10_1734552286499992所示。

在单领导者复制中， 一台数据库服务器作为领导者，其他服务器作为追随者。领导者服务器处理所有写操作，而追随者服务器处理读操作。领导者服务器上的更改以同步或异步方式复制到追随者服务器，确保所有服务器包含相同的数据。这种类型的复制对于扩展读密集型数据库非常有用。

在多领导者复制中， 每台数据库服务器都可以读写数据。对一台服务器所做的更改以同步或异步方式复制到其他服务器，确保所有服务器包含相同的数据。这种类型的复制对于扩展需要高可用性的数据库非常有用。在单领导者复制中，领导者选举和晋升会存在滞后，但在多领导者复制中，故障影响被隐藏，形成高可用性设置。然而，这带来了一个权衡：冲突解决，我们在#ch01_system_design_trade_offs_and_guidelines_1734552285979675中讨论过。由于写操作可以在多个领导者上独立进行，当同一数据在不同位置被同时修改时，可能会出现冲突更新。

对于这些复制类型，可以在追随者节点上进行全量复制、基于快照的复制、事务复制（即复制事务更新）或基于键的增量复制（即扫描数据库中已修改的键并仅复制这些键的数据）。复制可以同步或异步进行，各有其优缺点。

同步复制

在 分布式数据库中，同步复制提供了一种使用同步通信将数据从领导者副本复制到追随者副本的机制，使所有副本中的数据始终保持最新。通过维护始终与领导者副本同步的同步副本，这种复制机制提供了以下优势：

一致性写入

通过同步复制，客户端只有在领导者副本和同步追随者副本都确认后，才认为写操作成功。这种严格的同步确保了副本之间的数据一致性。通过等待来自两个副本的确认，系统保证写操作已被持久提交，并可供后续读操作使用。尽管这会增加延迟，但对于需要严格数据完整性和准确性的应用程序来说，这种一致性至关重要。

即时故障转移

同步复制的一个重要优势是其在领导者副本崩溃时实现即时故障转移的能力。由于同步副本始终与领导者保持同步，这些副本中的任何一个都可以立即晋升为新的领导者而不会丢失任何数据。这种无缝转换确保了即使发生故障，系统也能持续可用。通过消除停机时间和最小化数据丢失，同步复制增强了分布式系统的整体弹性和可靠性。

数据持久性

同步副本保证数据在多个副本中持久存储。当写操作得到领导者和同步追随者副本双方的确认时，确保数据安全地持久化在多台机器上。这种冗余提供了数据持久性，防止在副本故障或系统崩溃时发生数据丢失。通过维护多个同步副本，同步复制确保关键数据保持完整且可恢复，提高系统的整体数据弹性。

读操作一致性

同步复制不仅在写操作中确保一致性，在读操作中也同样如此。由于同步副本始终与领导者保持同步，可以在任何副本上执行读操作，并保证访问最新且一致的数据。此特性支持负载均衡，并提高了系统处理读密集型工作负载的能力。

总结而言，分布式数据库中的同步复制提供了一致性写入、即时故障转移、数据持久性和读操作一致性等优势。通过维护始终与领导者同步的同步副本，这种复制机制确保了数据完整性、持续可用性以及对最新信息的可靠访问。同步复制在严格一致性和高可用性至关重要的场景中尤为有价值，例如金融系统、实时应用和关键任务 环境。

异步复制

在 分布式数据库中，异步复制提供了一种将数据从领导者副本复制到异步副本的机制。这种复制方式具有以下特点和注意事项：

准实时更新

异步副本以准实时方式应用来自领导者副本的更改，但可能存在一定延迟。这意味着异步副本可能不会立即与领导者上的最新更改保持同步。领导者和异步副本之间的时间延迟会导致副本之间数据的临时不一致性。然而，随着时间推移，异步副本会追赶上领导者的更新而收敛。

数据滞后与潜在陈旧性

由于复制的异步特性，异步副本可能会落后于领导者副本。这种滞后的程度取决于多种因素，如网络条件、系统负载和正在复制的更改量。因此，异步副本可能无法反映数据的最新状态。这种潜在的陈旧性可能影响需要访问最新信息的应用程序或使用场景。在采用异步复制时，需要认真权衡准实时更新和潜在数据滞后之间的平衡。

数据丢失风险

由于异步副本可能存在滞后或数据陈旧，在领导者副本崩溃时将异步副本提升为新的领导者可能会带来数据丢失风险。由于异步副本可能尚未接收或应用前任领导者上的所有更改，过早提升它可能导致数据缺失或不一致。为降低这一风险，在将其提升为新领导者之前，应采取谨慎的考量和措施，例如监控复制滞后并确保异步副本已充分追赶。

可扩展性与性能

异步复制通常在优先考虑可扩展性和性能而非严格一致性的分布式系统中受到青睐。通过在复制过程中允许一定的灵活性并容忍临时数据不一致性，异步复制可以处理高写入吞吐量并适应大规模部署的系统。这种方式使系统能够分散工作负载并水平扩展，同时保持可接受的响应时间。

总结而言，分布式数据库中的异步复制提供准实时更新，但引入了数据滞后和潜在陈旧性的可能性。虽然它提供了可扩展性和性能优势，但在将异步副本提升为新领导者时存在数据丢失风险。采用异步复制时，需要仔细规划、监控和适当的降级机制，以确保数据完整性并最小化数据不一致性的影响。 

扩展分布式关系数据库是需要处理日益增长的数据量和流量的企业的重要任务。分区、分片和复制都是扩展数据库的有用技术。分区可以通过减少执行查询所需扫描的数据量来提高查询性能。分片对于扩展已变得过大而无法在单台服务器上管理的数据库非常有用。复制对于扩展需要高可用性或有大量读流量的数据库非常有用。

开源关系型数据库系统

开源 RDBMS    因其实惠、灵活以及社区支持而成为企业和开发人员的热门选择。两种广泛使用的开源 RDBMS 是 MySQL 和 PostgreSQL。在本节中，我们将对 MySQL 和 PostgreSQL 进行比较。

MySQL

MySQL 是一款于 1995 年首次发布的开源 RDBMS。它是世界上最流行的 RDBMS 之一，拥有庞大的用户社区和丰富的功能集。MySQL 以其速度和可扩展性著称，是需要处理大量数据和流量的企业的理想选择。

MySQL 的功能特性包括：

  • 支持 SQL 和 NoSQL 查询

  • 可扩展的架构

  • 高性能

  • 简单易用

  • 能够处理读密集型工作负载

  • 对集群和复制的强力支持

PostgreSQL

PostgreSQL 是一款于 1996 年首次发布的开源 RDBMS。它以健壮性、可靠性和功能丰富性著称。PostgreSQL 是需要高级数据管理功能和强大查询处理能力的企业的热门选择。

PostgreSQL 的功能特性包括：

  • 支持 SQL 和 NoSQL 查询

  • 符合 ACID 的事务

  • 对存储过程和触发器的强力支持

  • 支持 JSON 和 XML 数据类型

  • 能够处理写密集型工作负载

  • 高级数据管理功能

MySQL 与 PostgreSQL 的比较见#ch02_table_1_1734552286506439。两者都是开源 RDBMS，均符合 ACID 标准，均支持 SQL 和 NoSQL 查询。两者都对复制和集群提供强力支持。然而，MySQL 具有更简单直接的语法，而 PostgreSQL 提供更高级的功能和特性。MySQL 更适合读密集型工作负载；PostgreSQL 更适合写密集型工作负载。
